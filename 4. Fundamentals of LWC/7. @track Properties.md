# @track Properties in LWC

This document explains the **`@track` decorator** in Lightning Web Components (LWC) — why it's needed, how it differs from a normal property, and how to use it to track changes inside objects and arrays.

---

## 📌 What is `@track` Property?

> 🔎 **Definition (from training material):**
> When a field contains an **object** or an **array**, there's a limit to the depth of changes that are tracked. To tell the framework to observe changes to the **properties of an object** or to the **elements of an array**, decorate the field with `@track`.

In simple words: normally, LWC's reactivity system can only detect when you **replace the entire value** of a property. But if your property is an **object or array**, and you only change one **inner field/element** of it (not the whole object), LWC won't automatically notice that change — **unless** you decorate that property with `@track`.

---

## ⚖️ Normal Property vs `@track` Property

> 🔎 **Definition (from training material):**
> Without using `@track`, the framework observes changes that **assign a new value** to a field/property. If the new value is **not `===`** to the previous value, the component **re-renders**.

Let's break this down:

| | **Normal Property** | **`@track` Property** |
|---|---|---|
| **What it detects** | Only detects when the **entire value is reassigned** with something not `===` (strictly equal) to the old value | Detects changes made to **nested fields inside an object**, or **elements inside an array** |
| **Best suited for** | Primitive values (String, Number, Boolean) or objects/arrays that are always **fully replaced** | Objects/arrays where you update **individual properties/elements** without replacing the whole object/array |
| **Example that works without `@track`** | `this.title = 'Admin';` (a brand-new string value is assigned) | — |
| **Example that needs `@track`** | — | `this.address.city = 'Mumbai';` (only one field of the `address` object changes, the object itself is not replaced) |

**In short:** Use `@track` whenever you are mutating a **property inside an object** (like `this.address.city = ...`) rather than replacing the object entirely (like `this.address = {...}`).

## 🧩 Full Code Example

### JavaScript Controller (`helloWorld.js`)

```javascript
import { LightningElement, track } from 'lwc';

export default class HelloWorld extends LightningElement {
    fullName = 'Arun Kumar';
    title = 'Salesforce Developer';

    handleClick(event) {
        this.title = event.target.value;
    }

    @track address = {
        city: 'Chennai',
        Code: '600001',
        state: 'Tamil Nadu',
        country: 'India'
    };

    handleChange(event) {
        this.address.city = event.target.value;
    }
}
```

**Explanation:**
- `import { LightningElement, track } from 'lwc';` — the `track` decorator must be **imported** from the `lwc` module before it can be used.
- `fullName` and `title` are **normal properties** — simple strings that get fully reassigned, so they don't need `@track`.
- `handleClick(event)` — updates `title` with a brand-new string value (`event.target.value`), which is a **full reassignment**, so a normal property works fine here.
- `@track address = { ... }` — the `address` field is an **object** with nested properties (`city`, `Code`, `state`, `country`). It is decorated with `@track` so that changes to **individual fields inside it** (like just `city`) are also observed by the framework.
- `handleChange(event)` — this method updates **only the `city` field** inside the `address` object (`this.address.city = ...`), **without replacing the whole `address` object**. This is exactly the situation where `@track` is required — without it, the template would **not re-render** to show the updated city.

---

### HTML Template (`helloWorld.html`)

```html
<template>
    <lightning-card title="Two way Data Binding">
        <div class="slds-m-around_small">
            <lightning-input type="text" label="Enter Title" onkeyup={handleClick}></lightning-input>
            <div>{fullName} is a {title}</div>
        </div>
    </lightning-card>

    <lightning-card title="@track Properties">
        <div class="slds-m-around_small">
            <lightning-input type="text" label="Enter Title" onkeyup={handleChange}></lightning-input>
            <div>{address.city} is my city</div>
        </div>
    </lightning-card>
</template>
```

**Explanation:**
- The template has **two `lightning-card` sections**:
  1. **"Two way Data Binding" card** — recap of the previous concept, where typing in the input updates the `title` property directly (normal property, no `@track` needed).
  2. **"@track Properties" card** — a new input bound to `handleChange`. Every time the user types and releases a key (`onkeyup`), `handleChange` runs and updates `address.city`.
- `{address.city}` in the template uses **dot notation** to display the nested `city` field from the `address` object. Because `address` is decorated with `@track`, this value **updates live** on the page as the user types.

---

## 🎯 Step-by-Step Execution Flow

1. Component loads → `address = { city: 'Chennai', Code: '600001', state: 'Tamil Nadu', country: 'India' }`.
2. The page initially displays:
   > *Chennai is my city*
3. User types `"Mumbai"` into the **Enter Title** input box under the "@track Properties" card.
4. On every key release (`onkeyup`), `handleChange(event)` runs.
5. `this.address.city = event.target.value;` updates **only the `city` key** inside the `address` object.
6. Because `address` is decorated with `@track`, LWC detects this **nested change** and re-renders the template.
7. The page now updates to show:
   > *Mumbai is my city*

> ⚠️ **Without `@track`:** If `address` was a normal property (no `@track`), step 6 would **fail silently** — the `city` value would technically change in memory, but the UI would **not update**, because LWC only tracks full reassignments of the property by default.

## 📊 Summary Table

| Concept | Explanation |
|---|---|
| **`@track`** | A decorator imported from `lwc` that tells the framework to observe changes to nested properties of an object or elements of an array |
| **When required** | When mutating a field/element **inside** an object or array (e.g., `this.address.city = ...`) |
| **When NOT required** | When fully reassigning a primitive or replacing the entire object/array (e.g., `this.title = 'Admin'`) |
| **Reactivity rule (without `@track`)** | The framework only re-renders when a **new value** is assigned to a property, and that new value is **not `===`** to the previous value |
| **Import syntax** | `import { LightningElement, track } from 'lwc';` |
| **Usage syntax** | `@track propertyName = { ... };` placed directly above the property declaration |

---

## ✅ Quick Recap

- `@track` is needed when the framework must observe **changes inside** an object or array (not just full replacements).
- Without `@track`, LWC's reactivity only fires when a property is **reassigned entirely** with a value that's not strictly equal (`===`) to the old one.
- Import `track` from `'lwc'` and place `@track` directly above the object/array property you want to make deeply reactive.
- Common mistake: forgetting `@track` on an object property and then wondering why the UI doesn't update after changing just one of its nested fields.
