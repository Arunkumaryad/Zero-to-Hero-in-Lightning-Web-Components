# Lightning Data Service Wire Adapters and Functions — Introduction

## 1. Overview

This topic introduces the main ways a Lightning Web Component (LWC) works with Salesforce data. The screenshots compare three approaches:

1. **Base Lightning components built on Lightning Data Service (LDS):** easiest for standard record forms, with less control over the UI.
2. **Lightning Data Service wire adapters and functions:** reactive access to Salesforce data and metadata, with more UI customization.
3. **Apex:** useful for complex server-side queries, transactions, and business logic that is not conveniently supported by UI API/LDS.

The screenshots also introduce modules from `lightning/ui*Api`, which are built on Salesforce User Interface API and support many standard objects and custom objects.

## 3. The Three Main Approaches to Working with Salesforce Data

| Approach | Best suited for | Trade-off |
|---|---|---|
| Base Lightning components using LDS | Standard create, edit, and view forms | Fastest to implement; less UI customization |
| LDS wire adapters and functions | Custom UI with reactive standard data access | More code than a ready-made form |
| Apex | Complex queries, transactions, and server-side business logic | Requires Apex code and careful security handling |

The first screenshot lists these reasons for choosing an approach:

1. Use it to get raw record data, picklist values, record information, object information, and similar data.
2. Choose a more customizable approach when creating forms.
3. Use Apex when you need to perform business logic.

In practice, start with base components when they meet the requirement. Use LDS/UI API adapters and functions for a custom interface with standard Salesforce data access. Use Apex when the requirement needs server-side logic or capabilities unavailable through UI API.

## 4. Important `lightning/ui*Api` Modules

### 4.1 `lightning/uiObjectInfoApi`

**Purpose:** Retrieve object metadata and field information, including picklist values.

Common APIs include:

- `getObjectInfo` — obtains metadata for an object, such as its fields and record types.
- `getPicklistValues` — retrieves picklist values for a field and record type.
- `getPicklistValuesByRecordType` — retrieves picklist values for multiple fields for a record type.

**Example: Get Account object metadata**

```javascript
import { LightningElement, wire } from 'lwc';
import { getObjectInfo } from 'lightning/uiObjectInfoApi';
import ACCOUNT_OBJECT from '@salesforce/schema/Account';

export default class AccountObjectInfo extends LightningElement {
    @wire(getObjectInfo, { objectApiName: ACCOUNT_OBJECT })
    objectInfo;
}
```

Here, `@wire` provisions the Account object's metadata to `objectInfo`.

### 4.2 `lightning/uiListApi`

**Purpose in the screenshot:** Get records and metadata for a list view.

The exact APIs available in this module can vary by Salesforce release. Check the current official documentation before building a solution around a particular list-view API.

### 4.3 `lightning/uiRecordApi`

**Purpose:** Read record data, retrieve default values for record creation, and perform supported record operations.

Common APIs include:

- `getRecord` — retrieves record data.
- `getFieldValue` — reads a field value from a record response.
- `getRecordCreateDefaults` — retrieves default values for creating a record.
- `createRecord` — creates a record.
- `updateRecord` — updates a record.
- `deleteRecord` — deletes a record.
- `notifyRecordUpdateAvailable` — informs LDS that records have changed outside its own mechanisms, so affected data can be refreshed.

**Example: Read an Account Name**

```javascript
import { LightningElement, api, wire } from 'lwc';
import { getRecord, getFieldValue } from 'lightning/uiRecordApi';
import ACCOUNT_NAME from '@salesforce/schema/Account.Name';

const FIELDS = [ACCOUNT_NAME];

export default class AccountRecordName extends LightningElement {
    @api recordId;

    @wire(getRecord, { recordId: '$recordId', fields: FIELDS })
    account;

    get accountName() {
        return this.account.data
            ? getFieldValue(this.account.data, ACCOUNT_NAME)
            : '';
    }
}
```

Salesforce can provide `recordId` when the component is used in a supported record context. The `$recordId` reactive reference allows the wire adapter to provision data when the ID becomes available or changes.

## 5. What Is a Wire Adapter?

A **wire adapter** connects an LWC to a Salesforce data source and provisions data reactively. Use the `@wire` decorator with a supported adapter or Apex method.

The wire service can provision a value more than once. Treat the result as read-only and make a copy before changing data for local UI state.

```javascript
@wire(getRecord, {
    recordId: '$recordId',
    fields: FIELDS
})
record;
```

- `getRecord` is the wire adapter.
- `recordId` identifies the record.
- `$recordId` makes the parameter reactive.
- `FIELDS` specifies the fields to retrieve.
- The result includes `data` when successful and `error` when a request fails.

## 6. Wire Adapters vs. JavaScript Functions

| Feature | Wire adapter | JavaScript function |
|---|---|---|
| Typical use | Reactive data provisioning | Explicit action such as create, update, or delete |
| Invocation | Declaratively with `@wire` | Called from JavaScript, often in an event handler |
| Example | `getRecord` | `createRecord`, `updateRecord`, `deleteRecord` |
| Result handling | Handle `data` and `error` | Use the returned Promise with `.then()` / `.catch()` or `async` / `await` |

Some UI API APIs have specific usage requirements. Follow the official documentation for the individual adapter or function.

## 7. LDS/UI API vs. Apex

Prefer LDS/UI API when it meets the requirement because it integrates with Salesforce record access and sharing behavior and can reuse client-side caching.

Use Apex for complex server-side calculations, specialized SOQL, multi-step transactions, or business logic that is not available through UI API.

When using Apex, enforce object-level, field-level, and record-sharing requirements appropriately. Do not assume that Apex automatically enforces every UI API security behavior.

## 8. Benefits of LDS and UI API

- **Caching:** Reuses cached data where applicable and can reduce unnecessary server calls.
- **Reactive updates:** Wired data can update when reactive parameters change.
- **Security:** UI API respects Salesforce record access, sharing, and field-level security for supported operations.
- **Less boilerplate:** Standard record operations often do not require Apex.
- **Customization:** Wire adapters and functions let developers build a custom UI rather than relying only on standard forms.

## 9. When Should You Use Each Approach?

### Use base Lightning components when:
- You need a standard create, view, or edit form.
- Standard field rendering and validation meet the requirement.
- You want to minimize code.

Examples: `lightning-record-form`, `lightning-record-edit-form`, and `lightning-record-view-form`.

### Use LDS wire adapters and functions when:
- You need record data or object metadata inside a custom UI.
- You need picklist values or record type information.
- You need to create, update, or delete records from JavaScript using supported UI API functions.
- You need a custom user experience with standard Salesforce data access.

### Use Apex when:
- You need complex SOQL queries or server-side calculations.
- Multiple related operations must be coordinated.
- UI API/LDS does not support the requirement.
- You need server-side business logic.

## 10. Interview Questions and Short Answers

### Q1. What is Lightning Data Service (LDS)?
LDS is a framework for accessing Salesforce records in Lightning components. It provides caching and integrates with Salesforce record permissions and field-level security for supported operations.

### Q2. What is the difference between LDS and Apex?
LDS/UI API is suitable for standard record data and metadata operations. Apex is used for complex server-side queries, transactions, or business logic that UI API does not cover.

### Q3. What is a wire adapter in LWC?
It is an adapter used with the wire service to provision data reactively to a component.

### Q4. What does `@wire` do?
It connects a component property or function to a wire adapter or supported Apex method and provisions results as data or an error.

### Q5. What does the `$` prefix mean in a wire parameter?
It makes the parameter reactive. When the referenced property changes, the wire service can provision data again.

### Q6. What is `lightning/uiObjectInfoApi` used for?
It provides object metadata and picklist information, including APIs such as `getObjectInfo` and `getPicklistValues`.

### Q7. What is `lightning/uiRecordApi` used for?
It provides APIs for reading records and performing supported record operations, including `getRecord`, `createRecord`, `updateRecord`, and `deleteRecord`.

### Q8. What is `getFieldValue()` used for?
It extracts a field's value from a record response returned by APIs such as `getRecord`.

### Q9. Why use `getPicklistValues` instead of hard-coding picklist options?
It retrieves values configured in Salesforce for the relevant field and record type, helping the component reflect current metadata.

### Q10. Does LDS cache data?
Yes. LDS can cache records and metadata and coordinate updates across components, reducing unnecessary requests.

### Q11. When should you use Apex instead of LDS/UI API?
Use Apex when the required query, transaction, or business logic cannot be handled appropriately by supported UI API/LDS operations.

### Q12. Does UI API respect Salesforce security?
For supported operations, UI API respects the user's record access, sharing, and field-level security. Apex requires developers to handle applicable security requirements explicitly.

### Q13. What is the difference between a wire adapter and an imperative function?
Wire adapters are generally used for reactive data provisioning. Imperative functions are called explicitly, commonly in response to a user action, and often return a Promise.

### Q14. What is `recordId` in an LWC?
It is the Salesforce record identifier. Salesforce can provide it automatically when a component is used in a supported record-page context; it can also be passed into a component in other supported ways.
