# Lightning Data Service (LDS)

## 1. Overview

Lightning Data Service (LDS) is a Salesforce client-side data service that helps Lightning components retrieve, cache, and manage Salesforce record data. It is built on top of the Salesforce User Interface API (UI API).

LDS helps components share cached record data, reduces unnecessary server requests, and applies Salesforce access controls when data is accessed through supported UI API/LDS features.

This README explains the concepts shown in the provided screenshots, how the cache works, key benefits, examples, and common Salesforce interview questions.

## 3. Key Points from the Screenshots

The screenshots highlight these points:

1. **LDS is built on UI API.** It provides a common client-side data layer for supported Lightning components.
2. **UI API provides data and metadata.** UI API responses can include record data and metadata needed by Lightning experiences.
3. **Access controls are respected.** Supported LDS/UI API operations enforce applicable record access, object permissions, field-level security, and sharing.
4. **LDS caches data on the client.** If the requested record is already available in the cache, LDS can return the cached data rather than making another server request.
5. **Cache entries are kept in sync.** LDS manages cache freshness and invalidation when relevant Salesforce data changes. Components that update data outside LDS may need to notify LDS using the appropriate API.
6. **LDS optimizes server calls.** Reusing cached data can reduce unnecessary network requests and improve performance.

> **Important note:** The exact timing and behavior of cache refreshes are managed by Salesforce. Do not assume that every data change in every custom Apex flow automatically refreshes every LDS cache entry. Use the documented refresh or notification APIs when required.

## 4. How LDS Works

### Case A: The record is not in the cache

1. An LWC requests a record through LDS/UI API.
2. LDS checks whether the requested data is already available in its client-side cache.
3. If it is not available or must be refreshed, Salesforce retrieves the data through UI API.
4. LDS provides the result to the component and stores it in the client-side cache as appropriate.
5. Other components can benefit from shared LDS-managed record data.

### Case B: The record is already in the cache

1. An LWC requests a record through LDS/UI API.
2. LDS finds usable data in the client-side cache.
3. The data can be supplied from the cache without an unnecessary server request.
4. This can improve responsiveness and reduce server calls.

### Simplified flow

```text
Lightning Web Component
          |
          v
Lightning Data Service (LDS)
          |
          v
Is usable data in cache?
       /       \
     Yes        No / Refresh needed
      |                |
      v                v
Return cached      Salesforce UI API
data                    |
      |                 v
      |             Salesforce data
      |                 |
      +------< Cache and provide result
```

## 5. Main Benefits of LDS

### 5.1 Client-Side Caching

LDS keeps record data in a client-side cache. When the same supported data is requested again and the cached data is usable, it may be returned without a new server request.

### 5.2 Better Performance

Fewer unnecessary requests and shared data can make Lightning pages more responsive.

### 5.3 Security

LDS/UI API respects applicable Salesforce record access, object permissions, field-level security, and sharing for supported operations. Do not confuse this with Apex: Apex code must be written with appropriate sharing and object/field permission enforcement.

### 5.4 Data Sharing Between Components

Components using LDS can benefit from a common LDS-managed record cache. When record data is updated through supported mechanisms, LDS can coordinate updates to components using that data.

### 5.5 Less Boilerplate Code

For supported operations, developers can use base Lightning components or LDS APIs instead of writing Apex for every data access requirement.

### 5.6 Optimized Server Calls

Cached responses can reduce repeated requests to the server. This does not mean every operation is always served from cache; Salesforce determines cache use and freshness.

## 6. Common LDS Components and APIs

### Base Lightning components

- `lightning-record-form` — displays, creates, or edits a record with minimal code.
- `lightning-record-view-form` — displays record fields.
- `lightning-record-edit-form` — creates or edits a record with more control over the form layout.

### Wire adapters and functions

- `getRecord` — retrieves record data.
- `getFieldValue` — extracts a field value from a `getRecord` response.
- `getObjectInfo` — retrieves object metadata.
- `getPicklistValues` — retrieves picklist values.
- `createRecord()` — creates a record.
- `updateRecord()` — updates a record.
- `deleteRecord()` — deletes a record.

These APIs are commonly imported from `lightning/uiRecordApi` or related `lightning/ui*Api` modules. Confirm API availability and support for your target object and Salesforce API version.

## 7. Example: Retrieve a Record with LDS

This example uses the `getRecord` wire adapter to retrieve an Account's Name.

### `accountDetails.js`

```javascript
import { LightningElement, api, wire } from 'lwc';
import { getRecord, getFieldValue } from 'lightning/uiRecordApi';
import ACCOUNT_NAME from '@salesforce/schema/Account.Name';

export default class AccountDetails extends LightningElement {
    @api recordId;

    @wire(getRecord, {
        recordId: '$recordId',
        fields: [ACCOUNT_NAME]
    })
    account;

    get accountName() {
        return this.account.data
            ? getFieldValue(this.account.data, ACCOUNT_NAME)
            : '';
    }
}
```

### `accountDetails.html`

```html
<template>
    <lightning-card title="Account Details">
        <template lwc:if={account.data}>
            <p class="slds-p-around_medium">
                Account Name: {accountName}
            </p>
        </template>

        <template lwc:if={account.error}>
            <p class="slds-p-around_medium">
                Unable to load the Account record.
            </p>
        </template>
    </lightning-card>
</template>
```

### `accountDetails.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__RecordPage</target>
        <target>lightning__AppPage</target>
    </targets>
</LightningComponentBundle>
```

**How it works:**

- `@api recordId` allows the record page to provide the current record ID.
- `@wire(getRecord, ...)` requests the record reactively.
- `'$recordId'` is a reactive parameter; the wire service provisions data when the value is available or changes.
- `getFieldValue()` extracts the Account Name from the response.
- The template displays the data or an error message.

For a Record Page component, Salesforce supplies `recordId` when the component is placed in a supported record-page context.

## 8. Updating Data and Refreshing LDS

When you update a record with LDS functions such as `updateRecord()`, LDS manages the record data through its supported data layer.

When data is changed through Apex or another mechanism outside LDS, LDS may not automatically know about that change. Depending on the scenario, you may need to use APIs such as:

- `notifyRecordUpdateAvailable()` to tell LDS that specified record IDs have changed outside LDS.
- `refreshApex()` to refresh data provisioned by an Apex wire.

These APIs are not interchangeable: choose the one that matches how the data was obtained and changed. Consult Salesforce documentation for the correct usage in your scenario.

---

## 9. LDS vs. Apex

| Topic | LDS / UI API | Apex |
|---|---|---|
| Main purpose | Standard record and metadata operations | Custom server-side logic and queries |
| Client-side cache | Managed by LDS where applicable | Depends on invocation and caching configuration |
| Security | Applies supported UI API access controls | Developer must implement appropriate sharing and object/field permission enforcement |
| Code required | Often less | Requires Apex classes and tests |
| Best use | Standard record operations and supported metadata | Complex SOQL, multi-object logic, or unsupported UI API scenarios |

**Rule of thumb:** Prefer base Lightning components or LDS for supported record operations. Use Apex when the requirement genuinely needs custom server-side processing or functionality unavailable through LDS/UI API.

## 10. Interview Questions and Answers

### Q1. What is Lightning Data Service?

Lightning Data Service is a client-side data service built on Salesforce UI API. It helps Lightning components access, cache, and manage records through supported APIs.

### Q2. What is LDS built on?

It is built on top of Salesforce User Interface API (UI API).

### Q3. What is the main purpose of LDS caching?

Caching allows usable record data to be reused on the client, reducing unnecessary server calls and improving performance.

### Q4. Does LDS respect field-level security and sharing?

Supported LDS/UI API operations enforce applicable Salesforce access controls, including record access and field/object permissions.

### Q5. What happens when a record is already in the LDS cache?

If the cached data is usable and sufficiently fresh, LDS can provide it without making an unnecessary server request.

### Q6. Does LDS always make a server call?

No. It can use cached data when appropriate. Salesforce manages cache freshness and decides when data must be fetched or refreshed.

### Q7. Name some base Lightning components that use LDS.

`lightning-record-form`, `lightning-record-view-form`, and `lightning-record-edit-form`.

### Q8. What is the `getRecord` wire adapter used for?

It retrieves a record and selected fields through UI API.

### Q9. What is the difference between LDS and Apex?

LDS is intended for supported standard record and metadata operations with Salesforce-managed data behavior. Apex is used for custom server-side logic and more complex data requirements.

### Q10. If Apex updates a record, will LDS always refresh automatically?

Do not assume so. When data changes outside LDS, use the appropriate notification or refresh mechanism where required, such as `notifyRecordUpdateAvailable()` for affected record IDs.

### Q11. What is `notifyRecordUpdateAvailable()` used for?

It notifies LDS that specified record IDs have changed outside LDS so that LDS-managed data can be refreshed as appropriate.

### Q12. What is `refreshApex()` used for?

It refreshes data provisioned by an Apex wire. It is not a general replacement for LDS record notification APIs.

### Q13. Can LDS be used to create or update records?

Yes. Supported operations can be performed with functions such as `createRecord()` and `updateRecord()`, or with base record-form components.

### Q14. Why should you avoid Apex for simple record operations when LDS is sufficient?

LDS often needs less code and provides standard access-control and data-management behavior, which can simplify maintenance.

## 11. Scenario-Based Interview Questions

**Scenario 1: Two LWC components display the same Account. What can LDS help with?**  
Both components can benefit from the LDS-managed record cache and coordinated record data updates.

**Scenario 2: The Account Name is not visible to a user because of field permissions. What should you consider?**  
Check field-level security and the user's access. Supported LDS/UI API operations respect applicable access controls; do not attempt to bypass them.

**Scenario 3: Apex updates an Account, but an LDS-backed component shows old data. What should you investigate?**  
Check whether the change happened outside LDS and whether the component needs a record notification or refresh. Use the API appropriate to the data source.

**Scenario 4: You need a standard form to edit a Contact. Should you write Apex first?**  
No. Start by evaluating `lightning-record-edit-form` or `lightning-record-form`.

**Scenario 5: You need complex processing across several objects. Is LDS always enough?**  
Not necessarily. Evaluate UI API support first, then use Apex if custom server-side logic or complex queries are required.

---

## 12. Common Mistakes

- Assuming all data changes automatically refresh every LDS cache entry.
- Treating `refreshApex()` and `notifyRecordUpdateAvailable()` as interchangeable.
- Using Apex for simple record forms that base Lightning components can handle.
- Assuming Apex automatically enforces field-level security in every query and update.
- Forgetting to handle loading, empty, and error states in a custom component.
- Assuming every Salesforce object and operation is supported by every UI API adapter.

## Summary

Lightning Data Service is a client-side data service built on Salesforce UI API. It provides supported access to Salesforce records, caches data when appropriate, respects applicable access controls, and can reduce unnecessary server requests. Use base Lightning components for standard record forms, LDS wire adapters and functions for custom UI with supported data operations, and Apex when custom server-side logic is needed.
