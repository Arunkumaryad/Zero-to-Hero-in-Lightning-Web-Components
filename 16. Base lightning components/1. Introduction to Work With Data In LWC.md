# Introduction to Working with Data in LWC

## 1. Overview

Lightning Web Components (LWC) can retrieve, display, create, update, and delete Salesforce records in different ways. Choosing the right data-access approach helps reduce boilerplate code, improves maintainability, and makes components more efficient.

The screenshot explains three broad approaches for working with Salesforce data:

1. **Base Lightning components built on Lightning Data Service (LDS)** — easiest to implement, but with less flexibility.
2. **Lightning Data Service wire adapters and functions** — easy to use and more flexible than base components.
3. **Apex** — extremely flexible for custom server-side logic and complex data requirements.

The best approach depends on the use case. Start with the simplest option that meets the requirements, and use Apex when the standard data APIs cannot meet the requirement.

## 3. The Three Main Approaches

### 3.1 Base Lightning Components Built on Lightning Data Service

**Definition:** Base Lightning components such as `lightning-record-form`, `lightning-record-view-form`, and `lightning-record-edit-form` use Lightning Data Service to work with Salesforce records while handling much of the standard UI and data behavior for you.

**Best for:**
- Quickly displaying record fields.
- Creating or editing records using standard Salesforce forms.
- Reducing the amount of JavaScript and Apex code.
- Respecting Salesforce record access, field-level security, and sharing through the standard data APIs.

**Advantages**
- Requires very little code.
- Provides standard Salesforce user-interface behavior.
- Handles common record-form scenarios without writing custom Apex.
- Benefits from LDS caching and record data coordination.

**Limitations**
- Less control over the layout and behavior than a fully custom component.
- Best suited to supported standard record-form use cases.

**Example — display a record**

```html
<template>
    <lightning-record-form
        record-id={recordId}
        object-api-name="Account"
        layout-type="Full"
        mode="view">
    </lightning-record-form>
</template>
```

**Example — create or edit a record**

```html
<template>
    <lightning-record-form
        object-api-name="Account"
        record-id={recordId}
        layout-type="Full"
        mode="edit">
    </lightning-record-form>
</template>
```

For a new record, omit `record-id` and use `mode="edit"`.

### 3.2 Lightning Data Service Wire Adapters and Functions

**Definition:** Lightning Data Service (LDS) provides client-side APIs for working with Salesforce records. LWC wire adapters retrieve data reactively, while LDS functions support record operations such as creating, updating, or deleting records.

**Common wire adapters**
- `getRecord` — retrieves a record and selected fields.
- `getFieldValue` — extracts a field value from a record response.
- `getObjectInfo` — retrieves object metadata.
- `getPicklistValues` — retrieves picklist values for a field.
- `getListUi` — historically used for list data; check current Salesforce documentation for support and preferred alternatives in your API version.

**Common functions**
- `createRecord()` — creates a record.
- `updateRecord()` — updates a record.
- `deleteRecord()` — deletes a record.

**Best for:**
- Reading records and metadata reactively.
- Building a custom UI while using Salesforce's standard record data APIs.
- Creating or updating records without writing Apex when the operation is supported by LDS/UI API.

**Advantages**
- More control over the UI than standard base record-form components.
- No Apex required for supported record operations.
- Works with Salesforce's client-side record data infrastructure.

**Example — retrieve an Account**

```javascript
import { LightningElement, api, wire } from 'lwc';
import { getRecord, getFieldValue } from 'lightning/uiRecordApi';
import ACCOUNT_NAME from '@salesforce/schema/Account.Name';

export default class AccountDetails extends LightningElement {
    @api recordId;

    @wire(getRecord, {
        recordId: '$recordId',
        fields: [ACCOUNT_NAME]
    })
    account;

    get accountName() {
        return this.account.data
            ? getFieldValue(this.account.data, ACCOUNT_NAME)
            : '';
    }
}
```

```html
<template>
    <lightning-card title="Account Details">
        <template lwc:if={account.data}>
            <p>Account Name: {accountName}</p>
        </template>
        <template lwc:if={account.error}>
            <p>An error occurred while loading the Account.</p>
        </template>
    </lightning-card>
</template>
```

**Example — update a record**

```javascript
import { updateRecord } from 'lightning/uiRecordApi';

const fields = {
    Id: this.recordId,
    Name: 'Updated Account Name'
};

updateRecord({ fields })
    .then(() => {
        // Handle successful update.
    })
    .catch((error) => {
        // Handle the error.
        console.error(error);
    });
```

### 3.3 Apex

**Definition:** Apex is Salesforce's server-side programming language. An LWC can call Apex methods to retrieve or modify data and to execute custom business logic that is not conveniently handled by base components or LDS/UI API.

**Best for:**
- Complex queries or business logic.
- Combining data from multiple objects.
- Operations that require custom server-side processing.
- Use cases not supported by LDS/UI API.

**Advantages**
- Highly flexible.
- Supports complex SOQL queries and custom business logic.
- Can coordinate multi-step server-side operations.

**Limitations and responsibilities**
- Requires Apex classes and tests.
- Requires explicit handling of errors and loading states in the UI.
- Apex security must be designed carefully. Use sharing declarations and enforce object/field permissions appropriately.
- Avoid Apex when a simpler LDS solution meets the requirement.

**Example — Apex controller**

```apex
public with sharing class AccountController {
    @AuraEnabled(cacheable=true)
    public static Account getAccount(Id recordId) {
        return [
            SELECT Id, Name
            FROM Account
            WHERE Id = :recordId
            LIMIT 1
        ];
    }
}
```

**Example — call the Apex method from LWC**

```javascript
import { LightningElement, api, wire } from 'lwc';
import getAccount from '@salesforce/apex/AccountController.getAccount';

export default class AccountDetailsApex extends LightningElement {
    @api recordId;

    @wire(getAccount, { recordId: '$recordId' })
    account;
}
```

```html
<template>
    <lightning-card title="Account Details (Apex)">
        <template lwc:if={account.data}>
            <p>Account Name: {account.data.Name}</p>
        </template>
        <template lwc:if={account.error}>
            <p>An error occurred while loading the Account.</p>
        </template>
    </lightning-card>
</template>
```

The example uses `cacheable=true` because it only reads data. A method that changes data must not be marked cacheable.

## 4. Comparison Table

| Feature | Base Lightning Components using LDS | LDS Wire Adapters and Functions | Apex |
|---|---|---|---|
| Amount of code | Lowest | Low to moderate | Moderate to high |
| UI flexibility | Limited to component options | High | High |
| Custom server-side logic | No custom Apex needed for standard forms | Limited to supported UI API operations | Yes |
| Typical use | Standard record forms | Custom UI with standard record APIs | Complex data and business logic |
| Caching | Managed by LDS where applicable | Managed by LDS/UI API where applicable | Depends on how Apex is called and caching is configured |
| Security | Standard data APIs enforce applicable access | Standard data APIs enforce applicable access | Developer must explicitly follow Apex security best practices |
| Recommended starting point | Simple record display/edit/create | Custom UI for supported data operations | Requirements that LDS/UI API cannot satisfy |

## 5. How to Choose the Right Approach

Use this decision guide:

1. **Need a standard Salesforce record form?** Start with `lightning-record-form`, `lightning-record-edit-form`, or `lightning-record-view-form`.
2. **Need a custom UI but only supported record and metadata operations?** Consider LDS wire adapters and functions from `lightning/uiRecordApi`.
3. **Need complex SOQL, multi-object processing, or custom server-side business logic?** Consider Apex.
4. **Before choosing Apex,** confirm that a base component or LDS/UI API cannot satisfy the requirement.

## 6. Key Concepts to Understand

### Lightning Data Service (LDS)

LDS is the Salesforce client-side record data layer used by many Lightning components and UI API features. It helps load and cache records and coordinate record data across components.

### Wire Service

The LWC wire service provisions data reactively. A wired property or function can receive data when it becomes available and when reactive parameters change.

### UI API

The User Interface API provides Salesforce data and metadata capabilities used by Lightning experiences. LWC features such as `lightning/uiRecordApi` use this API.

### Imperative Calls

An imperative call is made explicitly from JavaScript, often in response to a user action. For example, `createRecord()` and `updateRecord()` can be called imperatively. Apex methods can also be called imperatively.

### `@AuraEnabled(cacheable=true)`

This annotation allows an Apex method that only reads data to be used with the LWC wire service and enables client-side caching. Do not use it for methods that create, update, or delete data.

### Security

For LDS/UI API, Salesforce applies the relevant record, object, and field access controls. For Apex, developers should use appropriate sharing declarations and enforce object- and field-level security, for example with user-mode database operations or `Security.stripInaccessible()` where appropriate.

## 7. Interview Questions and Answers

**Q1. What are the main ways to work with Salesforce data in LWC?**  
Base Lightning record components, LDS wire adapters/functions, and Apex.

**Q2. What is Lightning Data Service?**  
It is a client-side service that helps Lightning components access and manage Salesforce records, including caching and coordination of record data.

**Q3. When should you use `lightning-record-form`?**  
When a standard Salesforce record form meets the UI and behavior requirements and you want to minimize custom code.

**Q4. What is the difference between a base record component and an LDS wire adapter?**  
A base record component provides a ready-made UI. A wire adapter provides data that you can use to build a custom UI.

**Q5. What is `getRecord`?**  
It is an LDS wire adapter used to retrieve a record and specified fields through the UI API.

**Q6. What are `createRecord()` and `updateRecord()` used for?**  
They create and update records through the UI API when the operation is supported.

**Q7. When should you use Apex instead of LDS?**  
When you need custom server-side logic, complex queries, multi-object processing, or functionality not supported by LDS/UI API.

**Q8. What does `@AuraEnabled(cacheable=true)` mean?**  
It exposes an Apex method to Lightning code and declares that the method is read-only and eligible for caching. It is commonly used with wired Apex methods.

**Q9. Can a cacheable Apex method update a record?**  
No. A cacheable method must not change data.

**Q10. What is the difference between wired and imperative Apex?**  
Wired Apex is reactive and requires a cacheable read-only method. Imperative Apex is invoked explicitly and is useful when code must control when the call happens or when performing a mutation.

**Q11. Does Apex automatically enforce field-level security?**  
Do not assume that it does. Apex code must follow security best practices, including enforcing object and field permissions and using appropriate sharing or user-mode operations.

**Q12. Why avoid Apex when LDS can solve the problem?**  
LDS/UI API often requires less code and provides standard security and caching behavior, reducing maintenance work.

## 8. Scenario-Based Interview Questions

**Scenario 1: You need to show and edit a few Account fields using a standard form.**  
Start with `lightning-record-form` or `lightning-record-edit-form`.

**Scenario 2: You need to display Account Name in a custom-designed card.**  
Use `getRecord` with `getFieldValue`, then render the value in your own template.

**Scenario 3: You need to create an Account after a button click.**  
Use `createRecord()` if the required operation is supported by UI API. Use Apex if custom server-side processing is required.

**Scenario 4: You need to retrieve data from multiple related objects with complex filtering and business logic.**  
Evaluate whether UI API can meet the requirements; if not, use an Apex method with appropriate security and error handling.

**Scenario 5: A wired Apex method is not refreshing after a change.**  
Review the wire result and use `refreshApex()` when appropriate. For LDS-managed records, use the relevant LDS notification mechanisms when needed.

## 9. Common Mistakes to Avoid

- Writing Apex for simple record forms that a base Lightning component can handle.
- Using Apex without considering record sharing, object permissions, and field-level security.
- Marking an Apex method `cacheable=true` when it changes data.
- Forgetting to handle loading and error states in custom UIs.
- Assuming every data operation is supported by UI API; check the object's and operation's support.
- Assuming all cache behavior is identical between LDS/UI API and Apex.
