# lightning-record-form

## 1. Overview

`lightning-record-form` is a standard Salesforce Lightning Web Component (LWC) base component that lets you create, view, and update a record with minimal code. It uses Lightning Data Service (LDS) to load and save supported record data, so you do not need to write Apex just for common record-form operations.

This README follows the supplied screenshots and explains the definitions, attributes, examples, output modes, and interview topics in simple language.

---

## 2. Definitions from the Screenshots

### `lightning-record-form`

> Use the `lightning-record-form` component to quickly create forms to add, view, or update a record.

The component provides these helpful features:

- Switches between view and edit modes automatically when the user begins editing a field in a view form.
- Provides Cancel and Save buttons automatically in edit forms.
- Uses the object's default record layout with support for multiple columns.
- Loads all fields in the object's compact or full layout, or only the fields you specify.

`lightning-record-form` is less customizable. To customize the form layout or provide custom rendering of record data, use `lightning-record-edit-form` (add or update a record) and `lightning-record-view-form` (view a record).

**Performance note from the screenshot:** Whenever possible, to boost performance, define fields instead of a layout. Specify a layout only when the administrator, not the component, needs to manage the provisioned fields.

### Key Attributes

The screenshots describe these attributes:

- **`object-api-name`** — This attribute is always required. The `lightning-record-form` component requires you to specify the `object-api-name` attribute to establish the relationship between a record and an object.
  - **Note:** Event and Task objects are not supported by `lightning-record-form`.
- **`record-id`** — This attribute is required only when you’re editing or viewing a record.
- **`fields`** — Pass record fields as an array of strings. The fields display in the order you list them.
- **`layout-type`** — Use this attribute to specify a `Full` or `Compact` layout. Layouts are typically defined (created and modified) by administrators.
- **`mode`** — This form supports three modes:
  - **`edit`** — Creates an editable form to add a record or update an existing one. Edit mode is the default when `record-id` is not provided.
  - **`view`** — Displays a record that users can also edit. The record fields each have an edit button. View mode is the default when `record-id` is provided.
  - **`readonly`** — Displays a record without edit controls.
- **`columns`** — Use this attribute to show multiple columns in the form.

**Clarification:** The supported mode value for read-only display is `readonly` (not `read-only`). When `record-id` is supplied, the default mode is `view`; when it is omitted, the default mode is `edit`.

## 3. When to Use `lightning-record-form`

Use it when:

- You need a quick form to create a record.
- You need to show an existing record with minimal code.
- Users should be able to edit a record using Salesforce's standard inline editing experience.
- Admins should control the fields through a page layout.
- You do not need complete control over how each field is rendered.

Choose `lightning-record-edit-form` or `lightning-record-view-form` when you need more control over individual fields and the layout.

---

## 4. How It Works

1. Specify the object with `object-api-name`.
2. For an existing record, pass its Salesforce ID in `record-id`.
3. Choose fields explicitly using `fields`, or use `layout-type` to use the object's page layout.
4. Set `mode` if you want to choose the initial behavior.
5. Salesforce loads and saves the record using LDS.
6. The component handles standard form controls and supported validation behavior.

### `fields` vs. `layout-type`

- **`fields`**: You choose the exact fields and their order. This is often preferable for performance and predictable component behavior.
- **`layout-type`**: Salesforce uses the configured Compact or Full layout. This is useful when administrators need to manage the displayed fields declaratively.

For clarity, the examples below use one approach at a time.

## 5. Example A — Create an Account

This example creates a new Account using a selected list of fields.

### `createAccountForm.html`

```html
<template>
    <lightning-card title="Create Account Using Lightning Record Form">
        <lightning-record-form
            object-api-name={objectApiName}
            fields={fields}
            columns="1"
            mode="edit"
            onsuccess={handleSuccess}
            onerror={handleError}>
        </lightning-record-form>
    </lightning-card>
</template>
```

### `createAccountForm.js`

```javascript
import { LightningElement } from 'lwc';
import { ShowToastEvent } from 'lightning/platformShowToastEvent';

import ACCOUNT_OBJECT from '@salesforce/schema/Account';
import NAME_FIELD from '@salesforce/schema/Account.Name';
import ANNUAL_REVENUE_FIELD from '@salesforce/schema/Account.AnnualRevenue';
import TYPE_FIELD from '@salesforce/schema/Account.Type';
import INDUSTRY_FIELD from '@salesforce/schema/Account.Industry';
import RATING_FIELD from '@salesforce/schema/Account.Rating';

export default class CreateAccountForm extends LightningElement {
    objectApiName = ACCOUNT_OBJECT;

    fields = [
        NAME_FIELD,
        ANNUAL_REVENUE_FIELD,
        TYPE_FIELD,
        INDUSTRY_FIELD,
        RATING_FIELD
    ];

    handleSuccess(event) {
        this.dispatchEvent(
            new ShowToastEvent({
                title: 'Success',
                message: `Account created successfully. Record ID: ${event.detail.id}`,
                variant: 'success'
            })
        );
    }

    handleError() {
        this.dispatchEvent(
            new ShowToastEvent({
                title: 'Error',
                message: 'The Account could not be saved. Review the form errors.',
                variant: 'error'
            })
        );
    }
}
```

### `createAccountForm.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__AppPage</target>
        <target>lightning__HomePage</target>
    </targets>
</LightningComponentBundle>
```

**How it works:**

- `ACCOUNT_OBJECT` identifies the Account object.
- `fields` contains schema references for the fields to display, in the order they should appear.
- Because `record-id` is not provided, the form creates a new Account.
- `mode="edit"` explicitly requests an editable form.
- `onsuccess` runs after Salesforce saves the record.
- `onerror` runs when the form reports a save error.

Account Name (`Name`) is required by default. Other required fields and validation rules depend on your org configuration.

## 6. Example B — Display a Record with Inline Editing

This example displays an existing Account. Place the component on an Account record page so Salesforce supplies `recordId`, or otherwise pass a valid Account ID.

### `displayAccountForm.html`

```html
<template>
    <lightning-card title="Display Record Using Lightning Record Form">
        <lightning-record-form
            record-id={recordId}
            object-api-name={objectApiName}
            fields={fields}
            mode="view"
            columns="1">
        </lightning-record-form>
    </lightning-card>
</template>
```

### `displayAccountForm.js`

```javascript
import { LightningElement, api } from 'lwc';

import ACCOUNT_OBJECT from '@salesforce/schema/Account';
import NAME_FIELD from '@salesforce/schema/Account.Name';
import ANNUAL_REVENUE_FIELD from '@salesforce/schema/Account.AnnualRevenue';
import TYPE_FIELD from '@salesforce/schema/Account.Type';
import INDUSTRY_FIELD from '@salesforce/schema/Account.Industry';
import RATING_FIELD from '@salesforce/schema/Account.Rating';

export default class DisplayAccountForm extends LightningElement {
    @api recordId;
    objectApiName = ACCOUNT_OBJECT;

    fields = [
        NAME_FIELD,
        ANNUAL_REVENUE_FIELD,
        TYPE_FIELD,
        INDUSTRY_FIELD,
        RATING_FIELD
    ];
}
```

### `displayAccountForm.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__RecordPage</target>
        <target>lightning__AppPage</target>
    </targets>
</LightningComponentBundle>
```

**How it works:**

- `@api recordId` allows the Lightning record page to pass the current record ID into the component.
- `mode="view"` displays fields with inline-edit controls where supported.
- Users can edit fields and save or cancel through the standard form UI.

## 7. Example C — Display a Record in Read-Only Mode

Set `mode="readonly"` to display a record without edit controls.

```html
<template>
    <lightning-card title="Display Record in Read Only Mode">
        <lightning-record-form
            record-id={recordId}
            object-api-name="Account"
            fields={fields}
            mode="readonly"
            columns="1">
        </lightning-record-form>
    </lightning-card>
</template>
```

The JavaScript class should expose `recordId` and `fields`, as in Example B.

- `view`: shows record values and supports inline editing.
- `readonly`: shows record values without edit controls.
- `edit`: shows editable fields and standard Save/Cancel actions.

## 8. Example D — Edit a Record with a Compact Layout

This follows the attribute combination shown in the screenshots.

```html
<template>
    <lightning-card title="Edit Account Using Compact Layout">
        <lightning-record-form
            record-id={recordId}
            object-api-name="Account"
            columns="2"
            mode="edit"
            layout-type="Compact">
        </lightning-record-form>
    </lightning-card>
</template>
```

This form uses the Account Compact layout and starts in edit mode. The record ID must refer to an existing Account.

To use a specific set of fields instead of the layout, use the `fields` attribute as shown in Examples A and B.

## 9. Schema Imports Explained

The screenshots show this pattern:

```javascript
import objectName from '@salesforce/schema/objectReference';
import fieldName from '@salesforce/schema/object.fieldReference';
```

A real example:

```javascript
import ACCOUNT_OBJECT from '@salesforce/schema/Account';
import NAME_FIELD from '@salesforce/schema/Account.Name';
```

Schema imports provide references to Salesforce objects and fields. They help identify invalid references and support dependency tracking during deployment. For a static field list, schema references are generally preferred over plain string names.

## 10. Important Attributes at a Glance

| Attribute | Meaning | Example |
|---|---|---|
| `object-api-name` | Required API name/reference of the object | `object-api-name="Account"` |
| `record-id` | Existing record ID; omit when creating | `record-id={recordId}` |
| `fields` | Ordered list of fields to display | `fields={fields}` |
| `layout-type` | Uses a `Full` or `Compact` layout | `layout-type="Compact"` |
| `mode` | Initial behavior: `edit`, `view`, or `readonly` | `mode="edit"` |
| `columns` | Number of columns in the form | `columns="2"` |
| `onsuccess` | Handler after successful save | `onsuccess={handleSuccess}` |
| `onerror` | Handler for a form error | `onerror={handleError}` |

**Object support note:** The screenshots state that Event and Task are not supported by `lightning-record-form`. Consult the current Salesforce component reference for the exact supported-object and platform limitations for your org/API version.

## 11. Best Practices

- Prefer `fields` over `layout-type` when the component can specify the required fields itself; this can reduce unnecessary field loading.
- Use `layout-type` when administrators need to manage the field set through page layouts.
- Use schema imports for object and field references where practical.
- Use `@api recordId` when placing a component on a record page.
- Include success/error handling when users need feedback after saving.
- Confirm the running user has the required object and field permissions.
- Do not hard-code a real record ID into a component intended for multiple records.
- Use `lightning-record-edit-form` or `lightning-record-view-form` when you need greater control over individual field rendering.

## 12. Interview Questions and Answers

### Q1. What is `lightning-record-form`?

It is a Salesforce base component that provides a quick way to create, view, or update a record using Lightning Data Service.

### Q2. What is the purpose of `object-api-name`?

It identifies the Salesforce object associated with the form and is required.

### Q3. When is `record-id` required?

It is required when displaying or editing an existing record. For creating a new record, omit it.

### Q4. What happens when `record-id` is omitted?

The form defaults to `edit` mode and can be used to create a new record.

### Q5. What happens when `record-id` is provided?

The default mode is `view`, which displays the record and allows inline editing where supported.

### Q6. What are the three modes?

- `edit`: create or update a record.
- `view`: display a record with inline editing.
- `readonly`: display a record without editing controls.

### Q7. What is the difference between `fields` and `layout-type`?

`fields` lets the component developer choose exact fields and their order. `layout-type` asks Salesforce to use fields configured in the Full or Compact layout.

### Q8. Why might `fields` be preferred for performance?

It can avoid loading fields that the component does not need. Use a layout when administrator-managed field selection is a requirement.

### Q9. How do you display two columns?

Set `columns="2"`.

### Q10. How can you show a toast after saving?

Handle the `onsuccess` event and dispatch a `ShowToastEvent`.

### Q11. Does `lightning-record-form` require Apex?

No. Standard supported record operations are handled through Lightning Data Service.

### Q12. What if the user does not have access to a field?

Salesforce security is respected. Check object permissions, field-level security, record access, and page configuration when troubleshooting.

### Q13. When should you use `lightning-record-edit-form` instead?

Use it when you need a custom editable layout, explicit field placement, or more control over form events and rendering.

### Q14. When should you use `lightning-record-view-form` instead?

Use it when you need a custom read-only field layout with control over which fields are displayed and how they are arranged.

### Q15. Why use schema imports?

They provide references to Salesforce objects and fields, help detect invalid references, and improve dependency tracking.

## 13. Scenario-Based Interview Questions

**Scenario 1: You need a form to create Accounts with only Name, Industry, and Rating.**  
Use `lightning-record-form` without `record-id`, and pass those field references through `fields`.

**Scenario 2: You need to show an Account record and allow inline editing.**  
Pass `record-id`, set `object-api-name="Account"`, and use `mode="view"`.

**Scenario 3: You need a record display that users cannot edit.**  
Use `mode="readonly"`.

**Scenario 4: An admin must control which fields appear without changing component code.**  
Use `layout-type="Full"` or `layout-type="Compact"` as appropriate.

**Scenario 5: The form should show a success message after saving.**  
Use `onsuccess` and dispatch a success toast.

---

## 14. Common Mistakes

- Omitting the required `object-api-name`.
- Passing an existing record ID when the intention is to create a new record.
- Using `read-only` instead of the supported mode value `readonly`.
- Expecting full custom field-by-field rendering from `lightning-record-form`.
- Hard-coding a record ID that differs between sandbox and production.
- Choosing a layout when only a small, fixed set of fields is required.
- Forgetting that required fields and validation rules can vary by org.

---


## Summary

`lightning-record-form` is the quickest standard way to create, view, or update Salesforce records in LWC. It provides standard Save/Cancel controls and inline editing behavior, and uses Lightning Data Service for supported record operations. Choose explicit fields when the component should control the displayed fields; choose a layout when administrators should manage them.
