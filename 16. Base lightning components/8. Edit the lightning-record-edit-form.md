# Edit the lightning-record-edit-form

## 1. Overview

This project demonstrates how to edit an existing Salesforce Contact record with the Lightning Web Component (LWC) base component `lightning-record-edit-form`.

The form uses Salesforce schema references for the Contact object and its fields. It displays Account, Name, Title, Phone, and Email fields. The record is selected by the `record-id` attribute.

## 2. Definition

**`lightning-record-edit-form`** is a Lightning Web Component base component that provides a form for creating or updating a Salesforce record. It uses Lightning Data Service and supports Salesforce field metadata, validation, and record permissions.

In this example, the form edits an existing Contact because the markup includes a `record-id`. The **Cancel** button calls a JavaScript handler that resets the input fields to their initial values. The **Save** button submits the form.

### `editRecordEditForm.js`

This is the JavaScript logic shown in the screenshot, with the same imports, object reference, field mappings, and reset handler:

```javascript
import { LightningElement } from 'lwc';
import CONTACT_OBJECT from '@salesforce/schema/Contact';
import NAME_FIELD from '@salesforce/schema/Contact.Name';
import TITLE_FIELD from '@salesforce/schema/Contact.Title';
import PHONE_FIELD from '@salesforce/schema/Contact.Phone';
import EMAIL_FIELD from '@salesforce/schema/Contact.Email';
import ACCOUNT_FIELD from '@salesforce/schema/Contact.AccountId';

export default class RecordEditFormDemo extends LightningElement {
    objectName = CONTACT_OBJECT;

    fields = {
        accountField: ACCOUNT_FIELD,
        nameField: NAME_FIELD,
        titleField: TITLE_FIELD,
        phoneField: PHONE_FIELD,
        emailField: EMAIL_FIELD
    };

    handleReset() {
        const inputField = this.template.querySelectorAll('lightning-input-field');

        if (inputField) {
            Array.from(inputField).forEach(field => {
                field.reset();
            });
        }
    }
}
```

## 5. How the Code Works

### Schema imports

```javascript
import CONTACT_OBJECT from '@salesforce/schema/Contact';
import NAME_FIELD from '@salesforce/schema/Contact.Name';
import ACCOUNT_FIELD from '@salesforce/schema/Contact.AccountId';
```

These imports reference Salesforce object and field definitions. They help Salesforce validate references at build time and keep the code tied to the schema.

### `object-api-name`

```html
object-api-name={objectName}
```

This tells the form which Salesforce object it works with. Here, `objectName` refers to the Contact object.

### `record-id`

```html
record-id="003bm000025TtYHAA0"
```

This identifies the existing Contact to edit. For reusable components, it is usually better to pass the record ID dynamically (for example, through `@api recordId`) instead of hard-coding an ID.

### `lightning-input-field`

Each `lightning-input-field` renders a Salesforce field with its metadata-driven input, label, and validation behavior.

### `lightning-messages`

This component displays errors returned by the record form, such as validation-rule errors or missing required fields.

### Reset handler

```javascript
handleReset() {
    const inputField = this.template.querySelectorAll('lightning-input-field');

    if (inputField) {
        Array.from(inputField).forEach(field => {
            field.reset();
        });
    }
}
```

- `querySelectorAll()` finds the input fields in this component's template.
- `Array.from()` converts the collection to an array.
- `forEach()` loops through each field.
- `reset()` restores the field to its initial value.

`querySelectorAll()` returns a collection even when no matches are found, so `if (inputField)` is not strictly needed. A more concise version is:

```javascript
handleReset() {
    this.template
        .querySelectorAll('lightning-input-field')
        .forEach(field => field.reset());
}
```

## 6. Make the Record ID Reusable (Recommended)

The screenshot hard-codes a record ID. In a reusable component, expose the record ID using `@api` and bind it in the template.

Add `api` to the LWC import and add `@api recordId;` to the class:

```javascript
import { LightningElement, api } from 'lwc';

export default class RecordEditFormDemo extends LightningElement {
    @api recordId;
    // Keep the objectName, fields, and handleReset members from the example.
}
```

Then change the form markup to:

```html
<lightning-record-edit-form
    object-api-name={objectName}
    record-id={recordId}>
```

This lets Salesforce provide the current record ID when the component is placed on a supported record page. Do not keep both a hard-coded ID and the dynamic binding.

## 7. Setup and Testing

1. Open your Salesforce DX project in VS Code.
2. Generate the component:

   ```bash
   sf lightning generate component --name editRecordEditForm --type lwc --output-dir force-app/main/default/lwc
   ```

3. Put the HTML, JavaScript, and metadata XML in the generated bundle.
4. Replace the example record ID with a valid Contact ID, or use the recommended `@api recordId` approach.
5. Deploy the component:

   ```bash
   sf project deploy start --source-dir force-app/main/default/lwc/editRecordEditForm
   ```

6. In Salesforce, open **Setup → Lightning App Builder**.
7. Add the component to a Lightning App Page or, if using the dynamic `@api recordId` version, a Contact Record Page.
8. Save and activate the page.
9. Change a field and click **Cancel**. Confirm it returns to the initial value.
10. Change a field and click **Save**. Confirm the Contact record is updated.

The running user needs appropriate Contact object and field permissions. The record ID must exist in the same org where the component runs.

## 8. Important Notes

- A form with `record-id` edits the specified existing record. Without `record-id`, `lightning-record-edit-form` is used to create a new record.
- The Cancel button in this example only resets the current field inputs. It does not undo a save that has already completed.
- `reset()` returns each input to its initial value; it does not necessarily make every field blank.
- The screenshot's `if (inputField)` check is harmless but not needed because `querySelectorAll()` returns a collection.
- Use `lightning-record-edit-form` for standard record operations without writing Apex for the data save.
- Avoid hard-coded record IDs in production code.

## 9. Troubleshooting

### The form does not load the record
- Verify the Contact ID belongs to the current org.
- Confirm the ID belongs to a Contact record.
- Confirm the running user has access to the record and the fields.
- If using `@api recordId`, ensure the component is placed on a supported record page or that a parent supplies the ID.

### Save does not work
- Check required fields such as Contact Last Name.
- Check `lightning-messages` for validation or server errors.
- Check object permissions, field-level security, validation rules, duplicate rules, and automation.
- Ensure the Save button has `type="submit"`.

### Cancel does not reset values
- Ensure `onclick={handleReset}` matches the method name.
- Ensure the selector targets `lightning-input-field`.
- Remember reset returns values to their initial state, not necessarily blank.

## 10. Interview Questions and Answers

### Q1. What is `lightning-record-edit-form`?
A Salesforce LWC base component used to create or update records using a form that respects Salesforce field metadata and validation.

### Q2. How does it know which record to edit?
The `record-id` attribute identifies the record. Without it, the form is configured to create a new record.

### Q3. Why import fields from `@salesforce/schema`?
Schema imports provide references to Salesforce objects and fields, help catch invalid references, and support rename-safe references.

### Q4. What is the purpose of `lightning-input-field`?
It renders a field input based on Salesforce metadata, including its label and supported validation behavior.

### Q5. What is the purpose of `lightning-messages`?
It displays form validation and server-side error messages.

### Q6. How does the Cancel button work here?
It selects every `lightning-input-field` in the component and calls `reset()` on each one.

### Q7. Does `reset()` undo saved changes?
No. It resets the current inputs to their initial values. It does not roll back a completed server-side save.

### Q8. What does `@api recordId` do?
It exposes the record ID property so Salesforce or a parent component can provide the ID to the LWC.

### Q9. Does this example need Apex?
No. Standard create and update operations can be handled by `lightning-record-edit-form` and Lightning Data Service.

### Q10. What is the difference between create and edit mode?
Create mode omits `record-id`; edit mode supplies a valid `record-id`.

### Q11. Why should record IDs not be hard-coded?
IDs differ between orgs and environments, making components brittle during deployment and reuse.

### Q12. What can cause an update to fail?
Missing required values, validation rules, insufficient permissions, invalid data, duplicate rules, or errors from Salesforce automation.
