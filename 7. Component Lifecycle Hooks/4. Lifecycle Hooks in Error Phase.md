# Lifecycle Hooks in Error Phase

## 📌 Overview

In Lightning Web Components (LWC), the framework provides lifecycle hooks that allow developers to execute code at specific stages of a component's lifecycle.

The main LWC lifecycle hooks are:

* `constructor()`
* `connectedCallback()`
* `renderedCallback()`
* `disconnectedCallback()`
* `errorCallback()`

This topic focuses specifically on **`errorCallback()`**, which is used to handle errors thrown by **descendant/child components**.

Salesforce documentation describes `errorCallback()` as a lifecycle hook that can be used to create an **error boundary component** for catching errors from components lower in the component tree.

---

# 🔴 errorCallback(err, stack)

## Definition

> **This method called when a descendant component throws an error in one of its callback.**

The `errorCallback()` lifecycle hook is used when an error occurs in a descendant component.

A parent component can implement `errorCallback()` to catch errors thrown by its child or descendant components.

### Syntax

```javascript
errorCallback(error, stack) {
    // Handle error
}
```

---

# 📌 Points to Remember

The following are the important points from the video/screenshot:

### 1. When is this method called?

> **This method called when a descendant component throws an error in one of its callback.**

In simple words:

If a child component throws an error inside one of its lifecycle callbacks or a declaratively registered event handler, the error can propagate to its parent error boundary.

---

### 2. What is the `error` argument?

> **The error argument is a JavaScript native error object, and the stack argument is a string.**

Therefore:

```javascript
error
```

contains the actual JavaScript error object.

For example:

```javascript
console.log(error.message);
```

can be used to get the error message.

And:

```javascript
console.log(stack);
```

can be used to inspect the stack trace.

---

### 3. Is `errorCallback()` part of standard HTML Custom Elements?

> **This callback method is specific to Lightning Web Components, it isn’t from the HTML custom elements specification.**

This is an important interview point.

`errorCallback()` is an **LWC-specific lifecycle hook**.

It is not a standard lifecycle callback provided by the HTML Custom Elements specification.

---

# 🧠 What is an Error Boundary?

An **error boundary** is a component that catches errors from descendant components.

For example:

```text
Parent Component
│
├── Child Component
│   └── Error occurs ❌
│
└── errorCallback()
       ↓
   Error handled
```

The parent can act as an error boundary for its child components.

This allows the application to:

* Catch errors
* Log errors
* Display a fallback UI
* Prevent the entire application from failing
* Provide a better user experience

---

# 🔄 Error Propagation in LWC

Suppose we have:

```text
Parent
   |
   └── Child
```

The child throws an error:

```javascript
throw new Error('Loading of child component failed');
```

The error can propagate upward:

```text
Child
  ↓
Error occurs
  ↓
Parent errorCallback()
  ↓
Error handled
```

The parent can then inspect:

```javascript
error.message
```

and:

```javascript
stack
```

# 👶 Child Component Example

The following example demonstrates a child component throwing an error inside `connectedCallback()`.

## lifeCycleChild.js

```javascript
import { LightningElement } from 'lwc';

export default class LifeCycleChild extends LightningElement {

    constructor() {
        super();

        console.log('Child Constructor Called');
    }

    connectedCallback() {

        console.log('Child ConnectedCallback Called');

        throw new Error('Loading of child component failed');
    }

    renderedCallback() {

        console.log('Child renderedCallback Called');
    }

    disconnectedCallback() {

        alert('Child DisconnectedCallback Called.');
    }
}
```

---

# 🔍 Understanding the Child Code

The child component contains several lifecycle hooks.

### Constructor

```javascript
constructor() {
    super();

    console.log('Child Constructor Called');
}
```

The constructor is called when the component instance is created.

`super()` must be called before using `this`.

---

### connectedCallback()

```javascript
connectedCallback() {

    console.log('Child ConnectedCallback Called');

    throw new Error('Loading of child component failed');
}
```

Here we intentionally throw an error:

```javascript
throw new Error('Loading of child component failed');
```

This error is generated by the child component.

Because the child throws the error, the parent error boundary can handle it using:

```javascript
errorCallback(error, stack)
```

---

### renderedCallback()

```javascript
renderedCallback() {
    console.log('Child renderedCallback Called');
}
```

This hook executes after the component has completed rendering.

However, because the example intentionally throws an error during `connectedCallback()`, the normal lifecycle execution can be interrupted.

---

### disconnectedCallback()

```javascript
disconnectedCallback() {
    alert('Child DisconnectedCallback Called.');
}
```

This hook executes when the component is removed from the DOM.

# 👨‍👦 Parent Component Example

The parent component contains:

```javascript
errorCallback(error, stack) {
    console.log(error.message);
    console.log(stack);
}
```

Complete example:

## lifeCycleParent.js

```javascript
import { LightningElement } from 'lwc';

export default class LifeCycleParent extends LightningElement {

    isChildVisible = false;

    constructor() {
        super();

        console.log('Parent Constructor Called');
    }

    connectedCallback() {
        console.log('Parent ConnectedCallback Called');
    }

    renderedCallback() {
        console.log('Parent renderedCallback Called');
    }

    handleclick(event) {
        this.isChildVisible = !this.isChildVisible;
    }

    errorCallback(error, stack) {
        console.log(error.message);
        console.log(stack);
    }
}
```

---

The important method is:

```javascript
errorCallback(error, stack) {

    console.log(error.message);

    console.log(stack);
}
```

There are two parameters:

```text
error
  ↓
JavaScript Error object

stack
  ↓
Stack trace string
```

For example:

```javascript
console.log(error.message);
```

may produce:

```text
Loading of child component failed
```

And:

```javascript
console.log(stack);
```

prints the stack trace.

```javascript
errorCallback(error, stack)
```

# ⚠️ Important Behavior of errorCallback()

`errorCallback()` is designed to catch errors from **descendant components**, not errors thrown by the component itself.

For example:

```text
Parent
│
├── Child A
│
└── Child B
```

If Child A throws an error:

```text
Child A
   ↓
Error
   ↓
Parent.errorCallback()
```

The parent can catch it.

But the parent should not be considered an error boundary for its own errors.

---

# 📌 What Can errorCallback() Catch?

`errorCallback()` can catch errors from descendant components that occur in:

### Lifecycle hooks

For example:

```javascript
connectedCallback()
```

```javascript
renderedCallback()
```

and other lifecycle processing.

### Declaratively registered event handlers

For example:

```html
<lightning-button
    onclick={handleClick}>
</lightning-button>
```

If the handler throws an error:

```javascript
handleClick() {
    throw new Error('Something went wrong');
}
```

the error can propagate to the ancestor error boundary.

---

# ❌ What errorCallback() Does Not Catch

`errorCallback()` does not catch every possible JavaScript error.

For example, errors from programmatically assigned event handlers are not handled in the same way by the LWC error boundary mechanism.

Also, asynchronous errors such as errors from:

* Promises
* `async/await`
* Wire operations

should generally be handled using appropriate error-handling mechanisms such as:

```javascript
try {
    // code
} catch (error) {
    // handle error
}
```

or:

```javascript
promise()
    .then(result => {
        // success
    })
    .catch(error => {
        // error
    });
```

# 🛡️ Error Boundary Pattern

A common architecture is:

```text
Error Boundary Component
          │
          └── Functional Component
                    │
                    ├── Child Component
                    ├── Child Component
                    └── Child Component
```

The error boundary component implements:

```javascript
errorCallback(error, stack) {
    // Handle descendant errors
}
```

This creates a reusable mechanism for handling errors.

# 🖥️ Displaying a User-Friendly Error

Instead of only logging:

```javascript
console.log(error.message);
```

a real application can store the error:

```javascript
errorMessage;
```

and then:

```javascript
errorCallback(error, stack) {

    this.errorMessage = error.message;

    console.error(error);
    console.error(stack);
}
```

The HTML can display a fallback message:

```html
<template>

    <template lwc:if={errorMessage}>

        <div class="slds-notify slds-notify_alert slds-theme_error">
            Something went wrong. Please try again.
        </div>

    </template>

    <template lwc:else>

        <c-life-cycle-child></c-life-cycle-child>

    </template>

</template>
```

This provides a better user experience than exposing raw JavaScript errors.

# 🔁 Lifecycle Hooks vs Error Lifecycle

| Lifecycle Hook           | Purpose                                      |
| ------------------------ | -------------------------------------------- |
| `constructor()`          | Initializes the component instance           |
| `connectedCallback()`    | Runs when component is inserted into the DOM |
| `renderedCallback()`     | Runs after rendering                         |
| `disconnectedCallback()` | Runs when component is removed from the DOM  |
| `errorCallback()`        | Handles errors from descendant components    |

---

# 🧠 Important Lifecycle Flow

A simplified lifecycle flow is:

```text
constructor()
      ↓
connectedCallback()
      ↓
render()
      ↓
renderedCallback()
```

If an error occurs in a descendant component:

```text
Descendant Error
      ↓
Error Propagation
      ↓
Parent errorCallback(error, stack)
```

---

# ⚡ errorCallback() vs try...catch

These two mechanisms solve different problems.

## try...catch

Use `try...catch` when you know exactly where an operation can fail.

Example:

```javascript
handleClick() {

    try {

        throw new Error('Something went wrong');

    } catch (error) {

        console.error(error);
    }
}
```

---

## errorCallback()

Use `errorCallback()` when you want an ancestor component to act as an **error boundary** for descendant components.

Example:

```javascript
errorCallback(error, stack) {

    console.error(error.message);
    console.error(stack);
}
```

### Easy way to remember

```text
try...catch
     ↓
Handle error locally

errorCallback()
     ↓
Handle descendant component errors
```

# 🎯 Interview Questions

## 1. What is errorCallback() in LWC?

### Answer

`errorCallback()` is an LWC-specific lifecycle hook used by an ancestor component to catch errors thrown by descendant components.

It receives two parameters:

```javascript
errorCallback(error, stack)
```

where `error` is a JavaScript Error object and `stack` is a string containing the stack trace.

---

## 2. Is errorCallback() a standard Web Component lifecycle hook?

### Answer

No.

`errorCallback()` is specific to Lightning Web Components.

It is not part of the standard HTML Custom Elements lifecycle specification.

---

## 3. What are the parameters of errorCallback()?

### Answer

There are two parameters:

```javascript
errorCallback(error, stack)
```

`error` is the JavaScript native Error object.

`stack` is the stack trace string.

---

## 4. Can errorCallback() catch errors from the same component?

### Answer

No.

`errorCallback()` is designed to catch errors from **descendant components**.

A component should not rely on its own `errorCallback()` to catch errors thrown by itself.

---

## 5. What is an error boundary?

### Answer

An error boundary is a component that uses `errorCallback()` to catch errors from descendant components and provide appropriate error handling or fallback UI.

---

## 6. Can errorCallback() catch errors from child lifecycle hooks?

### Answer

Yes.

For example, if a child throws an error in:

```javascript
connectedCallback()
```

the error can propagate to the parent error boundary.

---

## 7. Can errorCallback() catch errors from event handlers?

### Answer

It can catch errors from event handlers that are declared in the component's template.

Example:

```html
<lightning-button
    onclick={handleClick}>
</lightning-button>
```

If the handler throws an error, it can propagate to an ancestor error boundary.

---

## 8. Does errorCallback() catch asynchronous errors?

### Answer

Not all asynchronous errors are handled by `errorCallback()`.

Errors from asynchronous operations such as:

```javascript
Promise
```

and:

```javascript
async/await
```

should generally be handled using:

```javascript
.catch()
```

or:

```javascript
try...catch
```

as appropriate.

---

## 9. What happens after an error is caught?

### Answer

The framework handles the failed descendant component as part of the error boundary process, and the child component that caused the error can be unmounted from the DOM.

The parent error boundary can then display fallback content or log the error.

---

## 10. What is the difference between error and stack?

### Answer

`error` contains the JavaScript Error object.

Example:

```javascript
error.message
```

returns the error message.

`stack` contains the stack trace.

Example:

```javascript
console.log(stack);
```

prints the stack information.

---

## 11. What is the difference between try...catch and errorCallback()?

### Answer

`try...catch` is normally used to handle an error locally where the code is executed.

`errorCallback()` is used as an LWC error boundary to handle errors originating from descendant components.

---

## 12. Why is errorCallback() useful in real projects?

### Answer

It allows developers to create centralized error handling for component trees.

It can be used to:

* Log errors
* Display fallback UI
* Improve user experience
* Debug component failures
* Prevent a child component failure from making the entire UI unusable
