# Lifecycle Hooks in Mounting Phase (LWC)

The **Mounting Phase** is the stage where a Lightning Web Component is being **created and inserted into the DOM**. During this phase, three lifecycle hooks fire in a specific order:

1. `constructor()`
2. `connectedCallback()`
3. `renderedCallback()`

*(Note: `render()` also exists in this phase but is an advanced/optional hook used mainly for switching between multiple templates — covered separately.)*

---

## 🔄 Parent-Child Component Creation & Render Lifecycle

When you have a **parent component** containing a **child component**, the hooks don't fire randomly — they follow a well-defined flow:

**Flow for a single component:**
```
Component lifecycle Start
      ↓
  Constructor
      ↓
Public property to update? ──Yes──▶ update public property value ──┐
      │No                                                           │
      ▼                                                             │
component inserted into DOM ◀───────────────────────────────────────┘
      ↓
connectedCallback called
      ↓
component rendered
      ↓
Any child component? ──Yes──▶ (repeat entire cycle for child)
      │No
      ▼
renderedCallback called
      ↓
Component lifecycle End
```

**Key takeaway for Parent → Child relationship:**
- `constructor()` and `connectedCallback()` flow **top-down**, i.e., **Parent → Child**. The parent's constructor and connectedCallback always run *before* the child's.
- `renderedCallback()` flows **bottom-up**, i.e., **Child → Parent**. The child finishes rendering first, then the parent's `renderedCallback()` fires.
- If a child has its own child, the same cycle repeats recursively until every component in the tree has completed its lifecycle.

**Overall order for Parent (P) and Child (C):**
```
P.constructor() → P.connectedCallback() → C.constructor() → C.connectedCallback() → C.renderedCallback() → P.renderedCallback()
```

## 1️⃣ constructor()

> Invoked when a component instance is created.

### Points to Remember
- This hook is invoked when a component instance is created.
- You have to call `super()` first inside this.
- At this point, the component properties won't be ready yet.
- To access the host element, use `this.template`.
- This method's lifecycle flows from Parent to Child component.
- We can't access child elements in the component body because they don't exist yet.
- Don't add attributes to the host element in the constructor.

### Why call `super()`?
Since an LWC class extends `LightningElement`, JavaScript requires that the parent class constructor (`super()`) be called before you can use `this` inside your own constructor — this is standard ES6 class inheritance behavior, not something specific to Salesforce.

### Example

**parent.html**
```html
<template>
    <lightning-card title="Life Cycle Hook Parent Card">
        <div class="slds-m-around_medium">

        </div>
    </lightning-card>
</template>
```

**parent.js**
```javascript
import { LightningElement } from 'lwc';

export default class LifeCycleParent extends LightningElement {
    constructor() {
        super();
        console.log('Parent Constructor Called');
    }
}
```

---

## 2️⃣ connectedCallback()

> Called when the element is inserted into a document.

### Points to Remember
- Called when the element is inserted into a document.
- This hook flows from parent to child.
- You can't access child elements in the component body because they don't exist yet.
- You can access the host element with `this.template`.
- **Use it to:** perform initialization tasks, such as fetch data, set up caches, or listen for events (such as publish-subscribe events).
- **Do not use** `connectedCallback()` to change the state of a component, such as loading values or setting properties. Use getters and setters instead.

### Example

**parent.js**
```javascript
import { LightningElement } from 'lwc';

export default class LifeCycleParent extends LightningElement {
    constructor() {
        super();
        console.log('Parent Constructor Called');
    }
    connectedCallback() {
        console.log('Parent ConnectedCallback Called');
    }
}
```

---

## 3️⃣ renderedCallback()

> Fires when a component's rendering is done.

### Points to Remember
- Fires when a component rendering is done.
- It can fire more than once.
- This hook flows from child to parent.
- When a component re-renders, all the expressions used in the template are reevaluated.

### Do NOT use `renderedCallback()`:
1. To change the state or update property of a component.
2. Don't update a wire adapter configuration object property in `renderedCallback()`, as it can result in an infinite loop.

## 🧩 Complete Working Example — Parent & Child Component

This example demonstrates the actual execution order of all three hooks across a parent-child relationship, along with a simple two-way data flow (input → property → passed to child).

### Parent Component (`lifeCycleParent`)

**lifeCycleParent.html**
```html
<template>
    <lightning-card title="Life Cycle Hook Parent Card">
        <div class="slds-m-around_medium">
            <input type="text" onkeyup={handleNameChange}>
            {name}
            <c-life-cycle-child></c-life-cycle-child>
        </div>
    </lightning-card>
</template>
```

**lifeCycleParent.js**
```javascript
import { LightningElement } from 'lwc';

export default class LifeCycleParent extends LightningElement {
    name;
    constructor() {
        super();
        console.log('Parent Constructor Called');
    }
    connectedCallback() {
        console.log('Parent ConnectedCallback Called');
    }
    renderedCallback() {
        console.log('Parent renderedCallback Called');
    }
    handleNameChange(event) {
        this.name = event.target.value;
    }
}
```

### Child Component (`lifeCycleChild`)

**lifeCycleChild.html**
```html
<template>
    <lightning-card title="Life Cycle Hook child Card">
        <div class="slds-m-around_medium">

        </div>
    </lightning-card>
</template>
```

**lifeCycleChild.js**
```javascript
import { LightningElement } from 'lwc';

export default class LifeCycleChild extends LightningElement {
    constructor() {
        super();
        console.log('Child Constructor Called');
    }
    connectedCallback() {
        console.log('Child ConnectedCallback Called');
    }
    renderedCallback() {
        console.log('Child renderedCallback Called');
    }
}
```

### 🖥️ Console Output on Initial Load

When this component is added to a page, opening the browser console shows the hooks firing in this exact order:

```
Parent Constructor Called
Parent ConnectedCallback Called
Child Constructor Called
Child ConnectedCallback Called
Child renderedCallback Called
Parent renderedCallback Called
```

This confirms:
- `constructor()` and `connectedCallback()` → **Parent first, then Child** (top-down)
- `renderedCallback()` → **Child first, then Parent** (bottom-up)

### ⌨️ What happens when you type in the input box?
Every time you type a character, `handleNameChange()` updates the reactive property `name`. Since `name` is used in the template (`{name}`), the component **re-renders**, and only `renderedCallback()` fires again (not `constructor()` or `connectedCallback()`, since the component isn't being re-created or re-inserted) — proving the earlier point that `renderedCallback()` can fire multiple times.

---

## 📚 Quick Recap

| Hook | Direction | Can Fire Multiple Times? | Typical Use |
|---|---|---|---|
| `constructor()` | Parent → Child | No | Initialize class fields |
| `connectedCallback()` | Parent → Child | Yes (if re-inserted) | Fetch data, subscribe to events |
| `renderedCallback()` | Child → Parent | Yes (on every re-render) | DOM interaction after render |

## 🎯 Interview Questions on Lifecycle Hooks – Mounting Phase

1. **In what order are `constructor()`, `connectedCallback()`, and `renderedCallback()` called for a parent-child component structure?**
   - Parent constructor → Parent connectedCallback → Child constructor → Child connectedCallback → Child renderedCallback → Parent renderedCallback.

2. **Why do we need to call `super()` in the constructor?**
   - Because LWC classes extend `LightningElement`; per JavaScript ES6 class rules, the base class constructor must be called before `this` can be used.

3. **Can you access child elements inside `constructor()` or `connectedCallback()`?**
   - No. In both hooks, child elements don't exist yet in the DOM, so they can't be accessed.

4. **Why shouldn't you set component state/properties inside `connectedCallback()`?**
   - Because it can lead to unpredictable behavior; getters/setters are the recommended way to react to and manage property changes.

5. **Can `renderedCallback()` be called more than once? Why?**
   - Yes. It fires every time the component finishes re-rendering — for example, whenever a reactive/tracked property changes and the template re-evaluates its expressions.

6. **Why is updating a property inside `renderedCallback()` considered risky?**
   - Because changing a property can trigger another render, which calls `renderedCallback()` again — potentially causing an **infinite loop**, especially if it's a wire adapter's configuration property.

7. **Does `connectedCallback()` flow from parent to child or child to parent?**
   - Parent to child — the parent always connects to the DOM before its children.

8. **Does `renderedCallback()` flow from parent to child or child to parent?**
   - Child to parent — children finish rendering first, and then the parent's `renderedCallback()` fires, since the parent's render isn't "complete" until all its children are rendered.

9. **What is the correct way to access the host element in `constructor()` or `connectedCallback()`?**
   - Using `this.template`.

10. **Where should you avoid adding attributes to the host element?**
    - Inside the `constructor()` — attributes shouldn't be added to the host element at that stage.

11. **What happens if a parent component has multiple nested child components — how does the lifecycle behave?**
    - The same mounting cycle (constructor → connectedCallback → render → renderedCallback) repeats recursively for every nested child, following the same top-down/bottom-up pattern, until the entire component tree has mounted.
