# Introduction to Apex in Lightning Web Components (LWC)

## 1. Overview

This folder introduces **how and when to use Apex in Lightning Web Components (LWC)**. The screenshots explain where Apex fits among the available ways to access Salesforce data and show the two ways to call Apex methods from an LWC:

1. **Wire Apex methods**
2. **Call Apex methods imperatively**

The main idea is to use the simplest suitable Salesforce data-access option first. Use Apex when the standard Lightning components and Lightning Data Service (LDS) UI API do not meet the requirement.

---

## 2. Apex in LWC — Definition From the Screenshot

The screenshot presents three approaches for working with Salesforce data:

- **Base Lightning components built on Lightning Data Service** — easiest to implement, but with less flexibility.
- **Lightning Data Service wire adapters and functions** — easy to use and more flexible than base components.
- **Apex** — extremely flexible.

The screenshot's key guidance is:

> If you can’t use a base component, and you can’t use the Lightning Data Service wire adapters or functions, use Apex.

### Explanation in simple words

When building an LWC, first check whether a standard Lightning base component can complete the task. If not, check whether a Lightning Data Service (LDS) adapter or function can do it. If those options cannot satisfy the requirement, use Apex to implement the required server-side logic.

Apex gives developers more control over queries, business logic, and operations, but it also means that developers must take responsibility for security, sharing, and data handling.

## 3. Three Approaches to Work With Salesforce Data

### 3.1 Base Lightning Components Built on Lightning Data Service

Base Lightning components are ready-made Salesforce components, such as `lightning-record-form`, `lightning-record-edit-form`, and `lightning-record-view-form`.

They are generally the easiest option when their built-in behavior meets the requirement.

**Example:**

```html
<template>
    <lightning-record-form
        record-id={recordId}
        object-api-name="Account"
        layout-type="Full"
        mode="view">
    </lightning-record-form>
</template>
```

**Advantages**
- Less code to write.
- Standard Salesforce UI and behavior.
- LDS handles much of the record interaction.
- Good choice for common record forms and views.

**Limitation**
- Less flexibility than a custom LWC and Apex implementation.

### 3.2 Lightning Data Service (LDS) Wire Adapters and Functions

LDS provides wire adapters and functions to read, create, update, and delete Salesforce records through the UI API.

Examples include:

| Adapter or function | Purpose |
|---|---|
| `getRecord` | Retrieve record data |
| `getRecords` | Retrieve multiple records |
| `getObjectInfo` | Retrieve object metadata |
| `getPicklistValues` | Retrieve picklist values for a field |
| `getPicklistValuesByRecordType` | Retrieve picklist values for a record type |
| `createRecord()` | Create a record |
| `updateRecord()` | Update a record |
| `deleteRecord()` | Delete a record |

**Example:**

```javascript
import { LightningElement, wire, api } from 'lwc';
import { getRecord, getFieldValue } from 'lightning/uiRecordApi';
import NAME_FIELD from '@salesforce/schema/Account.Name';

export default class AccountDetails extends LightningElement {
    @api recordId;

    @wire(getRecord, {
        recordId: '$recordId',
        fields: [NAME_FIELD]
    })
    account;

    get accountName() {
        return getFieldValue(this.account.data, NAME_FIELD);
    }
}
```

**Advantages**
- Less server-side code for common record operations.
- Integrates with Salesforce UI API and LDS.
- Respects applicable Salesforce security and sharing behavior.
- Wire adapters provide reactive data provisioning.

**Limitation**
- UI API supports specific objects and operations. It does not cover every possible query or business process.

### 3.3 Apex

Apex is Salesforce's strongly typed, object-oriented programming language. It runs on the Salesforce platform and can be used to implement server-side business logic and data operations.

Use Apex when a base component or LDS UI API cannot satisfy the requirement.

**Advantages**
- High flexibility for custom business logic.
- Supports SOQL queries and DML operations.
- Can coordinate multiple related operations in a transaction.
- Can work with objects or operations not supported by the UI API, subject to Apex access and platform rules.

**Responsibilities**
- Enforce sharing and record access appropriately.
- Enforce object-level and field-level permissions.
- Validate input and handle exceptions.
- Consider governor limits and bulkification.

## 4. When to Use the Apex Approach

The second screenshot lists three situations where Apex is appropriate.

### 4.1 To work with objects that aren't supported by the User Interface API

The screenshot gives **Task** and **Event** as examples.

If the required object or operation is not supported by the UI API, an Apex method may be needed.

### 4.2 To work with operations that the User Interface API doesn't support

The screenshot's example is loading a list of records by criteria:

> For example, to load the first 200 Accounts with Amount greater than $1M.

A custom SOQL query in Apex can implement criteria-based retrieval when the required query is not available through the UI API operation being used.

**Illustrative Apex example:**

```apex
public with sharing class AccountController {
    @AuraEnabled(cacheable=true)
    public static List<Account> getHighValueAccounts() {
        return [
            SELECT Id, Name, AnnualRevenue
            FROM Account
            WHERE AnnualRevenue > 1000000
            ORDER BY AnnualRevenue DESC
            LIMIT 200
        ];
    }
}
```

> The screenshot uses “Amount” in its example. The code above uses Account `AnnualRevenue` as an illustrative Account field; use the field that matches your actual business requirement.

### 4.3 To perform a transactional operation

The screenshot gives this example:

- Create an Account.
- Create an Opportunity associated with the new Account.
- If either create operation fails, roll back the entire transaction.

This is a good use case for Apex because both DML operations can be performed in one server-side transaction. If an unhandled failure occurs, or the code explicitly rolls back to a savepoint, the transaction can be rolled back.

**Illustrative Apex example:**

```apex
public with sharing class AccountOpportunityController {
    public class CreationResult {
        @AuraEnabled public Id accountId;
        @AuraEnabled public Id opportunityId;
    }

    @AuraEnabled
    public static CreationResult createAccountAndOpportunity(
        String accountName,
        String opportunityName
    ) {
        Savepoint sp = Database.setSavepoint();

        try {
            Account accountRecord = new Account(
                Name = accountName
            );
            insert accountRecord;

            Opportunity opportunityRecord = new Opportunity(
                Name = opportunityName,
                AccountId = accountRecord.Id,
                StageName = 'Prospecting',
                CloseDate = Date.today().addDays(30)
            );
            insert opportunityRecord;

            CreationResult result = new CreationResult();
            result.accountId = accountRecord.Id;
            result.opportunityId = opportunityRecord.Id;
            return result;

        } catch (Exception e) {
            Database.rollback(sp);
            throw new AuraHandledException(
                'Unable to create the Account and Opportunity: ' +
                e.getMessage()
            );
        }
    }
}
```

**How this works**
1. A savepoint is created before the DML operations.
2. The Account is inserted.
3. The Opportunity is inserted and linked to the new Account using `AccountId`.
4. If an exception occurs, `Database.rollback(sp)` rolls back changes made after the savepoint.
5. The error is returned to the LWC as a handled exception.

This is an educational example. In a production implementation, validate input, enforce permissions, and avoid exposing sensitive exception details.

## 5. Two Ways to Call Apex Methods in LWC

The third screenshot divides Apex calls in LWC into two approaches:

1. **Wire Apex Methods**
2. **Call Apex Methods Imperatively**

Both approaches call an Apex method exposed to LWC with `@AuraEnabled`, but they differ in how and when the method is invoked.

### 5.1 Wire Apex Methods

Use the `@wire` decorator to call an Apex method when the component needs a reactive stream of data.

**Apex class — `AccountController.cls`**

```apex
public with sharing class AccountController {
    @AuraEnabled(cacheable=true)
    public static List<Account> getAccounts() {
        return [
            SELECT Id, Name, Industry
            FROM Account
            ORDER BY Name
            LIMIT 50
        ];
    }
}
```

**JavaScript — `wireApexDemo.js`**

```javascript
import { LightningElement, wire } from 'lwc';
import getAccounts from '@salesforce/apex/AccountController.getAccounts';

export default class WireApexDemo extends LightningElement {
    @wire(getAccounts)
    accounts;
}
```

**HTML — `wireApexDemo.html`**

```html
<template>
    <lightning-card title="Accounts Using Wire Apex">
        <template lwc:if={accounts.data}>
            <template for:each={accounts.data} for:item="account">
                <div key={account.Id} class="slds-p-around_small">
                    {account.Name} - {account.Industry}
                </div>
            </template>
        </template>

        <template lwc:if={accounts.error}>
            <p class="slds-text-color_error">
                Unable to load Accounts.
            </p>
        </template>
    </lightning-card>
</template>
```

**Important points**
- The Apex method must be annotated with `@AuraEnabled(cacheable=true)` when used with `@wire`.
- A wired Apex method must be read-only; it must not perform DML.
- The wire service provisions data reactively.
- The result is an object containing `data` and `error`.
- To pass reactive parameters, use `$` before the JavaScript property in the wire configuration.

### 5.2 Call Apex Methods Imperatively

An imperative Apex call is made explicitly from JavaScript, usually in response to a user action such as clicking a button.

It returns a Promise, so use `.then()` / `.catch()` or `async` / `await`.

**Apex class — `AccountController.cls`**

```apex
public with sharing class AccountController {
    @AuraEnabled
    public static Account createAccount(String accountName) {
        Account accountRecord = new Account(
            Name = accountName
        );

        insert accountRecord;
        return accountRecord;
    }
}
```

**JavaScript — `imperativeApexDemo.js`**

```javascript
import { LightningElement } from 'lwc';
import createAccount from '@salesforce/apex/AccountController.createAccount';
import { ShowToastEvent } from 'lightning/platformShowToastEvent';

export default class ImperativeApexDemo extends LightningElement {
    accountName = '';

    handleNameChange(event) {
        this.accountName = event.target.value;
    }

    async handleCreateAccount() {
        if (!this.accountName.trim()) {
            this.showToast('Warning', 'Enter an Account name.', 'warning');
            return;
        }

        try {
            const result = await createAccount({
                accountName: this.accountName
            });

            this.showToast(
                'Success',
                `Account created. Record Id: ${result.Id}`,
                'success'
            );

            this.accountName = '';
        } catch (error) {
            this.showToast(
                'Error',
                error?.body?.message || 'Unable to create Account.',
                'error'
            );
            console.error(error);
        }
    }

    showToast(title, message, variant) {
        this.dispatchEvent(
            new ShowToastEvent({ title, message, variant })
        );
    }
}
```

**HTML — `imperativeApexDemo.html`**

```html
<template>
    <lightning-card title="Create Account Using Imperative Apex">
        <div class="slds-p-around_medium">
            <lightning-input
                label="Account Name"
                value={accountName}
                onchange={handleNameChange}>
            </lightning-input>

            <lightning-button
                class="slds-m-top_medium"
                label="Create Account"
                variant="brand"
                onclick={handleCreateAccount}>
            </lightning-button>
        </div>
    </lightning-card>
</template>
```

**Important points**
- The method is called only when JavaScript invokes it.
- It is suitable for user-triggered operations.
- It can be used for read or write operations.
- It returns a Promise.
- Pass Apex parameters as an object whose property names match the Apex method parameter names.

## 6. Wire vs. Imperative Apex

| Feature | Wire Apex | Imperative Apex |
|---|---|---|
| Invocation | Automatically by the wire service | Explicit JavaScript call |
| Typical use | Reactive data retrieval | Button clicks and controlled operations |
| Return handling | `data` and `error` properties | Promise |
| Apex annotation | `@AuraEnabled(cacheable=true)` | `@AuraEnabled`; use `cacheable=true` for cacheable read methods when appropriate |
| DML operations | Not allowed in a wired read method | Can perform DML |
| Parameters | Reactive values can use `$propertyName` | Passed in a JavaScript object |
| Execution control | Managed by wire service | Developer decides when to call |
| Example | Load Account list when component loads | Create Account after button click |

### Which one should you choose?

- Use **wire Apex** when you need read-only data that should be provisioned reactively.
- Use **imperative Apex** when you need to control exactly when a method runs, especially for user actions or DML operations.

## 7. How to Import an Apex Method in LWC

Use this format:

```javascript
import methodName from '@salesforce/apex/ClassName.methodName';
```

Example:

```javascript
import getAccounts from '@salesforce/apex/AccountController.getAccounts';
```

Where:
- `AccountController` is the Apex class name.
- `getAccounts` is the Apex method name.
- The imported JavaScript identifier can be used with `@wire` or called imperatively.

### Apex method requirements

- The Apex class must be accessible to the LWC through an `@AuraEnabled` method.
- The method must be `static`.
- The method must be annotated with `@AuraEnabled`.
- A method used with `@wire` must also have `cacheable=true`.
- The running user must have access to the Apex class.

## 8. Important Security Considerations

Apex provides flexibility, but developers must handle security carefully.

### Sharing

Use an appropriate sharing declaration, such as `with sharing`, to enforce record-level sharing rules for the class.

### Object-level and field-level permissions

`with sharing` does not automatically enforce object permissions or field-level security. Consider:
- `Security.stripInaccessible()`
- `WITH USER_MODE` in SOQL where appropriate
- User-mode database operations where appropriate
- Explicit permission checks when needed

### Input validation

Validate values received from the LWC. Do not assume client-side validation is sufficient.

### Error handling

Use controlled exceptions such as `AuraHandledException` when returning safe, understandable messages to the LWC. Avoid exposing internal implementation details.

### Governor limits

Apex runs under Salesforce governor limits. Write efficient SOQL and DML, avoid queries or DML inside loops, and bulkify operations.

## 9. Step-by-Step Setup

1. Open your Salesforce DX project in VS Code.
2. Create an Apex class in `force-app/main/default/classes`.
3. Add the `@AuraEnabled` method you need.
4. Create an LWC folder under `force-app/main/default/lwc`.
5. Add the component HTML, JavaScript, and metadata XML files.
6. Import the Apex method in the LWC JavaScript file.
7. Choose `@wire` for reactive read-only data or an imperative call for controlled execution.
8. Deploy the Apex class and LWC to your Salesforce org.
9. Add the component to a Lightning App Page or another supported target.
10. Test with users who have the intended permissions.

## 10. Interview Questions and Answers

### Q1. What is Apex in LWC?
Apex is Salesforce's server-side programming language. LWC can call Apex methods to execute custom business logic and data operations that are not adequately supported by base components or LDS UI API.

### Q2. When should we use Apex instead of Lightning Data Service?
Use Apex when the required object or operation is not supported by UI API, when custom SOQL or complex business logic is required, or when multiple operations must be handled in a single transaction.

### Q3. What are the three data-access approaches shown in the introduction?
1. Base Lightning components built on LDS.
2. LDS wire adapters and functions.
3. Apex.

### Q4. What are the two ways to call Apex from LWC?
1. Wire Apex methods using `@wire`.
2. Call Apex methods imperatively from JavaScript.

### Q5. What is the difference between wired and imperative Apex?
Wired Apex is provisioned reactively by the wire service and is used for read-only methods. Imperative Apex is invoked explicitly from JavaScript and returns a Promise, making it suitable for user-triggered operations and DML.

### Q6. What annotation is required to expose an Apex method to LWC?
Use `@AuraEnabled` on a `public` or `global` static method.

### Q7. What additional annotation is required for a wired Apex method?
Use `@AuraEnabled(cacheable=true)`. The method must not perform DML or otherwise modify data.

### Q8. Can we perform DML in a wired Apex method?
No. Wired Apex methods must be read-only. Use an imperative Apex call for DML operations.

### Q9. Can an imperative Apex method perform DML?
Yes. An imperative call can invoke an `@AuraEnabled` Apex method that performs insert, update, delete, or other supported server-side operations.

### Q10. How do you import an Apex method in LWC?
```javascript
import methodName from '@salesforce/apex/ClassName.methodName';
```

### Q11. How do you pass parameters to an imperative Apex method?
Pass a JavaScript object with property names matching the Apex method's parameter names.

```javascript
createAccount({ accountName: this.accountName });
```

### Q12. How do you handle errors from imperative Apex?
Use `.catch()` or `try/catch` with `async/await`.

### Q13. What does `cacheable=true` mean?
It indicates that the method is read-only and its result can be cached by the framework. It is required for Apex methods used with `@wire`.

### Q14. Can we use `cacheable=true` with an imperative Apex call?
Yes, for a read-only method. However, `cacheable=true` methods must not perform DML.

### Q15. What is a transaction in Apex?
A transaction is a unit of work. If an unhandled exception occurs, Salesforce generally rolls back the transaction's database changes. A savepoint and `Database.rollback()` can be used for explicit rollback handling.

### Q16. How can we create an Account and an Opportunity in one transaction?
Call an Apex method that inserts the Account, uses its generated ID as the Opportunity's `AccountId`, and inserts the Opportunity. Handle failures and roll back to a savepoint when appropriate.

### Q17. What is the purpose of `with sharing`?
It enforces record-level sharing rules for the Apex class. It does not by itself enforce object-level or field-level permissions.

### Q18. How do you enforce field-level security in Apex?
Use mechanisms such as `Security.stripInaccessible()` or user-mode operations, depending on the use case.

### Q19. What are governor limits?
Governor limits restrict resource usage in Apex, such as SOQL queries, DML statements, CPU time, and heap size, to protect the shared Salesforce platform.

### Q20. Why should SOQL queries not be placed inside loops?
It can cause governor-limit exceptions. Query records in bulk and process them using collections.

### Q21. What is the difference between `@wire` and `@api`?
`@wire` connects a property or function to a data source. `@api` exposes a public property or method for a parent component or framework to use.

### Q22. What is the difference between LDS and Apex?
LDS/UI API provides standard record operations and integrates with Salesforce data access behavior. Apex provides custom server-side logic and more flexibility, but developers must carefully enforce security and handle limits.

### Q23. What is `AuraHandledException`?
It is an Apex exception type that can be used to return a controlled error message to a Lightning component.

### Q24. Can Apex be called from a button click in LWC?
Yes. Import the Apex method and invoke it from the button's click handler. This is an imperative Apex call.

### Q25. When should you avoid Apex?
Avoid Apex when a standard base component or LDS UI API adapter/function already meets the requirement. This reduces custom code and security-maintenance responsibilities.

## Summary

The introduction explains that Salesforce data can be accessed through base Lightning components, LDS wire adapters and functions, or Apex. Prefer base components or LDS when they meet the requirement. Use Apex when you need unsupported data access, custom server-side logic, or coordinated transactional operations.

LWC can call Apex in two ways: **wire** for reactive, read-only data and **imperative** calls for explicitly controlled execution, including data changes.
