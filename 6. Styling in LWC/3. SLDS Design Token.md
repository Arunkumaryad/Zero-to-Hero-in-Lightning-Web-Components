This document explains **SLDS Design Tokens** — what they are, why they exist, and how to use them inside Lightning Web Components to keep your styling consistent with Salesforce's Lightning Design System.

---

## 📌 What is a Design Token?

**Definition:** A **design token** is a **named variable** that stores a single, reusable **design decision** — such as a color, spacing value, font size, or border radius — instead of hardcoding that raw value directly in your CSS.

In simple words — rather than writing a raw hex color like `#eb7092` or a raw pixel value like `12px` directly inside your CSS rules, SLDS gives that value a **meaningful name** (a token), like `$color-text-error` or `$spacing-medium`. You then use the **token name** in your styles instead of the raw value.

### Why This Matters
- If Salesforce ever **updates** the underlying value (e.g., changes its brand color slightly), every component using the **token** automatically picks up the new value — you don't have to hunt down and update hardcoded values everywhere.
- It keeps your custom component styling **consistent** with the rest of the Salesforce Lightning Experience, since you're reusing the **exact same values** that Salesforce's own UI uses internally.
- It makes your CSS more **readable and self-documenting** — `$color-text-error` clearly communicates intent, whereas `#ea001e` does not.

## 🧩 Types of SLDS Design Tokens

SLDS design tokens are generally grouped into categories based on what kind of design property they represent:

| Category | Example Tokens | Purpose |
|---|---|---|
| **Color** | `$color-brand`, `$color-text-error`, `$color-background-alt` | Consistent brand, text, and background colors |
| **Spacing** | `$spacing-x-small`, `$spacing-medium`, `$spacing-large` | Consistent margin/padding values |
| **Font** | `$font-size-3`, `$font-weight-bold` | Consistent typography sizing and weight |
| **Border** | `$border-radius-medium`, `$border-width-thin` | Consistent border styling |
| **Shadow** | `$shadow-drop-medium` | Consistent box-shadow / elevation effects |

## 🧩 Using Design Tokens in LWC

Since Lightning Web Components use **standard CSS** files (as covered earlier in the *Inline and External CSS* documentation), SLDS design tokens are typically consumed in one of the following ways:

### 1. Using SLDS CSS Custom Properties (CSS Variables)
Modern SLDS design tokens are exposed as **CSS custom properties** (CSS variables), which can be used directly inside your component's `.css` file:

```css
.myElement {
    color: var(--slds-g-color-brand-base-50, #0176d3);
    padding: var(--slds-g-spacing-4, 1rem);
}
```

- `var(--token-name, fallback-value)` — this is standard CSS variable syntax. It tells the browser: *"use the value of `--slds-g-color-brand-base-50` if it's defined; otherwise, fall back to `#0176d3`."*
- Using a **fallback value** is a best practice, in case the token isn't available in a particular context.

### 2. Using SLDS Utility Classes (Indirect Token Usage)
As covered in the *Lightning Design System* documentation, SLDS also provides ready-made **utility classes** (like `slds-m-around_medium`, `slds-p-top_small`) that **internally** apply these design tokens for you — so in many cases, you don't need to reference tokens directly at all; you simply use the utility class, and SLDS handles the token-based styling behind the scenes.

## ✅ Quick Recap

- **Design tokens** are named variables for design values (colors, spacing, fonts, borders, shadows) — used instead of hardcoding raw values.
- They keep custom LWC components **visually consistent** with Salesforce's own Lightning Experience UI.
- In LWC CSS files, tokens are typically consumed as **CSS custom properties** using `var(--token-name, fallback)`.
- Many SLDS **utility classes** already apply design tokens internally, so you often get token-based consistency "for free" just by using standard SLDS classes.
