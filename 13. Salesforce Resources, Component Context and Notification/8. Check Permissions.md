# Check Permissions in Salesforce LWC

## Overview

This README explains how to check standard Salesforce user permissions and custom permissions in a Lightning Web Component (LWC), following the supplied training screenshots.

The screenshots demonstrate importing `ViewAllData` from `@salesforce/userPermission`, importing `showPermission` from `@salesforce/customPermission`, creating a profile and user for testing, creating a custom permission, assigning it through a permission set, and conditionally displaying messages in an LWC.

## 1. Actual Definition from the Screenshot

The screenshot states:

> Import Salesforce permissions from the `@salesforce/userPermission` and `@salesforce/customPermission` scoped modules.

### Syntax shown in the screenshot

```javascript
import hasPermission from '@salesforce/userPermission/PermissionName';
```

```javascript
import hasPermission from '@salesforce/customPermission/PermissionName';
```

These scoped modules allow an LWC to check whether the current user has a supported standard Salesforce user permission or a custom permission. The imported value is Boolean: `true` if the current user has the permission and `false` otherwise.

## 2. What Is Permission Checking?

Permission checking means determining whether the current Salesforce user has a particular permission and using the result to control what the component displays.

| Permission type | Meaning | Module |
|---|---|---|
| Standard user permission | A permission provided by Salesforce, such as `ViewAllData` | `@salesforce/userPermission` |
| Custom permission | An organization-defined permission for a custom feature, such as `showPermission` | `@salesforce/customPermission` |

### Why use permission checks?

- Display or hide parts of the UI based on the user's access.
- Show appropriate messages for users with and without a permission.
- Control access to custom features through permission sets.
- Keep component behavior aligned with the Salesforce access model.

**Security note:** Hiding a button or message in LWC does not secure the underlying data or operation. Server-side logic must still enforce authorization and appropriate record, object, and field access.

## 3. Standard User Permission: `ViewAllData`

The screenshot imports this permission:

```javascript
import hasViewAllData from '@salesforce/userPermission/ViewAllData';
```

`ViewAllData` is a powerful Salesforce permission that provides broad visibility into organization data, subject to Salesforce platform behavior and exceptions. Grant it only when necessary.

To manage it, open **Setup**, find **Profiles** or **Permission Sets**, open the relevant profile or permission set, locate **System Permissions**, and enable **View All Data** if appropriate. Save the changes.

For practice, use a suitable test org and a test user. You do not need to grant this powerful permission simply to learn the import syntax.

## 4. Create the Custom Permission

The screenshots show **Setup → Custom Permissions** and the **New** button. The example permission is named `showPermission`.

1. Open Salesforce **Setup**.
2. Search for **Custom Permissions** in Quick Find.
3. Open **Custom Permissions** under **Custom Code**.
4. Click **New**.
5. Enter a label, for example `showPermission`.
6. Set the **Name** (API name) to `showPermission`.
7. Add an optional description.
8. Save.

A custom permission represents access to a custom feature or business function. Its label and API name may differ, so always use the actual API name in the import path.

## 5. Grant the Custom Permission Through a Permission Set

Creating a custom permission does not automatically grant it to users. It must be enabled through a supported access mechanism, such as a permission set or profile.

1. Open **Setup → Permission Sets**.
2. Click **New**, or open an existing permission set.
3. Create or select a permission set, for example `CustomPermissionDemo`.
4. Open the permission set.
5. Find **Custom Permissions**.
6. Click **Edit**, if required.
7. Enable `showPermission` by moving it into the enabled list.
8. Save.
9. Click **Manage Assignments**.
10. Assign the permission set to the user you want to test.

This allows feature access to be managed separately from a user's baseline profile.

## 6. Profile and User Setup Shown in the Screenshots

### Clone a profile

The screenshots show cloning the **System Administrator** profile and naming the clone `Permission Check`.

1. In Setup, search for **Profiles**.
2. Click **Clone** next to an existing profile.
3. Enter `Permission Check` as the profile name.
4. Save and review the profile permissions.

**Best practice:** Do not give a test user System Administrator-level access unless it is genuinely required. Prefer a less-privileged profile for ordinary testing.

### Create a user

1. In Setup, search for **Users**.
2. Open **Users** and click **New User**.
3. Enter the required user details, including a unique username and valid email address.
4. Select a compatible **User License**.
5. Select the appropriate **Profile**, such as `Permission Check`.
6. Complete other required fields and save.
7. Assign the permission set containing `showPermission` if you are testing the custom permission.

Available permissions depend on the user's license and profile. Ensure the selected access configuration is compatible with that license.

## 7. JavaScript Code from the Screenshot

The screenshot shows:

```javascript
import { LightningElement } from 'lwc';
import hasViewAllData from '@salesforce/userPermission/ViewAllData';
import myCustomPermission from '@salesforce/customPermission/showPermission';

export default class CheckPermissionDemo extends LightningElement {

    get hasViewAllDataAvailable() {
        return hasViewAllData;
    }

    get hasCustomPermissionAvailable() {
        return myCustomPermission;
    }
}
```

### Explanation

- `LightningElement` is the base class for an LWC.
- `hasViewAllData` imports the standard `ViewAllData` permission.
- `myCustomPermission` imports the custom permission `showPermission`.
- `hasViewAllDataAvailable` exposes the standard permission result to the template.
- `hasCustomPermissionAvailable` exposes the custom permission result to the template.
- The result represents the current user's permission.

The getter names are developer-defined and do not have to match the permission API names.

## 8. HTML Code from the Screenshot

The screenshot uses conditional templates like these:

```html
<template>
    <lightning-card title="User Permission Demo">
        <template if:true={hasViewAllDataAvailable}>
            <p>Hurray!! I have a User Permission.</p>
        </template>
        <template if:false={hasViewAllDataAvailable}>
            <p>Opps!! I don't have a User Permission.</p>
        </template>
    </lightning-card>

    <lightning-card title="Custom Permission Demo">
        <template if:true={hasCustomPermissionAvailable}>
            <p>Hurray!! I have a Custom Permission.</p>
        </template>
        <template if:false={hasCustomPermissionAvailable}>
            <p>Opps!! I don't have a Custom Permission.</p>
        </template>
    </lightning-card>
</template>
```

- `if:true` displays content when the permission is `true`.
- `if:false` displays the alternative when the permission is `false`.
- The first card checks `ViewAllData`.
- The second card checks `showPermission`.

The screenshot's wording `Opps!!` is reproduced above; for production UI, use correct spelling such as “Oops!”. Salesforce also supports the newer `lwc:if` and `lwc:else` directives, used in the complete example below.

## 9. Complete Example for Practice

Create this folder in your Salesforce DX project:

```text
force-app/main/default/lwc/checkPermissionDemo/
├── checkPermissionDemo.html
├── checkPermissionDemo.js
└── checkPermissionDemo.js-meta.xml
```

Create the custom permission `showPermission` in Setup and grant it through a permission set to your test user.

### `checkPermissionDemo.js`

```javascript
import { LightningElement } from 'lwc';

import hasViewAllData from '@salesforce/userPermission/ViewAllData';
import myCustomPermission from '@salesforce/customPermission/showPermission';

export default class CheckPermissionDemo extends LightningElement {
    get hasViewAllDataAvailable() {
        return hasViewAllData;
    }

    get hasCustomPermissionAvailable() {
        return myCustomPermission;
    }
}
```

### `checkPermissionDemo.html`

```html
<template>
    <lightning-card title="User Permission Demo">
        <div class="slds-p-around_medium">
            <template lwc:if={hasViewAllDataAvailable}>
                <p>The current user has the View All Data permission.</p>
            </template>
            <template lwc:else>
                <p>The current user does not have the View All Data permission.</p>
            </template>
        </div>
    </lightning-card>

    <lightning-card title="Custom Permission Demo">
        <div class="slds-p-around_medium">
            <template lwc:if={hasCustomPermissionAvailable}>
                <p>The current user has the custom permission.</p>
            </template>
            <template lwc:else>
                <p>The current user does not have the custom permission.</p>
            </template>
        </div>
    </lightning-card>
</template>
```

### `checkPermissionDemo.js-meta.xml`

The screenshot uses API version `67.0` and exposes the component on a Lightning App Page:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__AppPage</target>
    </targets>
</LightningComponentBundle>
```

Use an API version supported by your target Salesforce org. `67.0` is the version shown in the training screenshot.

## 10. Deploy and Test

1. Open the Salesforce DX project in VS Code.
2. Create the `checkPermissionDemo` folder and its three files.
3. Create `showPermission` in Setup.
4. Enable it in a permission set and assign the permission set to the test user.
5. Grant `ViewAllData` only if appropriate for the test user and test scenario.
6. Deploy the component and required metadata. For example:

   ```bash
   sf project deploy start
   ```

7. Open **Setup → Lightning App Builder**.
8. Create or edit a Lightning App Page.
9. Drag **Check Permission Demo** onto the page.
10. Save and activate the page if needed.
11. Open the page as the user you want to test.
12. Verify the messages displayed in both cards.

### Expected test results

| User access | Expected result |
|---|---|
| User has `ViewAllData` | First card displays the positive message |
| User lacks `ViewAllData` | First card displays the negative message |
| User is assigned `showPermission` | Second card displays the positive message |
| User is not assigned `showPermission` | Second card displays the negative message |

Test with appropriately configured users. Avoid changing production permissions just to test the component.

## 11. Important Concepts and Best Practices

### Standard permission vs. custom permission

- **Standard user permission:** Defined by Salesforce, such as `ViewAllData`.
- **Custom permission:** Defined by your organization for a custom feature, such as `showPermission`.

### Profile vs. permission set

- **Profile:** Provides a user's baseline permissions and settings.
- **Permission set:** Adds permissions to a user without requiring a profile change.
- **Custom permission:** Represents access to a custom feature and can be granted through supported profiles or permission sets.

### UI visibility is not security

A user may be prevented from seeing a button in the LWC, but that does not independently secure the operation. Enforce authorization and data access in Apex, APIs, and other server-side operations. Apply sharing, object permissions, field-level security, and user-mode operations as appropriate.

### Least privilege

Give users only the access needed for their work. `ViewAllData` is highly privileged. For access to a single custom feature, a custom permission is often a more focused solution.

# Interview Questions and Answers

### Q1. What is permission checking in LWC?

It checks whether the current Salesforce user has a specified standard user permission or custom permission and uses the Boolean result to control the UI.

### Q2. What are `@salesforce/userPermission` and `@salesforce/customPermission`?

They are scoped modules used to import supported standard user permissions and custom permissions into an LWC.

### Q3. What is the syntax for a standard user permission?

```javascript
import hasPermission from '@salesforce/userPermission/PermissionName';
```

Example:

```javascript
import hasViewAllData from '@salesforce/userPermission/ViewAllData';
```

### Q4. What is the syntax for a custom permission?

```javascript
import hasPermission from '@salesforce/customPermission/PermissionName';
```

Example:

```javascript
import myCustomPermission from '@salesforce/customPermission/showPermission';
```

### Q5. What does the imported value represent?

A Boolean value indicating whether the current user has the specified permission.

### Q6. What is a Custom Permission?

An organization-defined permission that represents access to a custom feature or business function.

### Q7. How do you grant a custom permission to a user?

Create the permission, enable it in a permission set or another supported assignment mechanism, and assign that permission set to the user.

### Q8. What is the difference between a Profile and a Permission Set?

A profile establishes baseline access. A permission set adds permissions to a user without changing their profile.

### Q9. Why might a custom permission import return `false`?

The user may not have been granted the permission, the permission set may not be assigned, or the import path/API name may be incorrect.

### Q10. Does hiding a button in LWC secure the underlying data?

No. UI checks are not a security boundary. Enforce authorization and data access at the server and data layers as well.

### Q11. What is `ViewAllData`?

A powerful standard Salesforce permission that provides broad visibility into organization data, subject to Salesforce platform behavior and exceptions.

### Q12. Why are getters used in this example?

Getters expose the imported permission values through properties referenced by the HTML template.

### Q13. What do `if:true` and `if:false` do?

They conditionally render template content based on a Boolean expression. Newer templates can use `lwc:if` and `lwc:else`.

### Q14. When should you use a custom permission?

Use it to represent access to a particular custom feature, such as a special approval action, and grant it to the intended users.

### Q15. Can any permission name be imported by writing it in the module path?

No. Use a permission supported by the relevant scoped module and ensure the API name and namespace are correct.

# Scenario-Based Interview Questions

### Scenario 1: Show a button only to users with a custom permission

**Approach:** Create the custom permission, grant it through a permission set, import it using `@salesforce/customPermission`, and conditionally render the button. Also enforce authorization when the operation reaches the server.

### Scenario 2: A user should have access, but the component shows the negative message

**Approach:** Verify the API name, confirm the permission is enabled in the permission set, check the user's assignment, and test as the intended user.

### Scenario 3: A user sees a button but gets an access error after clicking it

**Approach:** Review server-side authorization, Apex sharing, object permissions, field-level security, and record access. UI visibility alone does not grant server access.

### Scenario 4: The business wants to grant feature access without creating another profile

**Approach:** Create a custom permission and assign it through a permission set. This allows feature access to be managed independently of the user's profile.

### Scenario 5: You need to test both permission outcomes

**Approach:** Test with one user who has the permission and another who does not. Use a safe test environment and avoid granting unnecessary administrator permissions.

# One-Line Interview Definitions

- **Permission check:** Determines whether the current user has a particular permission.
- **User permission:** A supported standard Salesforce permission imported through `@salesforce/userPermission`.
- **Custom permission:** An organization-defined permission representing access to a custom feature.
- **`@salesforce/userPermission`:** Scoped module for importing supported standard user permissions into LWC.
- **`@salesforce/customPermission`:** Scoped module for importing custom permissions into LWC.
- **Profile:** Defines baseline user permissions and settings.
- **Permission set:** Grants additional permissions to a user.
- **Conditional rendering:** Displays template content only when a condition is met.
- **Least privilege:** Gives users only the access required for their work.
- **Server-side authorization:** Enforces access checks where the data or operation is actually performed.
