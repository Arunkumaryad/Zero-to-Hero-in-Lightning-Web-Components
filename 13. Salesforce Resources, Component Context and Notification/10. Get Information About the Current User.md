# Get Information About the Current User in Salesforce LWC

## Overview

This README explains how to get information about the current Salesforce user in a Lightning Web Component (LWC), using the `@salesforce/user` scoped module.

The training screenshots demonstrate importing the current user's ID and whether the current user is a guest user, displaying both values in an LWC, and exposing the component on a Lightning App Page.

## 1. Actual Definition from the Screenshot

The screenshot states:

> To get information about the current user, use the `@salesforce/user` scoped module.

### Syntax shown in the screenshot

```javascript
import property from '@salesforce/user/property';
```

The screenshot says that `property` supports only two properties:

1. **`Id`** — User's ID.
2. **`isGuest`** — A Boolean value indicating whether the user is a community guest user or not.

In the current Salesforce Experience Cloud terminology, this is commonly understood as whether the current user is a guest user. A guest user is an unauthenticated user accessing a public Experience Cloud site or other Salesforce guest-enabled experience.

## 2. What Is `@salesforce/user`?

`@salesforce/user` is a Salesforce scoped module that exposes information about the current user to a Lightning Web Component. The screenshot demonstrates these imports:

```javascript
import ID from '@salesforce/user/Id';
import IS_GUEST from '@salesforce/user/isGuest';
```

- `Id` provides the current user's Salesforce user ID.
- `isGuest` provides a Boolean value: `true` if the current user is a guest user, or `false` if not.

These imports refer to the user context in which the component is running. They do not let a component choose an arbitrary user by changing the import path.

## 3. JavaScript Code from the Screenshot

The screenshot shows:

```javascript
import { LightningElement } from 'lwc';
import ID from '@salesforce/user/Id';
import IS_GUEST from '@salesforce/user/isGuest';

export default class UserInformation extends LightningElement {
    userId = ID;
    isGuest = IS_GUEST;
}
```

### Explanation, line by line

- `import { LightningElement } from 'lwc';` imports the base class for an LWC.
- `import ID from '@salesforce/user/Id';` imports the current user's ID.
- `import IS_GUEST from '@salesforce/user/isGuest';` imports whether the current user is a guest user.
- `userId = ID;` stores the ID in a component property.
- `isGuest = IS_GUEST;` stores the Boolean guest-user result in a component property.
- The HTML template can reference these properties with `{userId}` and `{isGuest}`.

The import identifiers `ID` and `IS_GUEST` are developer-chosen variable names. The module property names `Id` and `isGuest` are case-sensitive and must match the supported names.

## 4. HTML Code from the Screenshot

The screenshot shows:

```html
<template>
    <lightning-card title="Get User Info Demo">
        <p><strong>User Id Is : </strong>{userId}</p>
        <p><strong>Is User Guest : </strong>{isGuest}</p>
    </lightning-card>
</template>
```

### Explanation

- `<template>` contains the component's markup.
- `<lightning-card>` creates a card titled **Get User Info Demo**.
- `{userId}` displays the imported current user's ID.
- `{isGuest}` displays `true` or `false`.
- `<strong>` makes the labels bold.

The screenshot's sample output shows a user ID and `Is User Guest: false`. Your org will display a different ID, and the Boolean depends on the current user context.

## 5. Component Metadata XML from the Screenshot

The screenshot uses API version `67.0` and exposes the component on a Lightning App Page:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__AppPage</target>
    </targets>

```

Use an API version supported by your target Salesforce org. `67.0` is the version shown in the training screenshot.

## 7. Deploy and Test Step by Step

1. Open your Salesforce DX project in VS Code.
2. Navigate to `force-app/main/default/lwc/`.
3. Create a folder named `userInformation`.
4. Add the HTML, JavaScript, and metadata XML files shown above.
5. Save the files.
6. Deploy the component to your Salesforce org. For example, from the project terminal:

   ```bash
   sf project deploy start
   ```

7. In Salesforce, open **Setup → Lightning App Builder**.
8. Create a new Lightning App Page or edit an existing one.
9. Find **Get User Info Demo** in the custom components list and drag it onto the page.
10. Save and activate the page if needed.
11. Open the page as the user you want to test.
12. Check the displayed user ID and guest-user value.

## 8. Understanding Guest Users

A guest user is an unauthenticated user who can access a public Experience Cloud site or another supported guest-enabled Salesforce experience without logging in.

- For a normal authenticated Salesforce user, `isGuest` is generally `false`.
- For an applicable guest-user context, `isGuest` is `true`.
- Guest-user access must be configured carefully because guest users can access only resources explicitly made available to them.

Do not treat the Boolean as a substitute for record-level or server-side security. Configure guest-user sharing and access policies appropriately.

## 9. Why Is This Useful?

You can use current-user information to:

- Display or log the current user's ID where appropriate.
- Make a UI behave differently for authenticated and guest contexts.
- Provide different navigation or messages for guest and logged-in users.
- Support debugging and user-context-aware component behavior.

Avoid displaying user identifiers unnecessarily in public interfaces. A user ID is an identifier and should only be shown when it is useful for the intended audience.

## 10. Important Notes and Best Practices

- Use the exact supported module paths and casing: `@salesforce/user/Id` and `@salesforce/user/isGuest`.
- `Id` is a string identifier; `isGuest` is a Boolean.
- These modules refer to the current execution context, not any user selected by the component.
- The module does not provide arbitrary user profile details, email addresses, or names through these two imports.
- Do not use `isGuest` as the only protection for sensitive operations. Enforce access with Salesforce permissions, sharing, and server-side checks.
- Test in the Salesforce context where the component will be used, including a guest-enabled site if guest behavior matters.

# Scenario-Based Interview Questions

### Scenario 1: Show a message only to authenticated users

**Approach:** Import `isGuest` and conditionally render the message when it is `false`. Remember that UI conditions do not replace authorization checks.

### Scenario 2: `isGuest` is `true` on a public site

**Approach:** Confirm that the page is being accessed without authentication and review the site's guest-user configuration. This is expected for an applicable guest context.

### Scenario 3: The displayed user ID differs between users

**Approach:** This is expected. The module reports the ID for the current execution context.

### Scenario 4: A developer wants to display sensitive records only to logged-in users

**Approach:** The component can use `isGuest` to tailor its UI, but the records must also be protected by Salesforce sharing and server-side authorization. Do not rely only on conditional rendering.
