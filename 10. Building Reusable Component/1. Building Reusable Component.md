# Building Reusable Component (LWC) – Custom Lightning Card

This project demonstrates how to build a **reusable, generic Lightning Web Component (LWC)** — a custom card — using **standard slots**, **named slots**, and the **`slotchange` event**. The same `c-custom-lightning-card` component is reused four times with different combinations of content (title, body, actions, footer), and it automatically adjusts its layout depending on what content is actually passed into it.

This mirrors how Salesforce's own `lightning-card` base component works internally.

## 🧩 Component 1: `customLightningCard` (the reusable child)

### `customLightningCard.html`

```html
<template>
    <article class="slds-card">

        <!-- ============================== -->
        <!-- HEADER -->
        <!-- ============================== -->

        <div class="slds-card__header slds-grid">

            <header class="slds-media slds-media_center slds-has-flexi-truncate">

                <!-- TITLE -->
                <div class="slds-media__body">

                    <h2 class="slds-card__header-title">

                        <div class="slds-card__header-link slds-truncate">
                            <slot name="title"></slot>
                        </div>

                    </h2>

                </div>

                <!-- ACTIONS -->
                <div class={actionsClass}>

                    <slot
                        name="actions"
                        onslotchange={handleActionsChange}>
                    </slot>

                </div>

            </header>

        </div>

        <!-- ============================== -->
        <!-- BODY -->
        <!-- ============================== -->

        <div class={bodyClass}>

            <slot
                onslotchange={handleBodyChange}>
            </slot>

        </div>

        <!-- ============================== -->
        <!-- FOOTER -->
        <!-- ============================== -->

        <footer class={footerClass}>

            <slot
                name="footer"
                onslotchange={handleFooterChange}>
            </slot>

        </footer>

    </article>
</template>
```

### `customLightningCard.js`

```javascript
import { LightningElement } from 'lwc';

export default class CustomLightningCard extends LightningElement {
    hasBody = false;
    hasActions = false;
    hasFooter = false;

    handleBodyChange(event) {
        this.hasBody = event.target.assignedElements.length > 0;
    }

    handleActionsChange(event) {
        this.hasActions = event.target.assignedElements.length > 0;
    }

    handleFooterChange(event) {
        this.hasFooter = event.target.assignedElements.length > 0;
    }

    get bodyClass() {
        return this.hasBody
            ? 'slds-card__body slds-card__body_inner'
            : 'slds-hide';
    }

    get actionsClass() {
        return this.hasActions
            ? 'slds-no-flex'
            : 'slds-hide';
    }

    get footerClass() {
        return this.hasFooter
            ? 'slds-card__footer'
            : 'slds-hide';
    }
}
```

### `customLightningCard.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>false</isExposed>
</LightningComponentBundle>
```

> `isExposed` is `false` here because this is an **internal, reusable building-block component**. It is only meant to be consumed by other components (like `reusableComponentDemo`), not placed directly on an App Builder page, so it does not need to be exposed as a target.

## 📖 Key Concepts Explained (Simple Terms)

### 1. What is a "reusable component" here?
Instead of writing four separate hardcoded cards, we build **one generic card component** (`customLightningCard`) whose header, body, actions, and footer are all left "empty" (as slots). The **parent component decides what content goes where**, while the child component only controls the **layout and styling**. This is the same pattern Salesforce uses for the standard `lightning-card` component.

### 2. What is a Slot?
A `<slot>` is a placeholder inside a child component's HTML that lets the **parent component inject its own markup** into a specific spot inside the child.

```html
<div class="slds-card__body">
    <slot></slot>
</div>
```

Whatever HTML the parent puts inside `<c-custom-lightning-card>...</c-custom-lightning-card>` (that isn't assigned to a named slot) automatically lands in this **default/unnamed slot**.

### 3. What is a Named Slot?
A component can have **multiple slots**, each identified with a unique `name` attribute:

```html
<slot name="title"></slot>
<slot name="actions"></slot>
<slot name="footer"></slot>
```

The parent targets a specific named slot using the `slot="..."` attribute on the element it passes in:

```html
<h1 slot="title">This is a title</h1>
<div slot="actions">...</div>
<div slot="footer">...</div>
```

Content **without** a `slot` attribute automatically goes into the **default (unnamed) slot** — that's why `<h1>This is the body</h1>` (no `slot` attribute) lands in the body section.

> ⚠️ **Rule:** A component can only have **one default (unnamed) slot**, but it can have **any number of named slots**.

### 4. What is the `slotchange` Event?
`slotchange` is a native DOM event that fires **automatically whenever the content assigned to a slot changes** — for example, when the component first renders and content gets projected into the slot, or when that content is later added/removed dynamically.

```html
<slot onslotchange={handleBodyChange}></slot>
```

This is the trick that lets `customLightningCard` **detect, at runtime, whether the parent actually passed content into a given slot** — since not every parent card in the demo provides a footer or actions.

### 5. What is `event.target.assignedElements()`/`.assignedElements`?
Inside the slotchange handler, `event.target` refers to the `<slot>` element itself. Calling `assignedElements()` (a native slot method) returns the array of actual DOM elements that were placed into that slot by the parent. If the array's length is `0`, it means nothing was passed in — so the component knows to hide that section.

```javascript
handleFooterChange(event) {
    this.hasFooter = event.target.assignedElements.length > 0;
}
```

### 6. Conditional CSS Classes via Getters
Each section's CSS class is computed through a **JavaScript getter property**, which LWC automatically re-evaluates whenever a tracked/reactive property (like `hasFooter`) changes:

```javascript
get footerClass() {
    return this.hasFooter
        ? 'slds-card__footer'
        : 'slds-hide';
}
```

* If the slot **has content** → apply the real SLDS class so it displays normally.
* If the slot **is empty** → apply `slds-hide` so the empty wrapper (`<footer>`, `<div>`, etc.) doesn't take up space or show an ugly empty box.

This is what makes the same component look different (and correctly sized) for Card 1 (all four sections), Card 2 (no footer), Card 3 (no actions), and Card 4 (title only).

### 7. `js-meta.xml` — `isExposed` and `targets`
* `isExposed: false` on `customLightningCard` → it's a private, internal building-block component; it cannot be dragged onto a Lightning page directly.
* `isExposed: true` + `<target>lightning__AppPage</target>` on `reusableComponentDemo` → this is the public-facing component that can be added to an App Page in Lightning App Builder.

## 🚀 How to Deploy / Try It Yourself

1. Clone this repo into your local **Salesforce DX project** under `force-app/main/default/lwc/`.
2. Authenticate to your Salesforce org using SFDX/SF CLI:
   ```bash
   sf org login web --alias myOrg
   ```
3. Deploy both components:
   ```bash
   sf project deploy start --source-dir force-app/main/default/lwc/customLightningCard
   sf project deploy start --source-dir force-app/main/default/lwc/reusableComponentDemo
   ```
4. Go to **Setup → Lightning App Builder**, create/edit an App Page, and drag the **Reusable Component Demo** component onto the page.
5. Activate the page and view it — you'll see four cards, each rendering a different combination of title/body/actions/footer, with empty sections auto-hidden.

## 🎯 Interview Questions & Answers (LWC – Slots, Reusability)

**Q1. What is a slot in LWC, and why is it useful?**
A slot is an HTML placeholder tag (`<slot></slot>`) inside a child component that allows a parent component to inject custom markup into it. It enables **composition** — building generic, reusable components (like cards, modals, layouts) whose exact content is decided by whoever uses them, rather than hardcoding content inside the component itself.

**Q2. What's the difference between a default slot and a named slot?**
A default (unnamed) slot (`<slot></slot>`) receives any child markup that doesn't have a `slot` attribute. A named slot (`<slot name="title"></slot>`) only receives markup explicitly tagged with a matching `slot="title"` attribute. A component can have only **one default slot**, but **multiple named slots**.

**Q3. How can a component detect whether content was passed into a slot?**
By listening to the `slotchange` event on the `<slot>` element and checking `event.target.assignedElements().length` (or `.assignedElements`, as commonly seen in LWC docs/examples) inside the handler. If the length is greater than 0, content was provided.

**Q4. When does the `slotchange` event fire?**
It fires when the component first renders (if slotted content exists) and any time the assigned nodes in that slot change — for example, if the parent conditionally adds/removes slotted content later.

**Q5. Why would you conditionally apply a CSS class (e.g., `slds-hide`) instead of conditionally rendering the whole block with `if:true`/`lwc:if`?**
Because the `<slot>` tag itself still needs to exist in the DOM for slotting to work correctly and for `slotchange` to keep firing. You can't wrap a `<slot>` in an `lwc:if` that depends on the slot's own content, since that would create a chicken-and-egg problem. Instead, the wrapping container is always rendered, but its CSS class toggles between a visible style and `slds-hide` based on whether the slot actually has content.

**Q6. What does light DOM vs shadow DOM have to do with slots?**
LWC components render in the Shadow DOM by default, and slots are the standard **Web Components / Shadow DOM API mechanism** for content projection — the same mechanism used natively in HTML custom elements. LWC just builds on top of this native browser feature.

**Q7. Why is `isExposed` set to `false` for `customLightningCard` but `true` for `reusableComponentDemo`?**
`customLightningCard` is an internal, reusable "building block" meant only to be used by other components in code (`<c-custom-lightning-card>`) — it has no reason to appear as a draggable component in App Builder. `reusableComponentDemo` is the outward-facing component meant to be placed on a Lightning page, so it's exposed and given a `target` (like `lightning__AppPage`).

**Q8. How is this pattern similar to Salesforce's own `lightning-card` base component?**
`lightning-card` also exposes `title`, `actions`, and `footer` named slots plus a default body slot, and it automatically renders (or hides) sections depending on what you provide — exactly the pattern rebuilt here from scratch to demonstrate how base components achieve that flexibility internally.

**Q9. Can slotted content have its own event listeners and interact with the parent, even though it's rendered inside a child's DOM structure?**
Yes — even though the slotted markup visually sits inside the child component's template, it is still owned and defined by the parent. Its event listeners, data bindings, and reactive properties belong to the parent's component instance, not the child's.

**Q10. What real-world scenarios call for this reusable-slot pattern?**
Generic card/panel layouts, modal/dialog components (header/body/footer), reusable list-item wrappers, custom accordion sections, or any UI "shell" component that needs to be visually consistent across an app while allowing flexible, page-specific content.
