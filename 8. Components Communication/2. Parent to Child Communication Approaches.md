# Parent to Child Communication Approaches

## 📌 Overview

In Lightning Web Components (LWC), components often need to communicate with each other.

When a **parent component needs to send data or instructions to a child component**, this is called:

> **Parent to Child Communication**

The data flow in LWC generally follows a **one-way data-flow model**:

```text
Parent
   |
   | Data / Method
   ↓
Child
```

Salesforce recommends that data flow from the parent to the child. The child should treat data received from its owner as read-only. If the child needs to request a change, it should communicate back to the parent using an event.

---

# 📚 Parent to Child Communication Approaches

The screenshot shows four approaches:

```text
                 Parent Component
                        |
        ┌───────────────┼────────────────┐
        ↓               ↓                ↓
Primitive Data    Non-Primitive Data   Action at Parent
        |               |                |
        └───────────────┼────────────────┘
                        ↓
                  Child Component

                        +

             Calling Child Method
                    from Parent
```

The four approaches are:

1. **Passing primitive data to child**
2. **Passing non-primitive data to child**
3. **Passing data to child on action at parent**
4. **Calling child method from parent**

---

# 1️⃣ Passing Primitive Data to Child

## 📖 Definition

> **Passing primitive data to child**

This means the parent component passes a primitive value such as a:

* String
* Number
* Boolean

to the child component.

The child exposes the property using:

```javascript
@api
```

and the parent provides the value through the child component's HTML.

Salesforce documents public properties decorated with `@api` as part of the child's public API.

---

# 🔹 What Are Primitive Data Types?

Common JavaScript primitive values include:

```text
String
Number
Boolean
Undefined
Null
BigInt
Symbol
```

In normal LWC parent-to-child examples, the most common values passed through public properties are:

```text
String
Number
Boolean
```

---

# 🧩 Example: Passing String

Suppose the parent contains:

```javascript
userName = 'Arun';
```

The parent wants to send this value to the child.

---

## Parent JavaScript

### parentComponent.js

```javascript
import { LightningElement } from 'lwc';

export default class ParentComponent extends LightningElement {

    userName = 'Arun';

}
```

---

## Parent HTML

### parentComponent.html

```html
<template>

    <lightning-card title="Parent Component">

        <div class="slds-p-around_medium">

            <c-child-component
                user-name={userName}>
            </c-child-component>

        </div>

    </lightning-card>

</template>
```

Notice:

```html
user-name={userName}
```

The JavaScript property is:

```javascript
userName
```

but the HTML attribute uses:

```text
user-name
```

Salesforce uses kebab-case for HTML attributes and camelCase for JavaScript properties.

---

## Child JavaScript

### childComponent.js

```javascript
import { LightningElement, api } from 'lwc';

export default class ChildComponent extends LightningElement {

    @api userName;

}
```

The important part is:

```javascript
@api userName;
```

This makes `userName` a **public property** of the child component.

---

## Child HTML

### childComponent.html

```html
<template>

    <lightning-card title="Child Component">

        <div class="slds-p-around_medium">

            <p>
                User Name: {userName}
            </p>

        </div>

    </lightning-card>

</template>
```

---

# 🔄 Data Flow

```text
Parent
  |
  | userName = "Arun"
  ↓
<c-child-component
    user-name={userName}>
  |
  ↓
Child
  |
  ↓
@api userName
```

The parent owns the data.

The child receives the data.

# ⭐ Important Interview Point

If a parent passes a public property:

```javascript
@api userName;
```

the child should generally **not modify the parent's value directly**.

Remember:

```text
Parent owns data
       ↓
Child receives data
       ↓
Child treats it as read-only
```

Salesforce explicitly recommends this one-way data-flow pattern to prevent unexpected side effects.

# 3️⃣ Passing Non-Primitive Data to Child

## 📖 Definition

> **Passing non-primitive data to child**

This means the parent passes complex data such as:

* Object
* Array

to the child component.

Example:

```javascript
user = {
    name: 'Arun',
    age: 25,
    city: 'Amritsar'
};
```

or:

```javascript
users = [
    {
        id: 1,
        name: 'Arun'
    },
    {
        id: 2,
        name: 'Rahul'
    }
];
```

---

# 🔹 Passing an Object

## Parent JavaScript

```javascript
import { LightningElement } from 'lwc';

export default class ParentComponent extends LightningElement {

    user = {
        name: 'Arun',
        age: 25,
        city: 'Amritsar'
    };

}
```

---

## Parent HTML

```html
<template>

    <c-child-component
        user={user}>
    </c-child-component>

</template>
```

---

## Child JavaScript

```javascript
import { LightningElement, api } from 'lwc';

export default class ChildComponent extends LightningElement {

    @api user;

}
```

---

## Child HTML

```html
<template>

    <lightning-card title="User Details">

        <div class="slds-p-around_medium">

            <p>Name: {user.name}</p>

            <p>Age: {user.age}</p>

            <p>City: {user.city}</p>

        </div>

    </lightning-card>

</template>
```

---

# 🔄 Object Data Flow

```text
Parent
  |
  | user object
  ↓
Child
  |
  ↓
@api user
```

---

# ⚠️ Important Rule for Objects and Arrays

Objects and arrays passed from a parent to a child should be treated as **read-only** by the child.

For example, suppose the parent sends:

```javascript
user = {
    name: 'Arun'
};
```

The child should not directly do:

```javascript
this.user.name = 'Rahul';
```

because the child does not own that object.

Salesforce documents that non-primitive values passed from an owner are read-only and recommends creating a shallow copy when the child needs its own mutable version.

---

# ✅ Correct Way to Modify an Object Locally

Instead of:

```javascript
this.user.name = 'Rahul';
```

create a copy:

```javascript
const updatedUser = {
    ...this.user,
    name: 'Rahul'
};
```

Then the child can work with its own copy:

```javascript
this.localUser = {
    ...this.user,
    name: 'Rahul'
};
```

# 🧠 Primitive vs Non-Primitive

| Primitive | Non-Primitive       |
| --------- | ------------------- |
| String    | Object              |

| Boolean   | Function            |

Primitive

Non-Primitive

# 4️⃣ Passing Data to Child on Action at Parent

## 📖 Definition

> **Passing data to child on action at parent**

This means the parent changes or prepares some data when the user performs an action, and that updated data is then passed to the child through a public property.

For example:

```text
Parent
   |
   | User clicks button
   ↓
Parent updates data
   |
   ↓
Child receives updated data
```

---

# 🧩 Example

Suppose the parent has:

```text
[Show Arun]
```

When the user clicks the button, the parent sets:

```javascript
userName = 'Arun';
```

and passes it to the child.

---

## Parent JavaScript

```javascript
import { LightningElement } from 'lwc';

export default class ParentComponent extends LightningElement {

    userName = '';

    handleClick() {

        this.userName = 'Arun';

    }

}
```

---

## Parent HTML

```html
<template>

    <lightning-card title="Parent Component">

        <div class="slds-p-around_medium">

            <lightning-button
                label="Show User"
                onclick={handleClick}>
            </lightning-button>

            <br />
            <br />

            <c-child-component
                user-name={userName}>
            </c-child-component>

        </div>

    </lightning-card>

</template>
```

---

## Child JavaScript

```javascript
import { LightningElement, api } from 'lwc';

export default class ChildComponent extends LightningElement {

    @api userName;

}
```

---

## Child HTML

```html
<template>

    <lightning-card title="Child Component">

        <div class="slds-p-around_medium">

            <p>
                Selected User: {userName}
            </p>

        </div>

    </lightning-card>

</template>
```

---

# 🔄 Execution Flow

Initially:

```text
userName = ''
```

The child displays:

```text
Selected User:
```

Then the user clicks:

```text
Show User
```

The parent executes:

```javascript
this.userName = 'Arun';
```

The value flows to the child:

```text
Parent
   |
   | userName = "Arun"
   ↓
Child
```

The child now displays:

```text
Selected User: Arun
```

---

# ⭐ Important Concept

The child does not need to know **how** the value was generated.

The child only needs:

```javascript
@api userName;
```

This provides a clean separation:

```text
Parent
   ↓
Business / Action Logic

Child
   ↓
Display / Child Logic
```

---

# 5️⃣ Calling Child Method From Parent

## 📖 Definition

> **Calling Child method from parent**

This means the parent directly invokes a **public JavaScript method** exposed by the child component.

The child exposes the method using:

```javascript
@api
```

Salesforce documentation explicitly describes `@api` public methods as a mechanism for an owner or parent to call JavaScript methods on child components.

---

# 🔹 Child Public Method

Suppose the child has:

```javascript
@api
showMessage() {

    console.log('Hello from Child');

}
```

Because the method has:

```javascript
@api
```

the parent can call it.

---

# 🧩 Complete Example

## Child JavaScript

### childComponent.js

```javascript
import { LightningElement, api } from 'lwc';

export default class ChildComponent extends LightningElement {

    @api
    showMessage() {

        console.log('Hello from Child Component');

    }

}
```

---

# Parent HTML

### parentComponent.html

```html
<template>

    <lightning-card title="Parent Component">

        <div class="slds-p-around_medium">

            <lightning-button
                label="Call Child Method"
                onclick={handleClick}>
            </lightning-button>

            <br />
            <br />

            <c-child-component>
            </c-child-component>

        </div>

    </lightning-card>

</template>
```

---

# Parent JavaScript

### parentComponent.js

```javascript
import { LightningElement } from 'lwc';

export default class ParentComponent extends LightningElement {

    handleClick() {

        const childComponent =
            this.template.querySelector('c-child-component');

        childComponent.showMessage();

    }

}
```

---

# 🔄 Execution Flow

```text
User clicks button
       ↓
Parent handleClick()
       ↓
querySelector()
       ↓
Child Component
       ↓
showMessage()
       ↓
Child method executes
```

---

# 🧠 Understanding `querySelector()`

This code:

```javascript
this.template.querySelector(
    'c-child-component'
);
```

finds the child component owned by the parent template.

Then:

```javascript
childComponent.showMessage();
```

calls the child's public method.

Salesforce's documentation uses this pattern to obtain a child component and invoke an `@api` public method.

---

# 🔹 Passing Data to Child Method

A public child method can also accept parameters.

## Child

```javascript
import { LightningElement, api } from 'lwc';

export default class ChildComponent extends LightningElement {

    @api
    showUser(name) {

        console.log('User Name:', name);

    }

}
```

Parent:

```javascript
handleClick() {

    const childComponent =
        this.template.querySelector('c-child-component');

    childComponent.showUser('Arun');

}
```

Flow:

```text
Parent
   |
   | showUser('Arun')
   ↓
Child
   |
   ↓
@api showUser(name)
```

Salesforce documents that public methods can accept parameters and return values.

---

# 🔹 Getting a Return Value

A public method can also return a value.

## Child

```javascript
@api
getUserName() {

    return 'Arun';

}
```

## Parent

```javascript
handleClick() {

    const childComponent =
        this.template.querySelector('c-child-component');

    const name =
        childComponent.getUserName();

    console.log(name);

}
```

Output:

```text
Arun
```

| ----------------------------- | ------------------------------------------- | --------------- |

| Passing non-primitive data    | Sends Object/Array                          | `@api` property |
| Passing data on parent action | Updates parent data and passes it           | `@api` property |
| Calling child method          | Parent directly invokes child functionality | `@api` method   |

# 🔥 `@api` — Most Important Concept

The `@api` decorator is imported from:

```javascript
import { LightningElement, api } from 'lwc';
```

It can expose:

### Public property

```javascript
@api name;
```

### Public method

```javascript
@api
resetForm() {
}
```

Salesforce identifies `@api` as the decorator used to expose public properties and methods.

---

# 📌 Public Property

Example:

```javascript
@api userName;
```

Parent:

```html
<c-child
    user-name={userName}>
</c-child>
```

This means:

```text
Parent
   ↓
Public Property
   ↓
Child
```

---

# 📌 Public Method

Example:

```javascript
@api
resetForm() {
    // logic
}
```

Parent:

```javascript
const child =
    this.template.querySelector('c-child');

child.resetForm();
```

This means:

```text
Parent
   ↓
Public Method Call
   ↓
Child
```

---

# 🆚 Public Property vs Public Method

| Public Property      | Public Method                |
| -------------------- | ---------------------------- |
| Uses `@api`          | Uses `@api`                  |
| Used to pass data    | Used to invoke functionality |
| Parent sets value    | Parent calls method          |
| Declarative          | Imperative                   |
| Example: `@api name` | Example: `@api resetForm()`  |

---

# ⚠️ Important: Property vs Method

Use a **public property** when the parent wants to provide data:

```javascript
@api recordId;
```

Use a **public method** when the parent wants the child to perform an action:

```javascript
@api
refreshData() {
}
```

Easy rule:

```text
Need to SEND DATA?
        ↓
    @api property


Need to TELL CHILD TO DO SOMETHING?
        ↓
    @api method
```

---

# 🔄 Declarative vs Imperative Parent-to-Child Communication

## Declarative

Passing a property:

```html
<c-child
    record-id={recordId}>
</c-child>
```

This is declarative.

---

## Imperative

Calling a child method:

```javascript
const child =
    this.template.querySelector('c-child');

child.refreshData();
```

This is imperative.

---

# 🧠 Why One-Way Data Flow Matters

LWC follows this principle:

```text
        Parent
           |
           ↓
        Child
```

Data flows down.

If the child needs to request a change:

```text
        Child
           |
           ↓
      Custom Event
           |
           ↓
        Parent
```

Then the parent changes its own data:

```text
Parent changes data
        |
        ↓
New data flows down
        |
        ↓
Child
```

Salesforce recommends this model to reduce complexity and unexpected side effects.

# ⚠️ Common Mistakes

## ❌ Mistake 1: Forgetting `@api`

Incorrect:

```javascript
userName;
```

The parent cannot use this as the child's public property.

Correct:

```javascript
@api userName;
```

---

# ❌ Mistake 2: Modifying Parent-Owned Object

Avoid:

```javascript
this.user.name = 'Rahul';
```

when `user` was passed from the parent.

Instead:

```javascript
this.localUser = {
    ...this.user,
    name: 'Rahul'
};
```

Salesforce documents parent-passed objects and arrays as read-only to the child.

---

# ❌ Mistake 3: Calling a Non-Public Child Method

Child:

```javascript
resetForm() {
}
```

The parent should not expect to call it as part of the child's public API.

Expose it:

```javascript
@api
resetForm() {
}
```

---

# ❌ Mistake 4: Incorrect `querySelector()`

Correct:

```javascript
this.template.querySelector(
    'c-child-component'
);
```

Avoid trying to select an element using an HTML `id` from the JavaScript.

Salesforce notes that IDs in LWC templates can be transformed, so `id` selectors aren't reliable for `querySelector()`.

---

# ❌ Mistake 5: Using `@api` Everywhere

Don't expose every internal property or method as public.

Only expose what the parent actually needs.

Good component design means:

```text
Internal Logic
     ↓
Private

Required API
     ↓
@api
```

# 🎤 Interview Questions

## 1. How do you communicate from parent to child in LWC?

### Answer

Parent-to-child communication is mainly done in two ways:

```text
1. Pass data using @api properties

2. Call child functionality using @api methods
```

Salesforce documents both public properties and public methods as parent-to-child communication mechanisms.

---

## 2. What is `@api`?

### Answer

`@api` is an LWC decorator used to expose a property or method as part of a component's public API.

Example:

```javascript
@api recordId;
```

or:

```javascript
@api
refreshData() {
}
```

---

## 3. How do you pass a String from parent to child?

### Answer

Parent:

```html
<c-child
    name={userName}>
</c-child>
```

Child:

```javascript
@api name;
```

---

## 4. How do you pass an Object from parent to child?

### Answer

Expose an `@api` property:

```javascript
@api user;
```

Parent:

```html
<c-child
    user={user}>
</c-child>
```

---

## 5. Can a child modify an object received from the parent?

### Answer

The child should treat the parent-owned object as read-only.

If the child needs to modify its own version, create a copy:

```javascript
this.localUser = {
    ...this.user
};
```

Salesforce explicitly documents this read-only behavior for non-primitive values passed from an owner.

---

## 6. What is the difference between primitive and non-primitive data?

### Answer

Primitive examples:

```text
String
Number
Boolean
```

Non-primitive examples:

```text
Object
Array
```

---

## 7. How can a parent call a child method?

### Answer

The child exposes the method with `@api`:

```javascript
@api
resetForm() {
}
```

The parent gets the child component and calls the method:

```javascript
const child =
    this.template.querySelector('c-child');

child.resetForm();
```

Salesforce documents `querySelector()` as a way to access the child component and invoke its public method.

---

## 8. Why do we use `querySelector()`?

### Answer

`querySelector()` allows the parent to obtain the child component instance from its template so that the parent can call the child's public `@api` method.

---

## 9. Can an `@api` method accept parameters?

### Answer

Yes.

Child:

```javascript
@api
showMessage(message) {

    console.log(message);

}
```

Parent:

```javascript
child.showMessage('Hello');
```

---

## 10. Can an `@api` method return a value?

### Answer

Yes.

Child:

```javascript
@api
getName() {

    return 'Arun';

}
```

Parent:

```javascript
const name = child.getName();
```

---

## 11. What is the difference between `@api` property and `@api` method?

### Answer

`@api` property is used to pass data.

```javascript
@api recordId;
```

`@api` method is used to expose functionality.

```javascript
@api
refreshData() {
}
```

---

## 12. What is one-way data flow in LWC?

### Answer

Data should generally flow from:

```text
Parent → Child
```

If the child needs to request a change, it sends an event:

```text
Child → Event → Parent
```

The parent owns the data and updates it. The updated value then flows back to the child.

---

## 13. What is the difference between parent-to-child and child-to-parent communication?

### Answer

### Parent → Child

Use:

```text
@api property
@api method
```

### Child → Parent

Use:

```text
CustomEvent
dispatchEvent()
```

Salesforce's event documentation explicitly recommends events for communication up the component containment hierarchy.

---

## 14. Can we use CustomEvent for parent-to-child communication?

### Answer

It is not the normal approach.

For parent-to-child communication, use:

```text
@api property
```

or:

```text
@api method
```

Custom events are primarily used for communication upward from child to parent.

---

## 15. What happens when the parent changes an `@api` property?

### Answer

If the public property is used by the child, the child's UI can react to the new value and rerender.

Salesforce documents public properties as reactive when used in the template.

# ⭐ Most Important Interview Points

Remember these points:

```text
1. Parent → Child communication uses @api.

2. @api can expose a public property.

3. @api can expose a public method.

4. Primitive data can be passed using @api properties.

5. Objects and arrays can also be passed using @api.

6. Parent owns the data.

7. Child should treat parent-provided data as read-only.

8. Create a copy if the child needs to modify an object/array locally.

9. Parent can call a child @api method using querySelector().

10. @api methods can accept parameters.

11. @api methods can return values.

12. Child → Parent normally uses CustomEvent.

13. LWC follows one-way data flow.

14. Data flows down.

15. Events communicate changes upward.

16. Don't expose unnecessary properties/methods with @api.
```

## 🎯 One-Minute Interview Revision

> **Parent-to-child communication in LWC is primarily achieved using public properties and public methods exposed with `@api`. Primitive values such as strings, numbers, and booleans, as well as non-primitive values such as objects and arrays, can be passed through `@api` properties. When the parent needs to instruct the child to perform an action, the child can expose an `@api` method that the parent calls through the child component reference. LWC follows one-way data flow, so parent-owned data should be treated as read-only by the child.**

### Easy Formula

```text
Parent → Child

Data
  ↓
@api Property

Action
  ↓
@api Method
```

And remember the opposite direction:

```text
Child → Parent
      ↓
CustomEvent
      ↓
dispatchEvent()
```

That distinction—**`@api` for parent-to-child and `CustomEvent` for child-to-parent**—is one of the most frequently asked LWC communication concepts in Salesforce interviews.
