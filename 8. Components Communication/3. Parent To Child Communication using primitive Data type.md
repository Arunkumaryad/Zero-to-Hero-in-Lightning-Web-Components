# Parent To Child Communication Using Primitive Data Type

## 📌 Overview

In Lightning Web Components (LWC), a parent component can send data to a child component.

This is called:

> **Parent to Child Communication**

In this example, we specifically learn how to pass **primitive data types** from a parent component to a child component using the **`@api` decorator**.

The basic flow is:

```text
Parent Component
       |
       | Primitive Data
       ↓
Child Component
```

Salesforce recommends one-way data flow in LWC:

```text
Parent → Child
```

The parent owns the data, and the child consumes the data. The child should generally treat a value received from its parent as read-only. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-data-flow.html))

# 1️⃣ `@api` Decorator

## 📖 Definition From the Screenshot

The screenshot gives the following points:

> **1. To make a field/property or method public, decorate it with @api decorator.**

> **2. When we want to expose the property we decorate the field with @api.**

> **3. An owner component that uses the component in its HTML markup can access the component's public properties via HTML attributes.**

> **4. Public properties are reactive in nature and if the value of the property changes the component's template re-renders.**

These are the key points to remember about `@api`.

# 🧠 What is `@api`?

`@api` is an LWC decorator used to expose a property or method as part of a component's **public API**.

Import it from:

```javascript
import { LightningElement, api } from 'lwc';
```

Example:

```javascript
import { LightningElement, api } from 'lwc';

export default class Child extends LightningElement {

    @api username;

}
```

Here:

```javascript
@api username;
```

means that `username` is publicly accessible to the parent component.

---

# 🔹 Without `@api`

Suppose the child has:

```javascript
username;
```

This is an internal/private field.

The parent cannot directly provide a value to it as a public component property.

---

# 🔹 With `@api`

```javascript
@api username;
```

Now the field becomes part of the child's public API.

The parent can provide a value:

```html
<c-child
    username={userName}>
</c-child>
```

# 🧠 What Does "Public Property" Mean?

A property normally belongs to the component that declares it.

For example:

```javascript
name;
```

is an internal field.

But:

```javascript
@api name;
```

makes it part of the component's public API.

Therefore:

```text
name
 ↓
Private/Internal

@api name
 ↓
Public
```

Salesforce defines fields decorated with `@api` as publicly available properties to component consumers. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/js-props-intro.html))

# 1️⃣0️⃣ HTML Attribute → JavaScript Property

This is a very important concept.

Suppose the parent writes:

```html
<c-child-comp
    card-heading={cardHeading}>
</c-child-comp>
```

The HTML attribute is:

```text
card-heading
```

The JavaScript property is:

```javascript
cardHeading
```

The mapping is:

```text
HTML                    JavaScript

card-heading     →      cardHeading

is-valid         →      isValid

user-name        →      userName

record-id        →      recordId
```

Salesforce explicitly documents this camelCase-to-kebab-case mapping. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/reactivity-public.html))

---

# 📌 Why Does LWC Use Kebab Case in HTML?

HTML attributes conventionally use dash-separated names.

JavaScript uses camelCase.

Therefore:

```javascript
cardHeading
```

becomes:

```html
card-heading
```

This is very common in LWC.

When passing Boolean values dynamically, prefer:



For static examples, be careful with HTML attribute semantics and type conversion. In real applications, dynamic property binding is preferable when the value comes from JavaScript.

# 1️⃣2️⃣ One-Way Data Flow

LWC follows:

```text
Parent
   |
   ↓
Child
```

The parent owns the data.

The child receives it.

The child should not directly change the parent-owned value.

Salesforce's data-flow guidance explicitly states that data should flow in one direction from parent to child and that a component should treat values passed to it as read-only. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-data-flow.html))

---

# 🔄 What If Child Wants to Change the Value?

Suppose:

```text
Parent
  |
  | name = "Arun"
  ↓
Child
```

The child should not try to modify the parent's property directly.

Instead:

```text
Child
  |
  | CustomEvent
  ↓
Parent
  |
  | Changes its own data
  ↓
Child receives new value
```

So:

```text
Data Down
Events Up
```

This is a fundamental LWC communication principle. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-data-flow.html))

# ⚠️ Important: Don't Use `@track` for This

You may see old LWC examples using:

```javascript
@track
```

for basic reactivity.

For normal fields, LWC has had automatic reactivity since Spring '20. You generally don't need `@track` for a primitive field like:

```javascript
message = 'Hello';
```

Salesforce's current documentation states that fields are reactive when used in the template, while `@track` is still relevant for observing internal changes to object properties or array elements in specific cases. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/reference-decorators))

For this example:

```javascript
@api message;
@api number;
@api isValid;
```

you do **not** need `@track`.

# 🚨 Common Mistakes

## ❌ Mistake 1 — Forgetting `@api`

Incorrect:

```javascript
message;
```

Correct:

```javascript
@api message;
```

Without `@api`, the field is not part of the child's public API.

---

# ❌ Mistake 2 — Incorrect Attribute Name

Incorrect:

```html
<c-child
    cardHeading={cardHeading}>
</c-child>
```

Correct:

```html
<c-child
    card-heading={cardHeading}>
</c-child>
```

Use:

```text
HTML → kebab-case
JavaScript → camelCase
```

---

# ❌ Mistake 3 — Trying to Change Parent Data From Child

Avoid treating:

```javascript
@api message;
```

as the child's own state.

The parent owns the public property.

If a child needs a change, communicate upward using an event.

---

# ❌ Mistake 4 — Confusing `@api` With `@track`

`@api`:

```text
Makes a property public
```

`@track`:

```text
Controls observation of internal object/array mutations in specific cases
```

They solve different problems.

---

# ❌ Mistake 5 — Using Complex Objects When Simple Values Are Enough

Salesforce recommends using primitive properties where practical because they clearly define the component's data shape and reduce coupling. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-data-flow.html))

Instead of:

```javascript
@api user;
```

when only the name is needed, consider:

```javascript
@api userName;
```

This makes the child's API clearer.

# 🎤 Interview Questions

## 1. What is `@api` in LWC?

### Answer

`@api` is an LWC-specific decorator used to expose a field or method as part of a component's public API.

Example:

```javascript
@api userName;
```

Salesforce documents `@api` as the decorator for public properties and public methods. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/reference-decorators))

---

## 2. How do you pass data from parent to child?

### Answer

Expose a property in the child using `@api`, then provide the value from the parent markup.

Child:

```javascript
@api message;
```

Parent:

```html
<c-child
    message={message}>
</c-child>
```

---

## 3. What is a public property?

### Answer

A property decorated with `@api` is a public property.

Example:

```javascript
@api recordId;
```

It becomes part of the component's public API and can be set by the component that owns/uses the child. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/reactivity-public.html))

---

## 4. Are `@api` properties reactive?

### Answer

Yes.

If a public property is used in the component's template and its value changes, the component can rerender.

Example:

```javascript
@api number;
```

If the value changes from:

```text
25 → 50
```

the template can update accordingly. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/reactivity-public.html))

---

## 5. What is the difference between an HTML attribute and a JavaScript property?

### Answer

HTML generally uses attributes:

```html
card-heading
```

JavaScript uses properties:

```javascript
cardHeading
```

LWC maps the kebab-case HTML attribute to the camelCase JavaScript public property. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/reactivity-public.html))

## 11. What is one-way data binding in LWC?

### Answer

Data generally flows from:

```text
Parent → Child
```

The parent owns the value.

If the child wants to request a change, it sends an event to the parent.

The parent then changes its data, and the updated value flows back down. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-data-flow.html))

---

## 12. Can the child modify an `@api` property?

### Answer

The child should generally not modify a value owned by the parent.

The recommended pattern is:

```text
Child
  ↓
Event
  ↓
Parent
  ↓
Update Data
  ↓
Child
```

This maintains one-way data flow. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-data-flow.html))

---

## 13. What is the difference between `@api` and `@track`?

### Answer

`@api` is used to expose a property or method publicly.

`@track` is related to observing internal changes to object properties or array elements in specific cases.

Basic fields are reactive by default in modern LWC. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/reference-decorators))

---

## 14. Why is primitive data often preferred for component APIs?

### Answer

Primitive properties make the component's API explicit and easy to understand.

For example:

```javascript
@api firstName;
@api lastName;
@api age;
```

is clearer than:

```javascript
@api user;
```

where the child must depend on a particular object structure.

Salesforce recommends primitive properties where practical for this reason. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-data-flow.html))

---

## 15. What happens when a public property changes?

### Answer

If the public property is used by the template, LWC reevaluates the template and rerenders the component with the new value. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/reactivity-public.html))

# 🔥 One-Minute Interview Answer

If the interviewer asks:

> **How do you pass primitive data from parent to child in LWC?**

Answer:

> In LWC, parent-to-child communication can be implemented by exposing a public property in the child using the `@api` decorator. The parent then passes the value to the child through the child component's HTML attribute. Primitive values such as String, Number, and Boolean can be passed this way. The data flow is one-way, from parent to child, and public properties used in the child's template are reactive. The child should treat the parent-owned value as read-only. ([developer.salesforce.com](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-data-flow.html))

Example:

```javascript
// Child
import { LightningElement, api } from 'lwc';

export default class ChildComp extends LightningElement {

    @api message;
    @api number;
    @api isValid;

}
```

```html
<!-- Parent -->
<c-child-comp
    message="Hello"
    number={number}
    is-valid={isValid}>
</c-child-comp>
```
