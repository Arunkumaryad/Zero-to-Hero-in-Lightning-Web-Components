# Component Communication Using PubSub (LWC)

This project is part of a **Lightning Web Components (LWC)** learning series. It demonstrates how to communicate between **Independent (unrelated) Components** — components that do **not** share a parent-child relationship — using the **PubSub (Publish-Subscribe) pattern**.

---

## 📌 Concept Overview

There are **two ways to communicate between Independent Components** in LWC:

1. **PubSub**
2. **Lightning Message Service (LMS)**

> **NOTE:** Use the PubSub approach only if **Lightning Message Service does not serve your purpose**. PubSub is an **old technique** to communicate with independent components in LWC — Salesforce now recommends **Lightning Message Service (LMS)** for new development.

### Why PubSub? (Parent-Child vs. Independent Components)

For **Parent-Child** components, LWC already provides built-in mechanisms:
- **Parent to Child** → using `@api` properties.
- **Child to Parent** → using Custom Events.

But when two components are **Independent** — i.e., placed separately on a page with no direct parent-child relationship — neither of these mechanisms works, because neither component has a reference to the other. This is where a **PubSub Module** comes in: it acts as a **middleman** that both components can talk to.

```
┌───────────────────────────────── Page ─────────────────────────────────┐
│                                                                          │
│  ┌────────────────────────────┐                                        │
│  │      Parent Component        │                                        │
│  │                              │        PubSub Module                  │
│  │  Parent to Child ↓  ↑ Child  │  ─────────────────────────────►        │
│  │                    to Parent │                              ┌────────────────┐
│  │  ┌────────────────────┐     │                              │  Independent    │
│  │  │   Child Component    │     │                              │   Component     │
│  │  └────────────────────┘     │                              └────────────────┘
│  └────────────────────────────┘                                        │
└──────────────────────────────────────────────────────────────────────┘
```

**In simple words:** A **Parent Component** (with its own Child Component inside it) needs to send a message to a completely separate, **Independent Component** elsewhere on the page. Since they have no direct relationship, both components import a shared **`pubsub` module**. One component **publishes** an event with data, and the other component **subscribes** to that same event name to receive the data.

## 🧩 The PubSub Module

### `pubsub.js`

This is the **core utility** — a plain, framework-agnostic JavaScript module (not itself an LWC component) that maintains an internal store of event subscriptions, and exposes three functions: `subscribe`, `unsubscribe`, and `publish`.

```js
const store = {};

/**
 *subscribe a callback for an event.
 *@param {string} eventName - Name of the event to listen for.
 *@param {function} callback - function to invoked when said event is fired.
 */

const subscribe = (eventName, callback) => {
    if (!store[eventName]) {
        store[eventName] = new Set();
    }
    store[eventName].add(callback);
};

/**
 *unsubscribe a callback for an event.
 *@param {string} eventName - Name of the event to unsubscribe for.
 *@param {function} callback - function to unsubscribe.
 */
const unsubscribe = (eventName, callback) => {
    if (store[eventName]) {
        store[eventName].delete(callback);
    }
};

/**
 *publish an event to listeners.
 *@param {string} eventName - Name of the event to publish.
 *@param {*} payload - Payload of the event to publish.
 */
const publish = (eventName, payload) => {
    if (store[eventName]) {
        store[eventName].forEach(callback => {
            try {
                callback(payload);
            } catch (error) {
                console.error(`Error occurred while invoking callback for event '${eventName}':`, error);
            }
        });
    }
};

export default {
    subscribe,
    unsubscribe,
    publish
};
```

**Explanation of each part:**

- **`const store = {}`** — an in-memory object that acts as a registry. Each key is an **event name**, and each value is a `Set` of **callback functions** subscribed to that event.
- **`subscribe(eventName, callback)`** — registers a `callback` function to be invoked whenever the named event is published.
  - If no subscribers exist yet for `eventName`, it creates a new `Set` for it (a `Set` is used so the same callback can't accidentally be added twice).
  - Adds the `callback` to that event's subscriber set.
- **`unsubscribe(eventName, callback)`** — removes a specific `callback` from an event's subscriber set, so it will no longer be invoked when that event is published. Important for cleanup (e.g., in `disconnectedCallback()`), to avoid memory leaks or stale references.
- **`publish(eventName, payload)`** — invokes **every** subscribed callback for the given `eventName`, passing them the `payload` (the data being sent).
  - Wrapped in a `try/catch` so that if one subscriber's callback throws an error, it doesn't stop the rest of the subscribers from also receiving the event — the error is simply logged to the console.
- **`export default { subscribe, unsubscribe, publish }`** — exposes these three functions as a single default-exported object, so any component can `import pubsub from 'c/pubsub'` and call `pubsub.subscribe(...)`, `pubsub.publish(...)`, etc.

## 🧩 Publisher Component — Component A

### `pubsubComponentA.html`

```html
<template>
    <lightning-card title="Pub Sub Component A">
        <div class="slds-p-around_medium">
            <lightning-input type="text" onkeyup={handleKeyUp}
            class="slds-m-bottom_medium"></lightning-input>
            <lightning-button variant="brand" onclick={handleClick}
            label="Publish"></lightning-button>
        </div>
    </lightning-card>
</template>
```

- A `lightning-input` captures whatever the user types, using `onkeyup={handleKeyUp}`.
- A **Publish** button triggers `handleClick`, which sends the typed message out through the PubSub module.

### `pubsubComponentA.js`

```js
import { LightningElement } from 'lwc';
import pubsub from 'c/pubsub';

export default class PubsubComponentA extends LightningElement {
    message;

    handleKeyUp(event) {
        this.message = event.target.value;
    }

    handleClick(event) {
        pubsub.publish('componentA', this.message);
    }
}
```

- `import pubsub from 'c/pubsub'` — imports the shared PubSub utility module (note: the module is imported using the `c/` namespace, just like any other LWC component/module reference).
- `handleKeyUp(event)` — updates the reactive `message` property every time the user types in the input field.
- `handleClick(event)` — calls `pubsub.publish('componentA', this.message)`, which:
  - Uses `'componentA'` as the **event name**.
  - Sends `this.message` (whatever the user typed) as the **payload**.
  - This triggers every callback that has subscribed to `'componentA'` — passing them the current message.

### `pubsubComponentA.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
```

- `isExposed>true</isExposed>` makes the component available for placement in tools like the Lightning App Builder.

## 🧩 Subscriber Component — Component B

### `pubsubComponentB.html`

```html
<template>
    <lightning-card title="Pub Sub Component A">
        <div class="slds-p-around_medium">
            <h1>Message Received - {message}</h1>
        </div>
    </lightning-card>
</template>
```

- Displays the message received from Component A, bound reactively via `{message}`.

### `pubsubComponentB.js`

```js
import { LightningElement } from 'lwc';
import pubsub from 'c/pubsub';

export default class PubsubComponentB extends LightningElement {
    message;

    connectedCallback() {
        this.callSubscriber();
    }

    callSubscriber() {
        pubsub.subscribe('componentA', (message) => {
            this.message = message;
        });
    }
}
```

- `connectedCallback()` — a **built-in LWC lifecycle hook** that runs automatically as soon as the component is inserted into the DOM. It's used here to set up the subscription as early as possible.
- `callSubscriber()` — calls `pubsub.subscribe('componentA', (message) => { this.message = message; })`:
  - Subscribes to the `'componentA'` event (the exact same event name that Component A publishes to).
  - The callback function receives whatever `payload` is published, and assigns it to `this.message`.
  - Since `message` is a reactive property, updating it automatically re-renders the `<h1>Message Received - {message}</h1>` line in the template.

### `pubsubComponentB.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__AppPage</target>
    </targets>
</LightningComponentBundle>
```

Same structure as Component A's metadata — exposes Component B for use on a Lightning App Page.

## ⚙️ How It Works (Step-by-Step)

1. Both **`pubsubComponentA`** and **`pubsubComponentB`** are placed independently on the same **Lightning App Page** (with no parent-child relationship between them).
2. When **Component B** is inserted into the DOM, its `connectedCallback()` fires automatically, which calls `callSubscriber()`.
3. `callSubscriber()` calls `pubsub.subscribe('componentA', callback)`, registering Component B's callback function in the shared `pubsub.js` module's internal `store`, under the key `'componentA'`.
4. The user types a message into **Component A**'s input field. Every keystroke updates `this.message` via `handleKeyUp`.
5. The user clicks the **Publish** button on Component A, triggering `handleClick`, which calls `pubsub.publish('componentA', this.message)`.
6. Inside `pubsub.js`, the `publish` function looks up all callbacks registered under `'componentA'` in its `store`, and invokes each one — passing `this.message` as the `payload`.
7. Component B's previously registered callback runs, setting `this.message = message` (the payload received).
8. Since `message` is reactive, Component B's template automatically re-renders, updating the `<h1>` to show **"Message Received - `<the typed message>`"**.

## 🔑 Key Takeaways

| Concept | Purpose |
|---|---|
| PubSub pattern | Enables communication between **independent** components with no parent-child relationship |
| `store` object (inside `pubsub.js`) | An in-memory registry mapping event names to sets of subscriber callbacks |
| `subscribe(eventName, callback)` | Registers interest in an event; the callback runs whenever that event is published |
| `unsubscribe(eventName, callback)` | Removes a previously registered callback, useful for cleanup |
| `publish(eventName, payload)` | Notifies all subscribers of an event, passing them the given payload |
| `connectedCallback()` | LWC lifecycle hook used here to subscribe as soon as the component is rendered |
| `c/pubsub` import | How components reference the shared module, using LWC's standard `c/` namespace |

---

## 🆚 PubSub vs. Lightning Message Service (LMS)

| Aspect | PubSub | Lightning Message Service (LMS) |
|---|---|---|
| Status | Older, custom-built technique | Modern, Salesforce-recommended standard |
| Setup | Requires manually creating and maintaining a `pubsub.js` utility module | Uses a declarative **Lightning Message Channel** metadata definition |
| Works across | LWC-to-LWC only (within the same DOM/page context) | LWC and Aura components, and even across the same DOM realm boundaries more robustly |
| Recommended use | Only when LMS doesn't fit your use case | Default choice for new independent-component communication |

## 💬 Interview Questions on This Topic

1. **What are the two ways to communicate between independent (unrelated) components in LWC?**
   PubSub and Lightning Message Service (LMS).

2. **Which of the two is Salesforce's recommended, modern approach — and why might you still use the other?**
   Lightning Message Service (LMS) is the recommended modern approach. PubSub, being an older technique, should only be used if LMS doesn't serve the specific purpose needed.

3. **Why can't `@api` properties or custom events be used to communicate between independent components?**
   `@api` properties (parent-to-child) and custom events (child-to-parent) both rely on a direct parent-child relationship in the component tree. Independent components have no such relationship, so neither mechanism can reach the other component.

4. **What data structure does the `pubsub.js` module use internally to track subscriptions, and why?**
   A plain object (`store`) where each key is an event name and each value is a `Set` of callback functions. A `Set` is used because it automatically prevents duplicate subscriptions of the exact same callback.

5. **What are the three core functions exposed by the PubSub module, and what does each do?**
   `subscribe(eventName, callback)` registers a callback for an event; `unsubscribe(eventName, callback)` removes a previously registered callback; `publish(eventName, payload)` invokes all callbacks registered for an event, passing them the payload.

6. **Why is the `publish` function's callback invocation wrapped in a `try/catch` block?**
   So that if one subscriber's callback throws an error, it doesn't prevent the other subscribers from still receiving and processing the published event — the error for that one callback is simply logged.

7. **Why does Component B call `pubsub.subscribe()` inside `connectedCallback()` rather than somewhere else?**
   `connectedCallback()` is a lifecycle hook that fires as soon as the component is inserted into the DOM, ensuring the subscription is set up early — before any event could potentially be published and missed.

8. **What happens if `publish()` is called for an event name that has no subscribers?**
   Nothing happens — the `publish` function checks `if (store[eventName])` first, and if no subscribers are registered for that event name, it simply does nothing (no error is thrown).

9. **Why is it important to call `unsubscribe()` when a component is destroyed (e.g., in `disconnectedCallback()`)?**
   To prevent memory leaks and avoid calling callback functions on components that no longer exist in the DOM — an unsubscribed component's stale callback could otherwise still be invoked and potentially throw errors or behave unexpectedly.

10. **In this example, what is the "event name" used to connect Component A and Component B, and why must it match exactly?**
    The event name is `'componentA'`. It must match exactly between the `publish()` call in Component A and the `subscribe()` call in Component B, because the `store` object uses this string as the key to look up which callbacks to invoke — a mismatch means the subscriber would simply never receive the message.

## 🚀 How to Deploy

1. Create the PubSub utility module and both components using the Salesforce CLI or VS Code Salesforce Extension:
   ```
   sfdx force:lightning:component:create --type lwc --componentname pubsub
   sfdx force:lightning:component:create --type lwc --componentname pubsubComponentA
   sfdx force:lightning:component:create --type lwc --componentname pubsubComponentB
   ```
2. Copy the respective JS/HTML/meta.xml content into the generated files.
3. Deploy to your Salesforce org:
   ```
   sfdx force:source:deploy -p force-app/main/default/lwc/pubsub
   sfdx force:source:deploy -p force-app/main/default/lwc/pubsubComponentA
   sfdx force:source:deploy -p force-app/main/default/lwc/pubsubComponentB
   ```
4. Add both `pubsubComponentA` and `pubsubComponentB` to the **same Lightning App Page** via **Lightning App Builder** (they don't need to be nested — placing them independently anywhere on the page demonstrates the pattern).

---

## 📝 Notes

- The `pubsub.js` module itself is **not** an LWC component (it has no `.html` file) — it's a plain JavaScript utility module, imported and shared across components.
- Since PubSub relies on a shared in-memory `store`, all communicating components must be part of the **same page/DOM session** — it does not persist data or work across page reloads.
- For new projects, evaluate **Lightning Message Service (LMS)** first, and fall back to this PubSub pattern only if LMS doesn't meet your specific requirements.
