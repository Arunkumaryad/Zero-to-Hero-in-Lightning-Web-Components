# Child to Parent Communication Using Simple Event (LWC)

This project is part of a **Lightning Web Components (LWC)** learning series. It demonstrates how a **Child Component can notify its Parent Component using a Simple Custom Event** (an event with **no data** attached) — implemented here through a practical **Show/Hide Modal** example.

---

## 📌 Concept Overview: Create and Dispatch Events

To communicate from child to parent, LWC uses the browser's native **`CustomEvent`** API along with the **`dispatchEvent()`** method. Together these are the foundation of every child-to-parent communication pattern in LWC.

### `CustomEvent` Syntax

```js
new CustomEvent('event name', { bubbles: false, composed: false, details: null })
```

These are the **default values** for every `CustomEvent` you create — by default, an event does **not** bubble, is **not** composed, and carries **no** details/data.

Example used in this project:

```js
new CustomEvent('show', { bubbles: true, details: 'hello' })
```

Here:
1. The event name is defined as `'show'`.
2. By default `bubbles` and `composed` are `false`, but we've explicitly made `bubbles: true` for event bubbling.
3. `detail` is used to pass data along with the event — in this example, the string `'hello'` is passed.

### `dispatchEvent` Syntax

```js
EventTarget.dispatchEvent(eventCreated)
```

Example used in this project:

```js
this.dispatchEvent(new CustomEvent('show', { bubbles: true, details: 'hello' }))
```

Here:
1. `this` refers to the `EventTarget` — i.e., the component firing the event.
2. `dispatchEvent()` triggers/fires the `CustomEvent` so that any listener attached to this component (typically the parent) is notified.

### Event Name Naming Conventions

- Only **String** values are allowed as event names.
- **No uppercase letters** allowed.
- **No spaces** allowed.
- Use **underscores** to separate words (e.g., `record_selected`, not `Record Selected`).

## 🧩 Component Code

### 1. Parent Component — `childToParentComponent.html`

The parent renders a **Show Modal** button. When clicked, it conditionally displays the child modal component using `template if:true`. The child's `close` event is listened to using `onclose={handleClose}`.

```html
<template>
    <lightning-card title="Child To Parent Communication">
        <div class="slds-p-around_medium">
            <lightning-button variant="brand" label="Show Modal" onclick={handleClick}></lightning-button>
            <template if:true={showModal}>
                <c-chil-to-parent-modal-component
                    onclose={handleClose}></c-chil-to-parent-modal-component>
            </template>
        </div>
    </lightning-card>
</template>
```

### 2. Parent Component — `childToParentComponent.js`

```js
import { LightningElement } from 'lwc';

export default class ChildToParentComponent extends LightningElement {
    showModal = false;

    handleClick(event) {
        this.showModal = true;
    }

    handleClose(event) {
        this.showModal = false;
    }
}
```

- `showModal` is a **reactive property** that controls whether the child modal is rendered (`template if:true={showModal}`).
- `handleClick` sets `showModal = true`, which renders the child modal component.
- `handleClose` is the listener for the child's `close` event — when the child fires `close`, this method runs and sets `showModal = false`, hiding the modal again.

### 3. Parent Component Metadata — `childToParentComponent.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__AppPage</target>
    </targets>
</LightningComponentBundle>
```

- `isExposed>true</isExposed>` makes the component available for use outside its own bundle, e.g., in the Lightning App Builder.
- `<target>lightning__AppPage</target>` specifically exposes this component so it can be dropped onto a **Lightning App Page**.

### 4. Child Component — `chilToParentModalComponent.html`

This is a standard **SLDS (Salesforce Lightning Design System) modal** markup, with an `Ok` button used to close the modal.

```html
<template>
    <section role="dialog" tabindex="-1" aria-modal="true" aria-labelledby="modal-heading-01"
        class="slds-modal slds-fade-in-open slds-modal_medium">
        <div class="slds-modal__container">

            <div class="slds-modal__header">
                <h1 id="modal-heading-01" class="slds-modal__title slds-hyphenate" tabindex="-1">
                    Child Modal</h1>
            </div>
            <div class="slds-modal__content slds-p-around_medium" id="modal-content-id-1">
                <p>Loaded Successfully.</p>
            </div>
            <div class="slds-modal__footer">
                <button class="slds-button slds-button_brand" onclick={handleClick}>Ok</button>
            </div>
        </div>
    </section>
    <div class="slds-backdrop slds-backdrop_open" role="presentation"></div>
</template>
```

- `role="dialog"`, `aria-modal="true"`, and `aria-labelledby` are accessibility (a11y) attributes that mark this markup as a proper modal dialog for screen readers.
- The `slds-backdrop` div renders the dimmed background behind the modal.
- The **Ok** button's `onclick` is wired to `handleClick` in the child's JS.

### 5. Child Component — `chilToParentModalComponent.js`

```js
import { LightningElement } from 'lwc';

export default class ChilToParentModalComponent extends LightningElement {
    handleClick(event) {
        const myEvent = new CustomEvent('close');
        this.dispatchEvent(myEvent);
    }
}
```

- When the **Ok** button is clicked, `handleClick` runs.
- `new CustomEvent('close')` creates a simple event named `close` — with **no data** attached (using all default values: `bubbles: false`, `composed: false`, `detail: null`).
- `this.dispatchEvent(myEvent)` fires this event, which is caught by the parent's `onclose={handleClose}` listener declared on the `<c-chil-to-parent-modal-component>` tag.

---

## ⚙️ How It Works (Step-by-Step)

1. The user clicks the **Show Modal** button on the parent component.
2. This runs `handleClick` in the parent, setting `showModal = true`.
3. Because `showModal` is now `true`, the `<template if:true={showModal}>` block renders, which displays the `<c-chil-to-parent-modal-component>` child component (the modal).
4. Inside the child, when the user clicks the **Ok** button, `handleClick` in the child's JS runs.
5. The child creates a simple `CustomEvent` named `'close'` (no data, default options) and fires it via `this.dispatchEvent(myEvent)`.
6. Because the parent declared `onclose={handleClose}` on the child's tag, the parent's `handleClose` method automatically executes when the `close` event reaches it.
7. `handleClose` sets `showModal = false`, which removes the child modal component from the DOM (since the `template if:true` condition is now false).

## 🔑 Key Takeaways

| Concept | Purpose |
|---|---|
| `new CustomEvent('event name', options)` | Creates a custom DOM event with a name and optional configuration (`bubbles`, `composed`, `detail`) |
| Default `CustomEvent` values | `bubbles: false`, `composed: false`, `detail: null` |
| `this.dispatchEvent(event)` | Fires the event from the component where `this` is the `EventTarget` |
| `on<eventname>` in parent template | How the parent listens for the child's event (e.g., `close` → `onclose`) |
| `template if:true={property}` | Conditionally renders a block of markup (used here to show/hide the modal) |
| Event naming rules | Lowercase only, no spaces, use underscores for multi-word names |

## 💬 Interview Questions on This Topic

1. **What is a `CustomEvent` in LWC, and where does it come from?**
   `CustomEvent` is a standard, native browser/DOM API (not something LWC-specific) that LWC reuses to let components fire custom events that other components can listen to.

2. **What are the default values when you create a `new CustomEvent()`?**
   `bubbles: false`, `composed: false`, and `detail: null` — meaning by default, the event does not propagate up the DOM, does not cross shadow DOM boundaries, and carries no data.

3. **What does `dispatchEvent()` do, and what does `this` refer to when calling it?**
   `dispatchEvent()` triggers/fires the event so listeners can react to it. `this` refers to the `EventTarget` — i.e., the component instance that is dispatching the event.

4. **What are the naming rules for custom events in LWC?**
   Event names must be strings, all lowercase, contain no spaces, and use underscores to separate multiple words.

5. **How does the parent component "listen" for an event fired by the child?**
   By adding an `on<eventname>` attribute directly on the child component's tag in the parent's template — e.g., a `close` event is listened to using `onclose={handlerMethodName}`.

6. **What is a "simple event" in the context of child-to-parent communication?**
   An event fired with no additional data — just `new CustomEvent('eventName')` — used purely to notify the parent that something happened, without needing to pass any value.

7. **In this modal example, how is the modal shown and hidden?**
   The parent uses a reactive Boolean property (`showModal`). Clicking "Show Modal" sets it to `true`, which renders the child modal via `template if:true={showModal}`. When the child fires the `close` event, the parent sets `showModal` back to `false`, which removes the modal from the DOM.

8. **Why is the modal built using SLDS classes like `slds-modal` and `slds-backdrop`?**
   These are standard Salesforce Lightning Design System classes that give the modal proper styling, positioning, and a dimmed backdrop consistent with the Salesforce Lightning look and feel, without writing custom CSS.

9. **What is the purpose of `aria-modal`, `role="dialog"`, and `aria-labelledby` in the modal markup?**
   These are accessibility (a11y) attributes that inform assistive technologies (like screen readers) that this element is a modal dialog, improving usability for users relying on accessibility tools.

10. **What does `isExposed` and `<target>lightning__AppPage</target>` control in the `.js-meta.xml` file?**
    `isExposed: true` makes the component available for use in Salesforce builder tools (like App Builder), and `<target>lightning__AppPage</target>` specifically allows the component to be placed on a Lightning App Page.

11. **What's the difference between a simple event and an event with `detail` data?**
    A simple event (like the `close` event here) just notifies the parent that something happened. An event with `detail` (e.g., `new CustomEvent('show', { detail: 'hello' })`) also passes a value/object that the parent can read via `event.detail`.

## 🚀 How to Deploy

1. Create the LWC components using the Salesforce CLI or VS Code Salesforce Extension:
   ```
   sfdx force:lightning:component:create --type lwc --componentname childToParentComponent
   sfdx force:lightning:component:create --type lwc --componentname chilToParentModalComponent
   ```
2. Copy the respective HTML/JS content (and the meta.xml for the parent) into the generated files.
3. Deploy to your Salesforce org:
   ```
   sfdx force:source:deploy -p force-app/main/default/lwc/childToParentComponent
   sfdx force:source:deploy -p force-app/main/default/lwc/chilToParentModalComponent
   ```
4. Add the `childToParentComponent` to a Lightning App Page via **Lightning App Builder** (since it's exposed to `lightning__AppPage`), or drop it onto a test Aura/LWC tab.

## 📝 Notes

- This pattern (simple event, no data) is ideal for **notifications/signals** — e.g., "close this modal," "action completed," "cancel this operation" — where the parent only needs to know *that* something happened, not any accompanying data.
- If the child needed to pass information back to the parent (e.g., which button was clicked, or a selected value), the `detail` property of `CustomEvent` would be used instead — see the **"Child to Parent Communication Using Event with Data"** approach for that pattern.
