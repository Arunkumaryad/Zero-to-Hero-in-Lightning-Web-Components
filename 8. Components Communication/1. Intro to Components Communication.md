# Intro to Components Communication

## 📌 Overview

In Lightning Web Components (LWC), components are designed as reusable and independent building blocks.

When multiple components work together, they often need to **exchange data or notify each other about changes**.

This process is called:

> **Component Communication**

For example:

```text
Parent Component
       |
       ↓
Child Component
```

The parent may need to send data to the child.

Or:

```text
Child Component
       |
       ↓
Parent Component
```

The child may need to notify the parent about an action.

For components that don't have a direct parent-child relationship, other communication mechanisms such as **Pub/Sub** or **Lightning Message Service (LMS)** can be used depending on the architecture.

---

# 📚 Components Communication Approaches

The main approaches covered in this topic are:

```text
1. Parent → Child Communication

2. Child → Parent Communication

3. Sibling Component Communication Using Pub/Sub

4. Communication Across Visualforce, Aura and LWC
   Using Lightning Message Service
```

The overall architecture can be represented as:

```text
                 Component Communication
                         |
        ┌────────────────┼─────────────────┐
        │                │                 │
        ↓                ↓                 ↓
 Parent → Child   Child → Parent     Sibling Communication
        │                │                 │
       @api          CustomEvent       Pub/Sub / LMS
        │                │
        └────────────────┴──────────────────┐
                                            ↓
                              Cross-Technology Communication
                                            |
                                            ↓
                                           LMS
                                            |
                              ┌─────────────┼─────────────┐
                              ↓             ↓             ↓
                             LWC           Aura      Visualforce
```

---

# 1️⃣ Parent to Child Communication

## 📖 Definition

**Parent-to-child communication is the process of passing data or invoking functionality from a parent component to its child component.**

In LWC, the parent can communicate with a child mainly by:

1. Passing values to public properties using `@api`
2. Calling public methods exposed by the child using `@api`

Salesforce's data-flow guidance recommends one-way data flow: data moves from the owner/parent down to the child, while the child communicates changes back through events.

---

# 🔹 Method 1: Passing Data Using `@api`

Suppose the parent has:

```javascript
name = 'Arun';
```

The parent can pass this value to the child.

## Parent HTML

```html
<template>

    <c-child
        user-name={name}>
    </c-child>

</template>
```

---

## Child JavaScript

```javascript
import { LightningElement, api } from 'lwc';

export default class Child extends LightningElement {

    @api userName;

}
```

---

## Child HTML

```html
<template>

    <lightning-card title="Child Component">

        <p class="slds-p-around_medium">
            Hello {userName}
        </p>

    </lightning-card>

</template>
```

The data flow is:

```text
Parent
  |
  | user-name = "Arun"
  ↓
Child
  |
  ↓
@api userName
```

---

# 🔹 Important Rule

The child should generally treat data received from the parent as **read-only**.

For example:

```javascript
@api userName;
```

The parent owns the value.

The child consumes the value.

Salesforce recommends one-way data flow to avoid unexpected side effects.

---

# 🔹 Method 2: Calling a Child Public Method

A child can expose a JavaScript method using `@api`.

## Child JavaScript

```javascript
import { LightningElement, api } from 'lwc';

export default class Child extends LightningElement {

    @api
    showMessage() {

        console.log('Public method called from parent');

    }

}
```

The `@api` decorator makes the method public.

---

## Parent HTML

```html
<template>

    <lightning-button
        label="Call Child Method"
        onclick={handleClick}>
    </lightning-button>

    <c-child></c-child>

</template>
```

---

## Parent JavaScript

```javascript
import { LightningElement } from 'lwc';

export default class Parent extends LightningElement {

    handleClick() {

        const child =
            this.template.querySelector('c-child');

        child.showMessage();
    }
}
```

Flow:

```text
Parent
  |
  | showMessage()
  ↓
Child
```

Salesforce documents `@api` public methods as a way for an owner/parent to call JavaScript methods on a child component.

---

# 🧠 Parent → Child Quick Revision

```text
Parent → Child
     |
     ├── @api property
     |
     └── @api method
```

### Remember:

> **Properties and public methods are used to communicate down the component hierarchy.**

---

# 2️⃣ Child to Parent Communication

## 📖 Definition

**Child-to-parent communication is the process in which a child component sends information or notifications to its parent component.**

In LWC, the standard approach is:

> **Custom Events**

Salesforce recommends events for communication up the component containment hierarchy.

The basic pattern is:

```text
Child
  |
  | dispatchEvent()
  ↓
Parent
  |
  ↓
Event Handler
```

---

# 🔹 Creating a Custom Event

Suppose the child has a button.

## Child HTML

```html
<template>

    <lightning-button
        label="Send Message"
        onclick={handleClick}>
    </lightning-button>

</template>
```

---

## Child JavaScript

```javascript
import { LightningElement } from 'lwc';

export default class Child extends LightningElement {

    handleClick() {

        const event = new CustomEvent(
            'messagechange',
            {
                detail: {
                    message: 'Hello Parent!'
                }
            }
        );

        this.dispatchEvent(event);
    }
}
```

---

# 🔹 Handling the Event in Parent

## Parent HTML

```html
<template>

    <c-child
        onmessagechange={handleMessage}>
    </c-child>

    <p>
        {message}
    </p>

</template>
```

---

## Parent JavaScript

```javascript
import { LightningElement } from 'lwc';

export default class Parent extends LightningElement {

    message;

    handleMessage(event) {

        this.message = event.detail.message;

    }
}
```

---

# 🔄 Child → Parent Flow

```text
Child
  |
  | new CustomEvent()
  |
  | dispatchEvent()
  ↓
Parent
  |
  | onmessagechange
  ↓
handleMessage()
  |
  ↓
event.detail
```

---

# 📌 Important CustomEvent Concepts

The basic syntax is:

```javascript
const event = new CustomEvent(
    'messagechange',
    {
        detail: {
            message: 'Hello Parent!'
        }
    }
);

this.dispatchEvent(event);
```

There are three important concepts:

### 1. Event Name

```javascript
'messagechange'
```

### 2. Data

```javascript
detail
```

### 3. Dispatch

```javascript
this.dispatchEvent(event);
```

Salesforce recommends the `CustomEvent` interface for creating and dispatching custom events in LWC.

---

# 🔹 Accessing Event Data

The parent receives:

```javascript
event
```

The data is available through:

```javascript
event.detail
```

Example:

```javascript
handleMessage(event) {

    console.log(event.detail.message);

}
```

---

# ⚠️ `event.target` vs `event.currentTarget` vs `event.detail`

This is an important interview topic.

### `event.target`

The element from which the event originated, subject to event retargeting across shadow boundaries.

### `event.currentTarget`

The element currently handling the event.

### `event.detail`

The custom data sent with a `CustomEvent`.

Example:

```javascript
new CustomEvent('messagechange', {
    detail: {
        name: 'Arun'
    }
});
```

Parent:

```javascript
event.detail.name
```

Salesforce's event guidance specifically discusses `detail` and event retargeting across shadow boundaries.

---

# 3️⃣ Sibling Component Communication Using Pub/Sub

## 📖 Definition

Sibling components are components that share the same parent.

For example:

```text
             Parent
             /    \
            /      \
       Child A    Child B
```

Child A and Child B are siblings.

There is no direct parent-child relationship between them.

Therefore:

```text
Child A → Child B
```

cannot normally be handled simply by passing an `@api` property directly from one sibling to the other.

A communication mechanism such as Pub/Sub or Lightning Message Service can be used.

---

# 🔄 Sibling Communication

```text
             Parent
             /    \
            ↓      ↓
        Child A  Child B
            |        ↑
            |        |
            └────────┘
             Message
```

---

# 📢 Pub/Sub Pattern

Pub/Sub stands for:

> **Publish / Subscribe**

One component publishes a message.

Another component subscribes to that message.

```text
Publisher
    |
    | publish
    ↓
 Pub/Sub
    |
    | subscribe
    ↓
Subscriber
```

---

# 🔹 Example

Suppose:

```text
Parent
│
├── componentA
│
└── componentB
```

`componentA` publishes:

```text
"Record selected"
```

`componentB` receives:

```text
"Record selected"
```

---

# ⚠️ Important Modern Salesforce Note

The Pub/Sub utility pattern is useful to understand for legacy LWC examples and situations where no suitable standard messaging mechanism is available.

For modern Salesforce development, **Lightning Message Service (LMS)** is generally the preferred platform-supported solution for communication across components when applicable.

Salesforce provides LMS specifically for communication across the DOM and between LWC, Aura, and Visualforce.

Therefore, in an interview:

> **For sibling components, explain Pub/Sub as a communication pattern, but also mention Lightning Message Service as the modern Salesforce-supported messaging solution.**

---

# 4️⃣ Lightning Message Service

## 📖 Definition

**Lightning Message Service (LMS) enables communication across the DOM between Visualforce pages, Aura components, and Lightning Web Components.**

Salesforce documents LMS as a way to communicate across the DOM within a Lightning page and between Visualforce, Aura, and LWC.

This matches the fourth communication approach shown in the screenshot:

> **Communication Across VF pages, Aura and LWC Using Lightning Messaging Service**

---

# 🌐 Why Do We Need LMS?

Imagine:

```text
Lightning Page
│
├── LWC Component
│
├── Aura Component
│
└── Visualforce Page
```

These components may not have a direct parent-child relationship.

Traditional:

```text
@api
```

and:

```text
CustomEvent
```

are not enough for this kind of cross-technology communication.

LMS provides a common messaging mechanism.

---

# 🔄 LMS Architecture

```text
             Message Channel
                   ↑
                   |
          ┌────────┼────────┐
          |        |        |
          ↓        ↓        ↓
         LWC      Aura      VF
          |        |        |
          └────────┼────────┘
                   |
              Message Data
```

---

# 📌 Lightning Message Channel

LMS uses a:

> **Lightning Message Channel**

A message channel defines the channel through which messages are published and received.

Salesforce uses the `LightningMessageChannel` metadata type for creating message channels.

Example:

```text
force-app/
└── main/
    └── default/
        └── messageChannels/
            └── RecordSelected.messageChannel-meta.xml
```

---

# 📝 Message Channel Example

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningMessageChannel
    xmlns="http://soap.sforce.com/2006/04/metadata">

    <masterLabel>Record Selected</masterLabel>

    <isExposed>true</isExposed>

    <description>
        Message channel used for record selection.
    </description>

    <lightningMessageFields>
        <fieldName>recordId</fieldName>
        <description>Selected Record Id</description>
    </lightningMessageFields>

</LightningMessageChannel>
```

---

# 📤 Publishing a Message

An LWC publisher imports:

```javascript
import {
    publish,
    MessageContext
} from 'lightning/messageService';

import {
    wire
} from 'lwc';
```

Then:

```javascript
@wire(MessageContext)
messageContext;
```

The message can be published:

```javascript
publish(
    this.messageContext,
    RECORD_SELECTED,
    {
        recordId: this.recordId
    }
);
```

Salesforce's LMS API uses `publish()` with a `MessageContext`, message channel, and message payload.

---

# 📥 Subscribing to a Message

The subscriber uses:

```javascript
subscribe()
```

Example:

```javascript
import {
    subscribe,
    MessageContext
} from 'lightning/messageService';

@wire(MessageContext)
messageContext;
```

Then:

```javascript
connectedCallback() {

    this.subscription = subscribe(
        this.messageContext,
        RECORD_SELECTED,
        (message) => {
            this.handleMessage(message);
        }
    );
}
```

---

# 🔄 LMS Flow

```text
Publisher
    |
    ↓
publish()
    |
    ↓
Lightning Message Channel
    |
    ↓
subscribe()
    |
    ↓
Subscriber
```

---

# 🧠 LMS Components

The important LMS concepts are:

```text
Lightning Message Service
        |
        ├── Message Channel
        |
        ├── Publisher
        |
        ├── Subscriber
        |
        ├── MessageContext
        |
        ├── publish()
        |
        ├── subscribe()
        |
        └── unsubscribe()
```

---

# 🧩 MessageContext

`MessageContext` provides information about the LWC using Lightning Message Service.

In an LWC, it is commonly obtained using:

```javascript
@wire(MessageContext)
messageContext;
```

Salesforce notes that when using the wired `MessageContext`, LMS automatically handles registration/unregistration with the component lifecycle.

---

# 📢 Publish

The publisher sends a message:

```javascript
publish(
    this.messageContext,
    MESSAGE_CHANNEL,
    payload
);
```

Example:

```javascript
publish(
    this.messageContext,
    RECORD_SELECTED,
    {
        recordId: '001XXXXXXXXXXXX'
    }
);
```

---

# 📥 Subscribe

The subscriber listens:

```javascript
subscribe(
    this.messageContext,
    MESSAGE_CHANNEL,
    message => {
        console.log(message);
    }
);
```

---

# 🧹 Unsubscribe

When manually managing a subscription, it can be removed using:

```javascript
unsubscribe(this.subscription);
```

This prevents unnecessary subscriptions from remaining active.

# 🎯 When to Use Which Approach?

## Use `@api` when:

```text
Parent → Child
```

Example:

```text
Parent has Account Name
       ↓
Child displays Account Name
```

---

## Use `CustomEvent` when:

```text
Child → Parent
```

Example:

```text
Child selects Account
       ↓
CustomEvent
       ↓
Parent receives Account Id
```

---

## Use Pub/Sub when:

```text
Sibling → Sibling
```

especially when dealing with legacy patterns where the components don't have a direct containment communication path.

---

## Use LMS when:

```text
LWC ↔ LWC
LWC ↔ Aura
LWC ↔ Visualforce
```

or when components need platform-supported messaging across broader parts of a Lightning application.

Salesforce positions LMS as the standard mechanism for communication across these technologies.

---

# ⚠️ Important Interview Concept: One-Way Data Flow

LWC follows the principle:

```text
Parent
  |
  ↓
Child
```

Data flows down.

To communicate changes upward:

```text
Child
  |
  ↓
Event
  |
  ↓
Parent
```

This is commonly summarized as:

> **Props down, events up.**

Salesforce recommends one-way data flow to reduce code complexity and unexpected side effects.

---

# 🚨 Event Bubbling

Events can propagate upward through the DOM.

For example:

```text
Child
  ↓
Parent
  ↓
Grandparent
```

However, don't automatically set:

```javascript
{
    bubbles: true,
    composed: true
}
```

for every event.

Salesforce recommends using the least permissive event configuration that solves the requirement. The default `bubbles: false` and `composed: false` provides the strongest encapsulation.

---

# 📌 Event Example With `detail`

Child:

```javascript
this.dispatchEvent(
    new CustomEvent('recordselected', {
        detail: {
            recordId: this.recordId
        }
    })
);
```

Parent:

```javascript
handleRecordSelected(event) {

    const recordId =
        event.detail.recordId;

    console.log(recordId);
}
```

# 🆚 `@api` vs CustomEvent vs LMS

| Feature                 | `@api`        | CustomEvent     | LMS                         |
| ----------------------- | ------------- | --------------- | --------------------------- |
| Parent → Child          | ✅             | ❌               | Possible but unnecessary    |
| Child → Parent          | ❌             | ✅               | Possible but unnecessary    |
| Sibling communication   | ❌ Directly    | ❌ Directly      | ✅                           |
| Cross DOM communication | ❌             | Limited         | ✅                           |
| LWC ↔ Aura              | ❌             | ❌               | ✅                           |
| LWC ↔ Visualforce       | ❌             | ❌               | ✅                           |
| Simple                  | ✅             | ✅               | Moderate                    |
| Main purpose            | Data/API down | Notification up | Messaging across components |

# 🎤 Interview Questions

## 1. What are the different component communication approaches in LWC?

### Answer

The major approaches are:

```text
Parent → Child
    ↓
@api property / @api method

Child → Parent
    ↓
CustomEvent

Sibling / unrelated components
    ↓
LMS

LWC ↔ Aura ↔ Visualforce
    ↓
Lightning Message Service
```

---

## 2. How does a parent pass data to a child?

### Answer

The parent passes data through a public property exposed using `@api`.

Example:

```javascript
@api name;
```

Parent:

```html
<c-child name={userName}></c-child>
```

---

## 3. How does a parent call a child method?

### Answer

Expose the method using `@api`:

```javascript
@api
resetForm() {
    // logic
}
```

Then the parent can obtain the child instance and call:

```javascript
this.template
    .querySelector('c-child')
    .resetForm();
```

Salesforce documents this pattern for calling public methods on child components.

---

## 4. How does a child communicate with its parent?

### Answer

Using a custom event.

Child:

```javascript
this.dispatchEvent(
    new CustomEvent('selected', {
        detail: {
            value: 'ABC'
        }
    })
);
```

Parent:

```html
<c-child
    onselected={handleSelected}>
</c-child>
```

---

## 5. What is `CustomEvent`?

### Answer

`CustomEvent` is a browser/DOM event interface used in LWC to create custom events and send information from a child component to its parent.

Salesforce recommends `CustomEvent` for LWC custom events.

---

## 6. How do you pass data through a CustomEvent?

### Answer

Use the `detail` property.

```javascript
new CustomEvent('selected', {
    detail: {
        recordId: this.recordId
    }
});
```

Parent:

```javascript
event.detail.recordId
```

---

## 7. How can sibling components communicate?

### Answer

Sibling components do not have a direct parent-child relationship.

Communication can be implemented through a common parent, a messaging mechanism such as LMS, or a Pub/Sub utility pattern where appropriate.

For modern Salesforce development, LMS is the preferred platform-supported messaging solution when applicable.

---

## 8. What is Pub/Sub?

### Answer

Pub/Sub means:

> **Publish and Subscribe.**

One component publishes a message and another component subscribes to that message.

```text
Publisher
    ↓
Message
    ↓
Subscriber
```

---

## 9. What is Lightning Message Service?

### Answer

Lightning Message Service is a Salesforce messaging service that allows components to communicate across the DOM and between LWC, Aura, and Visualforce.

---

## 10. What is a Lightning Message Channel?

### Answer

A Lightning Message Channel is the defined channel through which components publish and subscribe to messages using Lightning Message Service.

It is created using the `LightningMessageChannel` metadata type.

---

## 11. What are `publish()` and `subscribe()`?

### Answer

`publish()` sends a message to a message channel.

```javascript
publish(
    messageContext,
    channel,
    payload
);
```

`subscribe()` listens for messages on a channel.

```javascript
subscribe(
    messageContext,
    channel,
    handler
);
```

---

## 12. What is MessageContext?

### Answer

`MessageContext` provides the context required by Lightning Message Service to publish and subscribe to messages.

In LWC it is commonly obtained with:

```javascript
@wire(MessageContext)
messageContext;
```

Salesforce documents `MessageContext` as part of the LMS API.

---

## 13. Can LMS communicate between LWC and Aura?

### Answer

Yes.

Lightning Message Service supports communication between:

```text
LWC
↕
Aura
```

and also:

```text
LWC
↕
Visualforce
```

and:

```text
Aura
↕
Visualforce
```

when used in supported Lightning contexts.

---

## 14. What is the difference between `@api` and CustomEvent?

### Answer

`@api` is primarily used for communication **down** the component hierarchy.

```text
Parent → Child
```

Custom events are primarily used for communication **up** the hierarchy.

```text
Child → Parent
```

---

## 15. What is the difference between CustomEvent and LMS?

### Answer

`CustomEvent` is generally used for communication within a component's containment hierarchy.

```text
Child → Parent
```

LMS is designed for broader messaging across components and can communicate between LWC, Aura, and Visualforce.

# ⚠️ Common Mistakes

## Mistake 1: Trying to modify an `@api` value inside the child

Avoid treating parent-owned data as mutable state.

Instead:

```text
Parent owns data
      ↓
Child receives data
      ↓
Child dispatches event
      ↓
Parent updates data
      ↓
New value flows to child
```

This follows the one-way data-flow model.

---

## Mistake 2: Using `@api` for Child → Parent

Incorrect concept:

```text
Child
  ↓
@api
  ↓
Parent
```

Use:

```text
Child
  ↓
CustomEvent
  ↓
Parent
```

---

## Mistake 3: Using CustomEvent for unrelated components

If there is no suitable containment relationship, consider LMS rather than trying to force a custom event through unrelated components.

---

## Mistake 4: Making every event bubble

Avoid unnecessarily using:

```javascript
{
    bubbles: true,
    composed: true
}
```

Salesforce recommends the least permissive configuration that meets the requirement.

---

## Mistake 5: Using LMS for every simple communication

Don't use LMS when a simple:

```text
Parent → Child
```

relationship can be handled with:

```text
@api
```

Likewise, don't use LMS when:

```text
Child → Parent
```

can simply use:

```text
CustomEvent
```

Use the simplest mechanism that fits the communication requirement.

# ✅ Final Takeaway

The most important concept from this topic is:

```text
                 COMPONENT COMMUNICATION
                          |
          ┌───────────────┼────────────────┐
          ↓               ↓                ↓
       DOWN              UP             ACROSS
          |               |                |
        @api        CustomEvent           LMS
          |               |                |
          ↓               ↓                ↓
       Child           Parent       Other Components
```

### Remember these four lines for interviews:

```text
Parent → Child
       = @api

Child → Parent
       = CustomEvent

Sibling → Sibling
       = Pub/Sub / LMS

LWC ↔ Aura ↔ Visualforce
       = Lightning Message Service
```

The overall principle is:

> **Data flows down through properties, events communicate changes upward, and messaging services such as LMS handle broader communication across components and technologies.**

For modern Salesforce development, prefer the simplest communication mechanism that matches the relationship: `@api` for parent-to-child, `CustomEvent` for child-to-parent, and Lightning Message Service for broader component communication.
