# Child to Parent Communication Approaches (LWC)

This project is part of a **Lightning Web Components (LWC)** learning series that demonstrates the different ways a **Child Component can communicate with its Parent Component**.

> **Note:** Only the concept/flow diagram was provided for this topic (no code screenshots were shared). The code samples below follow the standard, official LWC pattern for each approach shown in the diagram. If you'd like this README updated to match your exact code, feel free to share the corresponding screenshots and I'll update it to mirror them precisely.

---

## 📌 Concept Overview

In LWC, a **child component can never directly call a method on its parent** or modify the parent's data (this would break component encapsulation). Instead, LWC uses the standard **DOM event model** — the child **dispatches (fires) a custom event**, and the parent **listens** for that event on the child's tag in its own template.

This diagram breaks Child → Parent communication into **three approaches**:

```
                         ┌────────────────────┐
                         │   Parent Component   │
                         └──────────▲───────────┘
                 ▲                  │                   ▲
                 │                  │                   │
      ┌──────────┴─────────┐ ┌──────┴───────────┐ ┌─────┴──────────┐
      │ Calling parent using │ │ Calling parent using│ │  Event Bubbling  │
      │    simple Event      │ │  Event with data     │ │                  │
      └──────────▲─────────┘ └──────▲───────────┘ └─────▲──────────┘
                 │                  │                   │
                 └──────────────────┼───────────────────┘
                                     │
                         ┌───────────┴──────────┐
                         │    Child Component     │
                         └───────────────────────┘
```

**In simple words:** The child component creates and fires a `CustomEvent`. The parent, having added an event listener on the child's tag in its template, catches that event and reacts to it — with or without receiving extra data, and with or without the event bubbling up further through the DOM.

## 🧩 Approach 1 — Calling Parent using a Simple Event

The child dispatches an event with **no extra data** — it's just a "signal" that something happened (e.g., a button was clicked).

### Child Component — `childSimpleEvent.html`
```html
<template>
    <lightning-card title="Child Component">
        <div class="slds-m-around_medium">
            <lightning-button variant="brand" label="Notify Parent" onclick={handleClick}></lightning-button>
        </div>
    </lightning-card>
</template>
```

### Child Component — `childSimpleEvent.js`
```js
import { LightningElement } from 'lwc';

export default class ChildSimpleEvent extends LightningElement {
    handleClick() {
        // Creating and dispatching a simple custom event with no data
        this.dispatchEvent(new CustomEvent('notify'));
    }
}
```

### Parent Component — `parentSimpleEvent.html`
```html
<template>
    <lightning-card title="Parent Component">
        <div class="slds-m-around_medium">
            <p>{message}</p>
            <c-child-simple-event onnotify={handleNotify}></c-child-simple-event>
        </div>
    </lightning-card>
</template>
```

### Parent Component — `parentSimpleEvent.js`
```js
import { LightningElement } from 'lwc';

export default class ParentSimpleEvent extends LightningElement {
    message = 'Waiting for child...';

    handleNotify(event) {
        this.message = 'Child component fired an event!';
    }
}
```

**How it works:**
- The child creates `new CustomEvent('notify')` and fires it using `this.dispatchEvent()`.
- In the parent's template, the listener is added as `on` + event name → `onnotify={handleNotify}` on the `<c-child-simple-event>` tag.
- When the button in the child is clicked, the parent's `handleNotify` method runs automatically.

## 🧩 Approach 2 — Calling Parent using Event with Data

Here, the child **passes data along with the event**, using the `detail` property of `CustomEvent`.

### Child Component — `childEventWithData.html`
```html
<template>
    <lightning-card title="Child Component">
        <div class="slds-m-around_medium">
            <lightning-input type="text" label="Enter your name" onchange={handleChange}></lightning-input>
        </div>
    </lightning-card>
</template>
```

### Child Component — `childEventWithData.js`
```js
import { LightningElement } from 'lwc';

export default class ChildEventWithData extends LightningElement {
    handleChange(event) {
        const nameValue = event.target.value;
        // Passing data to the parent using the "detail" property
        this.dispatchEvent(new CustomEvent('namechange', {
            detail: nameValue
        }));
    }
}
```

### Parent Component — `parentEventWithData.html`
```html
<template>
    <lightning-card title="Parent Component">
        <div class="slds-m-around_medium">
            <p>Hello, {childName}!</p>
            <c-child-event-with-data onnamechange={handleNameChange}></c-child-event-with-data>
        </div>
    </lightning-card>
</template>
```

### Parent Component — `parentEventWithData.js`
```js
import { LightningElement } from 'lwc';

export default class ParentEventWithData extends LightningElement {
    childName = '';

    handleNameChange(event) {
        // Data sent from the child is available in event.detail
        this.childName = event.detail;
    }
}
```

**How it works:**
- The child packages the value inside the `detail` key of the `CustomEvent` object.
- The parent retrieves this value using `event.detail` inside its handler.
- This is the most common approach for passing form input, selected values, or any piece of data from child to parent.

## 🧩 Approach 3 — Event Bubbling

By default, custom events in LWC do **not bubble** and are **not composed** — meaning they only reach the immediate parent that has the listener directly on the child's tag. **Event Bubbling** allows the event to propagate further up through the DOM tree (useful in nested/grandchild component structures), by setting `bubbles: true` (and `composed: true` if it needs to cross shadow DOM boundaries).

### Child Component — `childEventBubbling.html`
```html
<template>
    <lightning-card title="Child Component">
        <div class="slds-m-around_medium">
            <lightning-button variant="destructive" label="Delete Item" onclick={handleDelete}></lightning-button>
        </div>
    </lightning-card>
</template>
```

### Child Component — `childEventBubbling.js`
```js
import { LightningElement } from 'lwc';

export default class ChildEventBubbling extends LightningElement {
    handleDelete() {
        this.dispatchEvent(new CustomEvent('itemdeleted', {
            detail: { id: 101 },
            bubbles: true,   // allows the event to bubble up through the DOM
            composed: true   // allows the event to cross the shadow DOM boundary
        }));
    }
}
```

### Parent Component — `parentEventBubbling.html`
```html
<template>
    <lightning-card title="Parent Component">
        <div class="slds-m-around_medium" onitemdeleted={handleItemDeleted}>
            <c-child-event-bubbling></c-child-event-bubbling>
        </div>
    </lightning-card>
</template>
```

### Parent Component — `parentEventBubbling.js`
```js
import { LightningElement } from 'lwc';

export default class ParentEventBubbling extends LightningElement {
    handleItemDeleted(event) {
        console.log('Item deleted with id:', event.detail.id);
    }
}
```

**How it works:**
- `bubbles: true` allows the event to travel up through every ancestor element in the DOM, not just the direct parent that declared the listener on the child's own tag.
- `composed: true` allows it to cross out of the child's shadow DOM boundary so ancestors outside the immediate component can also catch it.
- This is especially useful when there are multiple levels of nesting (grandchild → child → parent) and you don't want to manually re-dispatch the event at every level.

## 🔑 Key Takeaways

| Approach | `CustomEvent` Options Used | Use Case |
|---|---|---|
| Simple Event | None | Just notifying the parent that something happened (e.g., button clicked) |
| Event with Data | `detail` | Sending a value/object from child to parent (e.g., form input, selected record) |
| Event Bubbling | `bubbles: true`, `composed: true` | Propagating an event through multiple levels of nested components |

| Concept | Purpose |
|---|---|
| `CustomEvent` | The standard DOM API used to create a custom event in LWC |
| `dispatchEvent()` | Fires the event from the child component |
| `on<eventname>` handler | How the parent listens for a child's event, added directly on the child's tag in the parent's template |
| `event.detail` | Where any data passed by the child is stored and read by the parent |
| `bubbles` / `composed` | Flags that control how far and how the event travels through the DOM |

## 💬 Interview Questions on This Topic

1. **How does a child component communicate with its parent in LWC?**
   By dispatching a `CustomEvent` from the child, which the parent listens to using an `on<eventname>` handler declared on the child's tag in its own template.

2. **Why can't a child directly call a method on the parent component?**
   LWC enforces strict component encapsulation — a child has no reference to its parent, so direct method calls aren't possible. Communication upward must always go through events.

3. **What is the difference between a simple event and an event with data?**
   A simple event just signals that something occurred, with no payload. An event with data uses the `detail` property of `CustomEvent` to pass information (like a value or object) to the parent.

4. **How do you access data sent from a child component inside the parent's event handler?**
   Through `event.detail` inside the handler method bound to the `on<eventname>` attribute.

5. **Do custom events in LWC bubble by default?**
   No. By default, custom events do not bubble and are not composed — they only reach the direct parent listening on the child's tag. To make them bubble, you must explicitly set `bubbles: true` (and `composed: true` to cross shadow DOM boundaries).

6. **What is the difference between `bubbles` and `composed` in a `CustomEvent`?**
   `bubbles: true` allows the event to propagate up through ancestor DOM elements. `composed: true` allows the event to cross out of the current component's shadow DOM so it can be caught by components/elements outside its own shadow tree.

7. **How do you name the event listener in the parent's template?**
   The listener attribute is always the event name prefixed with `on` — e.g., an event named `notify` is listened to using `onnotify` in the parent's HTML.

8. **What naming rule applies to custom event names in LWC?**
   Event names must be lowercase and cannot contain spaces or special characters — LWC enforces all-lowercase event names.

9. **When would you use event bubbling instead of a simple parent-child event?**
   When you have multiple levels of nested components (e.g., grandchild → child → parent) and want an event to propagate upward through all of them without manually re-dispatching it at each level.

10. **What's a real-world example of child-to-parent communication?**
    A child row component in a list firing a "delete" event with the record's ID, which the parent list component listens for to remove that record from its data and re-render the list.

## 🚀 How to Deploy

1. Create the LWC components using the Salesforce CLI or VS Code Salesforce Extension, for example:
   ```
   sfdx force:lightning:component:create --type lwc --componentname parentSimpleEvent
   sfdx force:lightning:component:create --type lwc --componentname childSimpleEvent
   ```
2. Copy the respective HTML/JS content into the generated files for each approach.
3. Deploy to your Salesforce org:
   ```
   sfdx force:source:deploy -p force-app/main/default/lwc/parentSimpleEvent
   sfdx force:source:deploy -p force-app/main/default/lwc/childSimpleEvent
   ```
4. Add the parent component to an App Page / Record Page via Lightning App Builder, or place it on a test Aura/LWC tab.

## 📝 Notes

- All three approaches rely on the same underlying mechanism: the DOM's native `CustomEvent` and `dispatchEvent()` API — LWC does not invent a new event system, it uses standard web APIs.
- Choose **Simple Event** for basic notifications, **Event with Data** when the parent needs specific information from the child, and **Event Bubbling** when the event must travel through more than one level of component nesting.
