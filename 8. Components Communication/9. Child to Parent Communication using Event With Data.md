# Child to Parent Communication Using Event With Data (LWC)

This project is part of a **Lightning Web Components (LWC)** learning series. It builds directly on the earlier **Simple Event** example, but this time the child component **passes actual data back to the parent** using the `detail` property of a `CustomEvent` — implemented through the same **Show/Hide Modal** example.

---

## 📌 Concept Overview

In the "Simple Event" approach, the child just tells the parent "something happened" — with no extra information. In **"Event with Data"**, the child additionally sends a **payload** (a string, object, number, etc.) along with the event, using the `detail` property of `CustomEvent`. The parent then reads this payload through `event.detail` inside its handler.

```js
new CustomEvent('close', {
    detail: "Modal Closed Successfully!!."
});
```

- `'close'` → the event name.
- `detail` → the property used to attach data to the event. Here, a simple string message is passed, but `detail` can hold any JavaScript value — a string, number, array, or object.

## 🧩 Component Code

### 1. Child Component — `chilToParentModalComponent.html`

The modal markup itself is unchanged from the Simple Event version — it's a standard SLDS modal dialog with an **Ok** button.

```html
<template>

                <p>Loaded Successfully.</p>

            <div class="slds-modal__footer">

            </div>

    </section>

```

- `role="dialog"`, `aria-modal="true"`, and `aria-labelledby` provide accessibility support so screen readers correctly announce this as a modal dialog.
- The `slds-backdrop` div creates the dimmed overlay behind the modal.
- Clicking the **Ok** button triggers `handleClick`, defined in the child's JS.

### 2. Child Component — `chilToParentModalComponent.js`

This is where the key difference from the Simple Event approach lives — the event now carries a **`detail`** payload.

```js
import { LightningElement } from 'lwc';

export default class ChilToParentModalComponent extends LightningElement {
    handleClick(event) {
        const myEvent = new CustomEvent('close', {
            detail: "Modal Closed Successfully!!."
        });
        this.dispatchEvent(myEvent);
    }
}
```

- `new CustomEvent('close', { detail: "Modal Closed Successfully!!." })` → creates a `close` event and attaches the string `"Modal Closed Successfully!!."` as its `detail` payload.
- `this.dispatchEvent(myEvent)` → fires the event, along with its attached data, up to any listener on this component (i.e., the parent).

### 3. Parent Component — `childToParentComponent.html`

The parent now also displays a message (`{msg}`) that will be populated from the data sent by the child.

```html
<template>
    <lightning-card title="Child To Parent Communication">
        <div class="slds-p-around_medium">
            <h1>{msg}</h1>
            <lightning-button variant="brand" label="Show Modal" onclick={handleClick}></lightning-button>
            <template if:true={showModal}>
                <c-chil-to-parent-modal-component
                    onclose={handleClose}></c-chil-to-parent-modal-component>
            </template>
        </div>
    </lightning-card>
</template>
```

- `<h1>{msg}</h1>` → binds to the `msg` reactive property in the parent's JS, and will display the message received from the child once the modal is closed.
- The rest of the structure is the same as the Simple Event version: a **Show Modal** button, and the child modal component conditionally rendered using `template if:true={showModal}`, with its `close` event wired to `onclose={handleClose}`.

### 4. Parent Component — `childToParentComponent.js`

```js
import { LightningElement } from 'lwc';

export default class ChildToParentComponent extends LightningElement {
    showModal = false;
    msg;

    handleClick(event) {
        this.showModal = true;
    }

    handleClose(event) {
        this.msg = event.detail;
        this.showModal = false;
    }
}
```

- `msg` → a new reactive property (declared but not initialized) that will store the message received from the child.
- `handleClick` → same as before, sets `showModal = true` to display the modal.
- `handleClose(event)` → this is the key update:
  - `event.detail` → reads the data sent by the child (the string `"Modal Closed Successfully!!."`) and stores it in `this.msg`.
  - `this.showModal = false` → hides the modal, just like in the Simple Event version.
  - Because `msg` is bound to `<h1>{msg}</h1>` in the template, the UI automatically updates to display this message the moment the modal closes.

## ⚙️ How It Works (Step-by-Step)

1. The user clicks **Show Modal** on the parent component.
2. `handleClick` runs in the parent, setting `showModal = true`, which renders the child modal component (`<c-chil-to-parent-modal-component>`).
3. Inside the child modal, the user clicks the **Ok** button, triggering `handleClick` in the child's JS.
4. The child creates a `CustomEvent` named `'close'` with a `detail` payload containing the message `"Modal Closed Successfully!!."`.
5. `this.dispatchEvent(myEvent)` fires this event upward.
6. Because the parent registered `onclose={handleClose}` on the child's tag, the parent's `handleClose` method runs automatically when the event arrives.
7. Inside `handleClose`, `event.detail` is used to extract the message sent by the child and store it in `this.msg`.
8. `showModal` is set back to `false`, removing the modal from the DOM.
9. Since `msg` is reactive and bound in the template (`{msg}`), the parent's UI instantly updates to show **"Modal Closed Successfully!!."**

## 🔑 Key Takeaways

| Concept | Purpose |
|---|---|
| `detail` property of `CustomEvent` | Used to attach any data (string, number, object, array) to a custom event |
| `event.detail` | How the parent's handler reads the data sent by the child |
| Reactive property (`msg`) | Automatically updates the UI when its value changes, without any manual DOM manipulation |
| `on<eventname>` in parent template | Registers the parent's listener for the child's event, same as in the Simple Event approach |
| `template if:true={property}` | Conditionally renders markup — used here to show/hide the modal |

## 🆚 Simple Event vs. Event with Data

| Aspect | Simple Event | Event With Data |
|---|---|---|
| `CustomEvent` options | None (all defaults) | `{ detail: <payload> }` |
| What the parent receives | Just a notification that the event fired | The notification **plus** actual data via `event.detail` |
| Typical use case | "Close this modal", "Action completed" | "Here's the value the user selected", "Here's the ID of the deleted record" |
| Example in this project | `new CustomEvent('close')` | `new CustomEvent('close', { detail: "Modal Closed Successfully!!." })` |

## 💬 Interview Questions on This Topic

1. **How do you send data from a child component to a parent component in LWC?**
   By passing a `detail` property inside the options object when creating the `CustomEvent`, e.g., `new CustomEvent('eventName', { detail: someValue })`. The parent then reads it via `event.detail` in its handler.

2. **What data types can be passed inside the `detail` property?**
   Any JavaScript value — a string, number, boolean, array, or object.

3. **How does the parent component access the data sent by the child?**
   Through the `detail` property of the `event` object received in its handler method — e.g., `event.detail`.

4. **What's the difference between a Simple Event and an Event with Data?**
   A Simple Event just signals that something happened, with no extra information. An Event with Data additionally carries a payload via the `detail` property, giving the parent actual information to work with.

5. **In this example, what data is sent from the child to the parent, and how is it used?**
   The child sends the string `"Modal Closed Successfully!!."` via `detail` when the modal's Ok button is clicked. The parent stores this in its `msg` reactive property and displays it in an `<h1>` element.

6. **Why is `msg` declared without an initial value in the parent's JS (`msg;`)?**
   Because its value isn't known until the child sends it — it starts as `undefined` and only gets populated once the `handleClose` method runs and assigns `event.detail` to it.

7. **What happens if you try to pass data without using the `detail` property?**
   The data simply won't reach the parent. `detail` is the standard, designated property in the `CustomEvent` API for carrying custom data — there's no other built-in way to attach a payload to a `CustomEvent`.

8. **Can you send multiple pieces of data using a single event?**
   Yes — since `detail` accepts any JavaScript value, you can pass an object containing multiple fields, e.g., `detail: { status: 'closed', timestamp: Date.now() }`, and the parent can then destructure or access individual fields from `event.detail`.

9. **Why does the parent's UI update automatically after `handleClose` runs?**
   Because `msg` and `showModal` are reactive properties in LWC. Any assignment to a reactive property automatically triggers a re-render of the component's template wherever that property is used.

10. **What's a real-world scenario where "Event with Data" would be preferred over a "Simple Event"?**
    A child list-item component notifying the parent which specific record was clicked or deleted (passing the record's ID via `detail`), or a child form component sending back the values a user entered, so the parent can process or save them.

## 🚀 How to Deploy

1. Create the LWC components using the Salesforce CLI or VS Code Salesforce Extension:
   ```
   sfdx force:lightning:component:create --type lwc --componentname childToParentComponent
   sfdx force:lightning:component:create --type lwc --componentname chilToParentModalComponent
   ```
2. Copy the respective HTML/JS content into the generated files.
3. Deploy to your Salesforce org:
   ```
   sfdx force:source:deploy -p force-app/main/default/lwc/childToParentComponent
   sfdx force:source:deploy -p force-app/main/default/lwc/chilToParentModalComponent
   ```
4. Add the `childToParentComponent` to a Lightning App Page via **Lightning App Builder**, or place it on a test Aura/LWC tab.

## 📝 Notes

- This approach builds directly on the **Simple Event** pattern — the only change is adding a `detail` payload to the `CustomEvent` and reading it via `event.detail` in the parent.
- Always keep the `detail` payload lightweight and relevant — it's meant for passing small pieces of information (IDs, status flags, short messages, selected values), not large datasets.
