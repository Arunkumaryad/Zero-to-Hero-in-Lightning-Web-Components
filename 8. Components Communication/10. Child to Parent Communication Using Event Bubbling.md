# Child to Parent Communication Using Event Bubbling (LWC)

This project is part of a **Lightning Web Components (LWC)** learning series. It builds on the earlier **Event with Data** example, and demonstrates **Event Bubbling** — where an event fired deep inside a component tree propagates ("bubbles") up through every ancestor element, not just the one immediate listener declared on the child's own tag.

---

## 📌 Concept Overview: Event Bubbling

**Lightning Web Components has only two event propagation options**, both configured when creating a `CustomEvent`:

- **`bubbles`** — A Boolean value indicating whether the event bubbles up through the DOM or not. **Defaults to `false`.**
- **`composed`** — A Boolean value indicating whether the event can pass through the shadow boundary. **Defaults to `false`.**

```js
this.dispatchEvent(new CustomEvent('show', { bubbles: true, details: 'hello' }))
```

### Event Bubbling Demo

```
Parent component
┌───────────────────────────────────────────────────────────┐
│ <div onshow={parentHandler}>                                │  → 3rd: onshow captures the event based on the
│                                                               │     event name, and parentHandler is triggered
│   Child component                                            │
│   ┌───────────────────────────────────────────────────┐     │
│   │ <div onclick={Y}>                                    │     │  → 2nd: Y is triggered, and the event bubbles
│   │   <button onclick={X}>Click me</button>              │     │  → 1st: X is triggered, and then the event bubbles
│   │ </div>                                                │     │
│   └───────────────────────────────────────────────────┘     │
│ </div>                                                       │
└───────────────────────────────────────────────────────────┘
```

**How to read this demo:** When the `<button>` is clicked:
1. **1st** — `X` (the button's own `onclick` handler) is triggered, and then the event **bubbles** upward.
2. **2nd** — `Y` (the surrounding `<div>`'s `onclick` handler) is triggered, and the event **bubbles** further.
3. **3rd** — `onshow` on the outermost `<div>` (in the parent component) captures the event based on the **event name**, and `parentHandler` is finally triggered.

This is the essence of bubbling: a single dispatched event can trigger **multiple handlers**, one at each level of the DOM tree it passes through, as long as `bubbles: true` is set.

## 🧩 Component Code

### 1. Child Component — `chilToParentModalComponent.html`

The modal markup is mostly the same as previous examples, but note the **`slds-modal__footer`** `<div>` now also has its own `onclick={footerHandler}` — this is what will be used to demonstrate bubbling.

```html
<template>
    <section role="dialog" tabindex="-1" aria-modal="true" aria-labelledby="modal-heading-01"
        class="slds-modal slds-fade-in-open slds-modal_medium">
        <div class="slds-modal__container">

            <div class="slds-modal__header">
                <h1 id="modal-heading-01" class="slds-modal__title slds-hyphenate" tabindex="-1">
                    Child Modal</h1>
            </div>
            <div class="slds-modal__content slds-p-around_medium" id="modal-content-id-1">
                <p>Loaded Successfully.</p>
            </div>
            <div class="slds-modal__footer" onclick={footerHandler}>
                <button class="slds-button slds-button_brand" onclick={handleClick}>Ok</button>
            </div>
        </div>
    </section>
    <div class="slds-backdrop slds-backdrop_open" role="presentation"></div>
</template>
```

- `onclick={footerHandler}` on the **footer `<div>`** is a *native DOM click handler*, separate from the custom event system — it demonstrates that native click events already bubble automatically through plain HTML elements.
- `onclick={handleClick}` on the **Ok button** fires the custom `close` event (with `bubbles: true`), which is the one we're tracking through the component tree.

### 2. Child Component — `chilToParentModalComponent.js`

```js
import { LightningElement } from 'lwc';

export default class ChilToParentModalComponent extends LightningElement {
    handleClick(event) {
        const myEvent = new CustomEvent('close', {
            bubbles: true,
            detail: "Modal Closed Successfully!!."
        });
        this.dispatchEvent(myEvent);
    }

    footerHandler(event) {
        console.log('Footer button clicked');
    }
}
```

- `handleClick(event)` — fired when the **Ok** button is clicked.
  - `new CustomEvent('close', { bubbles: true, detail: "Modal Closed Successfully!!." })` creates a `close` event, this time explicitly setting `bubbles: true` (overriding the default `false`), in addition to carrying the same `detail` payload as before.
  - `this.dispatchEvent(myEvent)` fires the event. Because `bubbles: true`, this event will now propagate further up the DOM than in the "Event with Data" example.
- `footerHandler(event)` — a plain **native click handler** attached to the footer `<div>`. Native DOM click events bubble by default, so clicking the Ok button (which is inside the footer) also triggers this handler, and simply logs `'Footer button clicked'` to the console. This demonstrates native bubbling side-by-side with custom event bubbling.

### 3. Parent Component — `childToParentComponent.html`

Notice the key change here: **`onclose={handleClose}` is no longer only placed on the child's own tag** — it's moved up to the surrounding `<div>` in the parent, demonstrating that the bubbled event can be caught by *any* ancestor element, not just the immediate parent.

```html
<template>
    <lightning-card title="Child To Parent Communication">
        <div class="slds-p-around_medium" onclose={handleClose}>
            <h1>{msg}</h1>
            <lightning-button variant="brand" label="Show Modal" onclick={handleClick}></lightning-button>
            <template if:true={showModal}>
                <c-chil-to-parent-modal-component
                ></c-chil-to-parent-modal-component>
            </template>
        </div>
    </lightning-card>
</template>
```

- `onclose={handleClose}` has moved from the `<c-chil-to-parent-modal-component>` tag onto the **outer `<div class="slds-p-around_medium">`**.
- Because the `close` custom event was dispatched with `bubbles: true`, it still successfully reaches and triggers `handleClose` — even though the listener is no longer directly on the child's own tag, but on one of its ancestor elements.

### 4. Parent Component — `childToParentComponent.js`

```js
import { LightningElement } from 'lwc';

export default class ChildToParentComponent extends LightningElement {
    showModal = false;
    msg;

    handleClick(event) {
        this.showModal = true;
    }

    handleClose(event) {
        console.log('Handle close event Called.');
        this.msg = event.detail;
        this.showModal = false;
    }
}
```

- Logic is functionally identical to the "Event with Data" example — `handleClose` reads `event.detail` into `msg` and hides the modal.
- The `console.log('Handle close event Called.')` line is added purely to make it easy to verify (in the browser console) that this handler is indeed being triggered by the bubbled event, even though its listener sits on an ancestor `<div>` rather than directly on the child's tag.

## ⚙️ How It Works (Step-by-Step)

1. The user clicks **Show Modal** on the parent. `handleClick` sets `showModal = true`, rendering `<c-chil-to-parent-modal-component>`.
2. Inside the child modal, the user clicks the **Ok** button.
3. This triggers two things simultaneously, from innermost to outermost:
   - The button's own `onclick={handleClick}` fires the custom `close` event with `bubbles: true`.
   - Because the button sits inside the footer `<div>`, and native click events bubble by default, the footer's `onclick={footerHandler}` also fires, logging `'Footer button clicked'`.
4. The custom `close` event, because it was dispatched with `bubbles: true`, does not stop at the child component — it continues propagating **up through the DOM**, out of the child's shadow boundary, and into the parent component's template.
5. In the parent, the listener `onclose={handleClose}` is registered not on the child's own tag, but on the **surrounding `<div>`** — yet it still catches the bubbled event.
6. `handleClose` runs: it reads `event.detail` (`"Modal Closed Successfully!!."`) into `msg`, and sets `showModal = false`, hiding the modal.
7. The parent's `<h1>{msg}</h1>` updates automatically to display the message.

## 🔑 Key Takeaways

| Concept | Purpose |
|---|---|
| `bubbles: true` | Allows a custom event to propagate up through ancestor elements, instead of only reaching a listener on the immediate child tag |
| `composed` | Controls whether the event can cross the shadow DOM boundary (defaults to `false`, same as `bubbles`) |
| Native DOM events (e.g., plain `onclick`) | Bubble automatically by default — no configuration needed, unlike custom events |
| Listener placement | With bubbling, the `on<eventname>` listener can be placed on *any* ancestor element, not just the direct child's own tag |
| `event.detail` | Still used the same way to read data attached to the event, regardless of bubbling |

---

## 🆚 Comparing All Three Approaches

| Aspect | Simple Event | Event With Data | Event Bubbling |
|---|---|---|---|
| `bubbles` option | `false` (default) | `false` (default) | `true` (explicit) |
| `detail` payload | None | Present | Present |
| Listener location | Directly on child's own tag | Directly on child's own tag | Can be on **any ancestor**, not just the direct child tag |
| Use case | Simple notifications | Passing values back to parent | Multi-level nested components, or when the listener needs to live higher up the DOM tree |

## 💬 Interview Questions on This Topic

1. **How many event propagation options does LWC support, and what are they?**
   Two — `bubbles` and `composed`, both configured as options when creating a `CustomEvent`.

2. **What does the `bubbles` property control, and what is its default value?**
   It's a Boolean that determines whether the event propagates up through the DOM tree. It defaults to `false`.

3. **What does the `composed` property control, and what is its default value?**
   It's a Boolean that determines whether the event can cross the shadow DOM boundary (i.e., escape the component's own shadow tree). It also defaults to `false`.

4. **In the Event Bubbling demo, if a button inside two nested `<div>`s is clicked, in what order do the handlers fire?**
   From innermost to outermost — the button's own handler fires first, then the immediate parent `<div>`'s handler, then the outer `<div>`'s handler, as the event bubbles upward.

5. **Do native DOM events (like a plain `onclick` on a `<div>`) bubble by default?**
   Yes — native browser DOM events bubble automatically. It's specifically **custom events** created via `CustomEvent` in LWC that do not bubble unless explicitly configured with `bubbles: true`.

6. **Why would you set `bubbles: true` on a custom event in LWC?**
   To allow the event to be caught by an ancestor element that isn't the immediate parent — useful when a listener needs to sit further up the component tree, or in scenarios with multiple levels of nested components.

7. **If a `close` event is dispatched with `bubbles: true`, can the listener be placed anywhere other than directly on the child's own component tag?**
   Yes — with bubbling enabled, the listener (`onclose`) can be placed on any ancestor DOM element in the parent's template, and it will still catch the event as it propagates upward.

8. **What's the difference between `bubbles` and `composed`?**
   `bubbles` controls whether the event travels up through ancestor DOM elements. `composed` controls whether the event can cross out of the component's shadow DOM boundary to be caught by elements/components outside that shadow tree. Both are needed together in many real cross-component scenarios.

9. **In this modal example, what changed in the parent's template to demonstrate bubbling?**
   The `onclose={handleClose}` listener was moved from directly on the `<c-chil-to-parent-modal-component>` tag to the surrounding `<div>` element — and it still successfully catches the event because it was dispatched with `bubbles: true`.

10. **What's a real-world use case where event bubbling is especially useful?**
    Deeply nested component structures — e.g., a grandchild component inside a child component inside a parent — where you don't want to manually catch and re-dispatch the event at every intermediate level; bubbling lets a single ancestor-level listener catch it directly.

## 🚀 How to Deploy

1. Create the LWC components using the Salesforce CLI or VS Code Salesforce Extension:
   ```
   sfdx force:lightning:component:create --type lwc --componentname childToParentComponent
   sfdx force:lightning:component:create --type lwc --componentname chilToParentModalComponent
   ```
2. Copy the respective HTML/JS content into the generated files.
3. Deploy to your Salesforce org:
   ```
   sfdx force:source:deploy -p force-app/main/default/lwc/childToParentComponent
   sfdx force:source:deploy -p force-app/main/default/lwc/chilToParentModalComponent
   ```
4. Add the `childToParentComponent` to a Lightning App Page via **Lightning App Builder**, or place it on a test Aura/LWC tab.

## 📝 Notes

- This project builds on top of the **Simple Event** and **Event with Data** examples — the only change needed to enable bubbling is adding `bubbles: true` when creating the `CustomEvent`.
- Use bubbling thoughtfully: while powerful for deeply nested structures, overusing it (or forgetting to stop propagation when needed) can make event flow harder to trace in larger applications.
