# CSS Behaviour in Parent Child Component (LWC)

This project is part of a **Lightning Web Components (LWC)** learning series. It demonstrates how **CSS styling scopes and behaves** across a Parent-Child component relationship — including the use of the **`:host`** pseudo-class and CSS applied to **slotted content**.

---

## 📌 Concept Overview: CSS Behaviour in Parent Child Component

LWC enforces **CSS encapsulation** through the Shadow DOM. This leads to four important rules:

1. **Parent CSS can't reach into a child component.**
2. **A parent component CSS can style a host element (`<c-css-child>`).**
3. **A Child Component CSS can reach up and style its own host element.**
4. **You can style an element passed into the slot from the parent component only.**

**In simple words:** Each LWC component's CSS file is scoped strictly to that component's own template. A parent's CSS cannot dictate how the inside of a child component looks. However, there are two specific exceptions where styling crosses this boundary:
- The **parent** can style the child's outer wrapper tag (its "host element", e.g., `<c-css-child-demo>`) directly — as if it were any other HTML tag in its own template.
- The **child** can style its own host element from the inside, using the special `:host` CSS selector.
- For **slotted content** specifically (markup the parent passes into a child's `<slot>`), styling ownership stays with whoever wrote that markup — the **parent's CSS** (not the child's) controls how it looks, since the parent is the one who authored it.

## 🧩 Child Component Code

### 1. `cssChildDemo.html`

```html
<template>
    <h1>Hello, I am child Component.</h1>
    <slot></slot>
</template>
```

- `<h1>Hello, I am child Component.</h1>` → the child's own static content.
- `<slot></slot>` → an **unnamed slot**, which will render whatever markup the parent passes in between the `<c-css-child-demo>` opening and closing tags.

### 2. `cssChildDemo.js`

```js
import { LightningElement } from 'lwc';

export default class CssChildDemo extends LightningElement {}
```

- No special JavaScript logic is needed for this demo — the focus here is purely on CSS behavior.

### 3. `cssChildDemo.css` — Using `:host`

```css
:host {
    display: block;
    background: red;
    color: white;
}

:host(.blue) {
    display: block;
    background: blue;
    color: white;
}
```

- **`:host`** → a special CSS pseudo-class that lets a component style **its own outer host element** (i.e., the `<c-css-child-demo>` tag itself, as it appears in the parent's template) from *within* the child's own CSS file. Here, it sets a `red` background with `white` text by default.
- **`:host(.blue)`** → this is `:host` combined with a **class selector condition**. It only applies these styles (`blue` background, `white` text) **if** the host element itself has the CSS class `blue` applied to it externally — for example, if the parent writes `<c-css-child-demo class="blue">`.
- This demonstrates that while a child normally can't be *directly* told what to look like by its parent, `:host(.className)` allows the child to expose specific "themeable" variations that a parent can opt into simply by adding a class name — without ever writing CSS that reaches into the child.

### 4. `cssChildDemo.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>false</isExposed>
</LightningComponentBundle>
```

- `isExposed>false</isExposed>` — the child component isn't meant to be placed independently on a page; it's used only inside `cssParentDemo`.

## 🧩 Parent Component Code

### 5. `cssParentDemo.html`

```html
<template>
    <lightning-card title="Parent CSS Demo">
        <div class="slds-p-around_medium">
            <h1>Hello i am Parent Component.</h1>
            <c-css-child-demo>
                <p>Hello I am slot one.</p>
            </c-css-child-demo> <br>
            <c-css-child-demo class="blue">
                <p>Hello I am slot two.</p>
            </c-css-child-demo>
        </div>
    </lightning-card>
</template>
```

- The child component `<c-css-child-demo>` is used **twice**:
  - **First instance** — no extra class is applied, so it uses the child's **default `:host` styling** (red background). A `<p>Hello I am slot one.</p>` is passed into its unnamed slot.
  - **Second instance** — has `class="blue"` applied directly on the `<c-css-child-demo>` tag. Because the child's CSS defines `:host(.blue)`, this instance instead renders with a **blue background**. A separate `<p>Hello I am slot two.</p>` is passed into its slot.
- Notice this is a case of **Rule 2** from the concept overview in action: *"A parent component CSS can style a host element (`<c-css-child>`)"* — here it's done simply by applying a class attribute directly on the child's tag, which the child's own `:host(.className)` rule then reacts to.

### 6. `cssParentDemo.js`

```js
import { LightningElement } from 'lwc';

export default class CssParentDemo extends LightningElement {}
```

- No special logic needed — again, this demo is focused entirely on CSS behavior.

### 7. `cssParentDemo.css`

```css
h1 {
    font-size: 30px;
    color: red;
}

/* c-css-child-demo {
    display: block;
    background: green;
    color: white;
} */

p {
    font-size: 20px;
    color: yellow;
}
```

- **`h1 { font-size: 30px; color: red; }`** → this styles **all** `<h1>` elements that exist directly in the *parent's own template* — this includes `<h1>Hello i am Parent Component.</h1>`, but **NOT** the `<h1>Hello, I am child Component.</h1>` inside the child, because that `<h1>` lives inside the child's own encapsulated Shadow DOM, which the parent's CSS cannot reach (**Rule 1**: *"Parent CSS can't reach into a child component"*).
- **The commented-out block** — `c-css-child-demo { display: block; background: green; color: white; }` — is intentionally left commented to demonstrate that while a parent *can* technically target the child's host tag using its element/tag name as a CSS selector (as an alternative to the class-based approach shown above), this specific example instead relies on the `class="blue"` + `:host(.blue)` technique in the child's own CSS. Either approach is valid for styling the host element from the parent side.
- **`p { font-size: 20px; color: yellow; }`** → this is the key demonstration of **Rule 4**: *"You can style an element pass into the slot from the parent component only."* Both `<p>Hello I am slot one.</p>` and `<p>Hello I am slot two.</p>` were written by the **parent** and passed into the child's slot — so even though they visually render *inside* the child component, their styling is still controlled by the **parent's** CSS file (turning them yellow, 20px), not the child's.

### 8. `cssParentDemo.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__AppPage</target>
    </targets>
</LightningComponentBundle>
```

- `isExposed>true</isExposed>` and `<target>lightning__AppPage</target>` expose the parent component for direct placement on a **Lightning App Page** via App Builder.

## ⚙️ How It Works (Step-by-Step)

1. The parent renders its own `<h1>Hello i am Parent Component.</h1>`, styled **red, 30px** by the parent's own CSS (`h1 { color: red; font-size: 30px; }`).
2. The parent embeds `<c-css-child-demo>` twice.
3. **First instance:** no class applied → the child's own `:host { background: red; color: white; }` rule applies, giving it a **red background**. Inside, the child's own `<h1>Hello, I am child Component.</h1>` remains styled only by the child's CSS (the parent's `h1` rule cannot reach it).
4. The `<p>Hello I am slot one.</p>` passed by the parent renders inside the child's `<slot>` — but its **yellow, 20px** styling comes from the **parent's** `p { ... }` CSS rule, since the parent authored that markup.
5. **Second instance:** `class="blue"` is applied directly on `<c-css-child-demo>` → this triggers the child's `:host(.blue) { background: blue; color: white; }` rule instead, giving it a **blue background**.
6. Again, the `<p>Hello I am slot two.</p>` passed into this instance's slot is styled **yellow, 20px** by the **parent's** CSS — proving that slot styling always belongs to whichever component wrote the slotted markup, regardless of which component it visually appears inside.

## 🔑 Key Takeaways

| Rule | Explanation |
|---|---|
| 1. Parent CSS can't reach into a child | A parent's CSS selectors (e.g., `h1 {...}`) never apply to elements inside a child component's own template — Shadow DOM blocks this. |
| 2. Parent CSS can style the child's host element | The parent can affect the child's outer `<c-css-child-demo>` tag directly — e.g., by applying a class the child's own `:host(.class)` rule reacts to, or by targeting the tag name as a selector. |
| 3. Child CSS can style its own host element | Using the `:host` pseudo-class, a child can style its own outer wrapper tag from within its own CSS file. |
| 4. Slotted content is styled by the parent | Any markup the parent passes into a child's `<slot>` keeps its styling ownership with the **parent's** CSS, even though it visually renders inside the child. |

## 🆚 `:host` vs. `:host(.className)`

| Selector | Applies When | Example Use |
|---|---|---|
| `:host` | Always, to every instance of the component | Default styling for the component's host element |
| `:host(.className)` | Only when the host element has the specified class applied externally (usually by the parent) | Theming/variant styling — e.g., a "blue" or "danger" variant a parent can opt into |

## 💬 Interview Questions on This Topic

1. **Why can't a parent component's CSS style elements inside a child component in LWC?**
   Because LWC uses the Shadow DOM for component encapsulation — each component's template and styles are scoped and isolated, preventing CSS from one component from leaking into or affecting another's internal markup.

2. **What is the `:host` pseudo-class used for in LWC?**
   It lets a component apply CSS styles to its **own outer host element** — the tag as it appears when used in a parent's template (e.g., `<c-css-child-demo>`) — from within the component's own CSS file.

3. **What does `:host(.className)` do differently from plain `:host`?**
   `:host(.className)` only applies its styles when the host element additionally has the specified CSS class applied to it (typically added externally, e.g., by a parent writing `<c-child class="blue">`). Plain `:host` applies unconditionally to every instance.

4. **Can a parent component style a child component's host element? If so, how?**
   Yes — a parent can style a child's host element in its own CSS (e.g., using the child's tag name as a selector), and/or by applying a class to the child's tag that the child's own `:host(.className)` rule is designed to respond to.

5. **How does styling work for content passed into a slot — does the parent's or the child's CSS apply?**
   The **parent's** CSS applies, because the parent is the one who authored that markup — even though it visually renders inside the child's template via the `<slot>`.

6. **In this project, why does the first `<c-css-child-demo>` instance appear red while the second appears blue?**
   The child's CSS defines a default `:host { background: red; ... }` rule that applies to any instance without a class. The second instance has `class="blue"` applied directly on its tag, which activates the child's `:host(.blue) { background: blue; ... }` rule instead.

7. **Why does the parent's `<h1>` render in red/30px, but the child's own `<h1>` inside its template does not?**
   The parent's CSS rule `h1 { color: red; font-size: 30px; }` only applies within the parent's own encapsulated template. The child's `<h1>` lives inside the child's separate Shadow DOM boundary, which the parent's CSS selectors cannot cross.

8. **Why do both `<p>` elements (slot one and slot two) appear in yellow, even though they're rendered inside different `c-css-child-demo` instances?**
   Because both `<p>` elements were authored by the **parent**, and passed into the child's slot — so they're still governed by the parent's own `p { color: yellow; font-size: 20px; }` CSS rule, regardless of which child component instance they end up rendering inside.

9. **What is the significance of leaving a selector like `c-css-child-demo {...}` commented out in the parent's CSS in this example?**
   It demonstrates an *alternative* way a parent can style a child's host element — directly by using the child's custom element tag name as a CSS selector — as opposed to the class + `:host(.className)` technique that was actually used and demonstrated live in this example.

10. **What is the overall design principle behind LWC's CSS encapsulation rules?**
    To promote strong component isolation and reusability — a component's internal styling should not be affected by wherever it happens to be used, while still giving components controlled, intentional ways (via `:host`, host-element styling, and slot ownership) to allow certain styling to cross component boundaries when explicitly designed to do so.

## 🚀 How to Deploy

1. Create the LWC components using the Salesforce CLI or VS Code Salesforce Extension:
   ```
   sfdx force:lightning:component:create --type lwc --componentname cssChildDemo
   sfdx force:lightning:component:create --type lwc --componentname cssParentDemo
   ```
2. Copy the respective HTML/JS/CSS/meta.xml content into the generated files.
3. Deploy to your Salesforce org:
   ```
   sfdx force:source:deploy -p force-app/main/default/lwc/cssChildDemo
   sfdx force:source:deploy -p force-app/main/default/lwc/cssParentDemo
   ```
4. Add the `cssParentDemo` component to a Lightning App Page via **Lightning App Builder**.
