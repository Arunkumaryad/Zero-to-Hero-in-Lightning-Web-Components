# Passing Markup Using Slots (LWC)

This project is part of a **Lightning Web Components (LWC)** learning series. It demonstrates how to use **Slots** to pass **HTML markup** (not just data) from a Parent Component into a Child Component — including **Named Slots**, **Unnamed Slots**, and detecting slot content changes with `onslotchange`.

---

## 📌 Concept Overview: Passing Markup into Slots

1. **Slot is useful to pass HTML markup into another component.**
2. **`<slot></slot>` markup is used to catch the HTML passed by the parent component.**
3. **You can't pass an Aura component into a slot.**

### There are two types of Slots

| Slot Type | Definition |
|---|---|
| **Named Slots** | When a **`name`** attribute is defined in the slot element: `<slot name="user"></slot>` |
| **Unnamed Slots** | When a slot is used **without** a `name` attribute: `<slot></slot>` |

**In simple words:** A slot is a placeholder that a child component defines in its own template — marking a spot where the **parent component's own markup** should be inserted. This lets the parent inject custom HTML (paragraphs, buttons, images, etc.) directly into specific positions inside the child, rather than the child only ever displaying its own fixed content.

## 🧩 Component Code

### 1. Child Component — `slotChildDemo.html`

This is where the slots are **defined** — using both unnamed content and two named slots (`"first"` and `"second"`), plus a third named slot (`"footer"`) that starts hidden.

```html
<template>
    <div>What is your name ??</div>
    <div><slot name="first"></slot></div>  <!-- unnamed slots -->
    <div>What is your age ?</div>
    <div><slot name="second"></slot></div>
    <br>
    <footer class="slds-modal__footer slds-hide">
        <slot name="footer" onslotchange={handleSlotChange}></slot>
    </footer>
</template>
```

- `<div>What is your name ??</div>` and `<div>What is your age ?</div>` are the child's **own static content** — these are not slots, they always render exactly as written.
- `<slot name="first"></slot>` → a **Named Slot** called `"first"`. Any markup the parent assigns to `slot="first"` will render here.
- `<slot name="second"></slot>` → a second **Named Slot** called `"second"`, for a different piece of parent-provided markup.
- `<footer class="slds-modal__footer slds-hide">` → the footer starts with the `slds-hide` class applied, meaning it's **hidden by default**.
- `<slot name="footer" onslotchange={handleSlotChange}></slot>` → a third **Named Slot** called `"footer"`, with an `onslotchange` event handler attached. This event fires whenever the content assigned to this slot changes (including when it's first rendered) — used here to reveal the footer only if content is actually provided.

### 2. Child Component — `slotChildDemo.js`

```js
import { LightningElement } from 'lwc';

export default class SlotChildDemo extends LightningElement {

    handleSlotChange() {
        const slotElement = this.template.querySelector('.slds-modal__footer');
        if(slotElement) {
            slotElement.classList.remove('slds-hide');
        }
    }
}
```

- `handleSlotChange()` — runs whenever the `onslotchange` event fires on the `"footer"` slot (i.e., whenever the parent assigns or changes content for that slot).
  - `this.template.querySelector('.slds-modal__footer')` → finds the `<footer>` element inside the child's own template.
  - `if (slotElement) { slotElement.classList.remove('slds-hide'); }` → if the footer element is found, its `slds-hide` class is removed, which makes it **visible**.
- **The overall effect:** the footer stays hidden until the parent actually provides content for the `"footer"` slot — at which point `onslotchange` fires and the footer becomes visible. This is a common pattern for conditionally showing UI sections only when a parent has chosen to populate them.

### 4. Parent Component — `slotParentDemo.html`

The parent demonstrates the child component being used **twice** — once passing content into **all three slots** (`first`, `second`, `footer`), and once with the `footer` slot content **commented out**, to show the difference in behavior.

```html
<template>
    <lightning-card title="Slot Parent Demo">
        <div class="slds-p-around_medium">
            <c-slot-child-demo>
                <p class="slds-text-color_success" slot="first">My name is Arun Kumar.</p>
                <p class="slds-text-color_error" slot="second">My age is : 25</p>
                <p slot="footer">I am footer.</p>
            </c-slot-child-demo>
        </div>

        <div class="slds-p-around_medium">
            <c-slot-child-demo>
                <p class="slds-text-color_success" slot="first">My name is Arun Kumar.</p>
                <p class="slds-text-color_error" slot="second">My age is : 25</p>
                <!-- <p slot="footer">I am footer.</p> -->
            </c-slot-child-demo>
        </div>
    </lightning-card>
</template>
```

- `<c-slot-child-demo>` → embeds the child component.
- `slot="first"`, `slot="second"`, `slot="footer"` → these attributes on the `<p>` elements tell LWC **which named slot** in the child each piece of markup should be inserted into.
  - `<p slot="first">My name is Arun Kumar.</p>` → goes into the child's `<slot name="first">`.
  - `<p slot="second">My age is : 25</p>` → goes into the child's `<slot name="second">`.
  - `<p slot="footer">I am footer.</p>` → goes into the child's `<slot name="footer">`, which triggers `onslotchange` in the child, revealing the footer.
- In the **second** instance of `<c-slot-child-demo>`, the `slot="footer"` paragraph is **commented out** — meaning no content is provided for the `"footer"` slot at all. As a result, `onslotchange` either doesn't fire meaningfully or the slot remains empty, so the footer stays hidden (`slds-hide` is never removed) for this second instance.

### 5. Parent Component — `slotParentDemo.js`

```js
import { LightningElement } from 'lwc';

export default class SlotParentDemo extends LightningElement {}
```

- The parent component doesn't need any special logic of its own here — all the slot assignment happens declaratively in the HTML template using the `slot="..."` attribute.

## ⚙️ How It Works (Step-by-Step)

1. The child component (`slotChildDemo`) defines its template with fixed content ("What is your name ??", "What is your age ?") interspersed with **three named slots**: `first`, `second`, and `footer`.
2. The `footer` slot sits inside a `<footer>` element that starts with the `slds-hide` CSS class, so it's invisible by default.
3. The parent component embeds `<c-slot-child-demo>` and, using the `slot="..."` attribute on its own `<p>` elements, assigns specific markup to each named slot.
4. When the browser renders this, LWC takes each piece of parent markup and inserts it into the matching `<slot name="...">` location inside the child's template — this is standard **Shadow DOM slotting** behavior, not unique to LWC (it's a native web component feature).
5. Because content was assigned to the `footer` slot, the `onslotchange` event fires on that slot in the child.
6. This triggers `handleSlotChange()` in the child's JS, which finds the `<footer>` element and removes the `slds-hide` class — making the footer visible with the parent-provided **"I am footer."** text inside it.
7. In the parent's **second usage** of `<c-slot-child-demo>`, the `slot="footer"` paragraph is commented out, so no content is assigned to that slot — and the footer remains hidden, since `onslotchange` doesn't reveal it with meaningful content (or the footer stays empty and hidden as designed).

## 🔑 Key Takeaways

| Concept | Purpose |
|---|---|
| `<slot></slot>` | Placeholder inside a child component's template where parent-provided markup gets inserted |
| Named Slot (`<slot name="...">`) | Lets a component define **multiple** distinct insertion points, each targeted individually by the parent using `slot="..."` |
| Unnamed Slot (`<slot></slot>`, no `name`) | A single, generic slot — any parent markup without a `slot="..."` attribute goes here |
| `slot="..."` attribute (on parent's markup) | Tells LWC which named slot in the child a given piece of markup should be placed into |
| `onslotchange` | Event that fires when the content assigned to a slot changes — useful for reacting to whether/what content was provided |
| Aura component limitation | LWC slots **cannot** accept an Aura component as slotted content |

---

## 🆚 Named Slots vs. Unnamed Slots

| Aspect | Named Slots | Unnamed Slots |
|---|---|---|
| Declaration in child | `<slot name="user"></slot>` | `<slot></slot>` |
| How parent targets it | `<p slot="user">...</p>` | Any markup with **no** `slot` attribute |
| Number allowed per component | Multiple (each with a unique name) | Only **one** unnamed slot per component |
| Use case | When the child needs several distinct, independently placed content areas | When the child just needs one generic content area |

## 💬 Interview Questions on This Topic

1. **What is a slot in LWC, and what problem does it solve?**
   A slot is a placeholder in a child component's template that lets a parent component inject its own custom HTML markup into specific locations within the child — enabling flexible, composable UI structures rather than the child only ever showing fixed, static content.

2. **What's the difference between a Named Slot and an Unnamed Slot?**
   A Named Slot has a `name` attribute (`<slot name="user"></slot>`) and can be individually targeted by the parent using a matching `slot="user"` attribute. An Unnamed Slot has no `name` attribute (`<slot></slot>`) and catches any parent markup that doesn't specify a `slot` attribute — only one unnamed slot is allowed per component.

3. **Can you pass an Aura component into an LWC slot?**
   No — LWC slots cannot accept Aura components as slotted content.

4. **How does a parent component specify which named slot a piece of markup should go into?**
   By adding a `slot="slotName"` attribute directly on the element being passed, matching the `name` attribute of the corresponding `<slot name="slotName">` in the child.

5. **What does the `onslotchange` event do, and when does it fire?**
   It's an event handler attached directly to a `<slot>` element that fires whenever the content assigned to that slot changes — including when content is first slotted in. It's commonly used to react to whether (or what) content the parent has provided.

6. **In this example, why does the footer stay hidden by default, and how is it revealed?**
   The `<footer>` element starts with the `slds-hide` CSS class applied. When the parent provides content for the `footer` named slot, the `onslotchange` event fires in the child, running `handleSlotChange()`, which removes the `slds-hide` class — making the footer visible only when there's actual content to show.

7. **Why does the child use `this.template.querySelector()` inside `handleSlotChange`, and what would happen without the `if (slotElement)` check?**
   `this.template.querySelector()` finds the footer element within the child's own shadow DOM template so its class can be modified. Without the `if (slotElement)` check, calling `.classList.remove()` on a `null` result (if the element weren't found) would throw a runtime error.

8. **What is the maximum number of unnamed slots a single component can have?**
   Only **one**. A component can have multiple named slots, but only a single unnamed (default) slot.

9. **What happens if the parent doesn't provide any content for a given named slot?**
   The slot simply renders empty — unless the child template also defines fallback/default content directly inside the `<slot>` tags, which is used only when no content is provided by the parent.

10. **How is slot-based markup passing different from passing data via `@api` properties?**
    `@api` properties pass **data** (strings, numbers, objects, arrays) from parent to child, which the child then uses within its own predefined template structure. Slots pass **actual HTML markup**, letting the parent directly control the structure/content rendered at specific points inside the child's template — this is fundamentally about composing UI, not just passing values.

## 🚀 How to Deploy

1. Create the LWC components using the Salesforce CLI or VS Code Salesforce Extension:
   ```
   sfdx force:lightning:component:create --type lwc --componentname slotChildDemo
   sfdx force:lightning:component:create --type lwc --componentname slotParentDemo
   ```
2. Copy the respective HTML/JS/meta.xml content into the generated files.
3. Deploy to your Salesforce org:
   ```
   sfdx force:source:deploy -p force-app/main/default/lwc/slotChildDemo
   sfdx force:source:deploy -p force-app/main/default/lwc/slotParentDemo
   ```
4. Add the `slotParentDemo` component to a Lightning App Page via **Lightning App Builder**.

## 📝 Notes

- Slots are a **native web component / Shadow DOM feature**, not something invented specifically by LWC — this makes the concept transferable to plain web components as well.
- Slots are especially useful for building **reusable "wrapper" or "layout" components** (e.g., modals, cards, accordions) where the outer structure/styling is fixed, but the inner content needs to vary depending on how the component is used.
- Combine slots with `onslotchange` when you need to conditionally show/hide or otherwise react to whether the parent has actually provided content for a given slot.
