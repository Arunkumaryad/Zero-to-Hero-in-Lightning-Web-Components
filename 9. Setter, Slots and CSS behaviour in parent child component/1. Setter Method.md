# Setter Method (@api Getter/Setter) in LWC

This project is part of a **Lightning Web Components (LWC)** learning series. It demonstrates the **Setter Method** pattern — using `@api` **getters and setters** to intercept, validate, or transform data as it flows from a Parent Component into a Child Component.

---

## 📌 Concept Overview: Setter Method

> **This method is used to modify the data coming from the parent component.**
> **If an Object is passed as data to the setter, to mutate the object we have to create a shallow copy.**

Normally, when a parent passes data to a child using a plain `@api` property, the child receives it as-is, with no opportunity to intercept or transform it. An **`@api` getter/setter pair** changes that — it lets the child component run custom logic **every time new data arrives from the parent**, before storing it.

### Basic Pattern

```js
@api
get detail() {
    return this.userObject;
}

set detail(data) {
    let newData = // mutation of logic
    this.userObject = newData
}
```

- `@api get detail()` → the **getter** — defines what value is returned whenever something reads `this.detail` (or when the parent's template reads the property).
- `set detail(data)` → the **setter** — automatically runs whenever the parent passes a new value into this property (e.g., `<c-child details={someValue}>`). The incoming value is available as `data`.
- Inside the setter, `newData` represents wherever your **mutation/transformation logic** goes, and the result is stored into a separate internal property (`this.userObject`) — **not** back into `detail` itself, since `detail` is only a getter/setter pair, not a real storage location.
- **Important:** if `data` is an **object**, you should not mutate it directly (since it's a reference passed from the parent) — instead, create a **shallow copy** (e.g., using the spread operator `{ ...data }`) before modifying any of its fields.

## 🧩 Component Code

### 1. Parent Component — `setterDemoParent.html`

```html
<template>
    <lightning-card title="Setter Demo Parent">
        <c-setter-demo-child details={userDetails}></c-setter-demo-child>
    </lightning-card>
</template>
```

- The parent embeds the child using `<c-setter-demo-child>`, and passes its `userDetails` object into the child's `details` property.

### 2. Parent Component — `setterDemoParent.js`

```js
import { LightningElement } from 'lwc';

export default class SetterDemoParent extends LightningElement {
    userDetails = {
        name: 'Arun Kumar',
        age: 25
    }
}
```

- `userDetails` is a plain object with two fields: `name` and `age`. Notice there's **no `location`** field here — this is important, because the child's setter will end up **adding** a `location` field itself (see below).

### 3. Parent Component Metadata — `setterDemoParent.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__AppPage</target>
    </targets>
</LightningComponentBundle>
```

- `isExposed>true</isExposed>` and `<target>lightning__AppPage</target>` make the parent component available for placement on a **Lightning App Page** via App Builder.

### 4. Child Component — `setterDemoChild.html`

```html
<template>
    <p><strong>Name : - </strong> {details.name}</p>
    <p><strong>Age : - </strong> {details.age}</p>
    <p><strong>Location : - </strong> {details.location}</p>
</template>
```

- Displays three fields from the `details` object: `name`, `age`, and `location` — even though the parent only originally sent `name` and `age`.

### 5. Child Component — `setterDemoChild.js`

```js
import { LightningElement, api } from 'lwc';

export default class SetterDemoChild extends LightningElement {
    userDetail;
    @api get details() {
        return this.userDetail;
    }

    set details(data) {
        let newAge = data.age * 4;
        this.userDetail = { ...data, age: newAge, "location": "Gaur City Mall Noida" };
    }
}
```

**Explanation, line by line:**

- `userDetail;` — a private internal property that will actually **hold** the data. This is necessary because `details` itself is just a getter/setter pair, not a real variable.
- `@api get details() { return this.userDetail; }` — the **getter**: whenever `this.details` is read (including in the template via `{details.name}`), it simply returns whatever is currently stored in `this.userDetail`.
- `set details(data) { ... }` — the **setter**: this runs automatically every time the parent updates the `details` property being passed to the child (i.e., whenever `<c-setter-demo-child details={userDetails}>` sends new data).
  - `let newAge = data.age * 4;` — takes the incoming `age` value from the parent and **multiplies it by 4**, demonstrating a simple data transformation.
  - `this.userDetail = { ...data, age: newAge, "location": "Gaur City Mall Noida" };` — this is the **shallow copy** in action:
    - `{ ...data, ... }` spreads all the original fields from `data` (i.e., `name` and `age`) into a **brand-new object**, rather than mutating the parent's original `data` object directly.
    - `age: newAge` then **overrides** the copied `age` field with the newly calculated value (`age * 4`).
    - `"location": "Gaur City Mall Noida"` **adds a completely new field** that didn't exist in the original object sent by the parent.
  - The final, transformed object is stored into `this.userDetail`, which the getter (and the template) will then read from.

### 6. Child Component Metadata — `setterDemoChild.js-meta.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>67.0</apiVersion>
    <isExposed>false</isExposed>
</LightningComponentBundle>
```

- `isExposed>false</isExposed>` — unlike the parent, the child component is **not** exposed for direct placement on an App Page (no `<targets>` block either). It's meant to be used only internally, as a child inside `setterDemoParent`.

## ⚙️ How It Works (Step-by-Step)

1. The parent component defines `userDetails = { name: 'Arun Kumar', age: 25 }` and passes it to the child via `<c-setter-demo-child details={userDetails}>`.
2. Because the child declares `details` as an `@api` **getter/setter pair** (not a plain property), passing data into it automatically invokes the **setter** (`set details(data)`), with `data` being `{ name: 'Arun Kumar', age: 25 }`.
3. Inside the setter:
   - `newAge` is calculated as `25 * 4 = 100`.
   - A **new object** is created using the spread operator: `{ ...data, age: newAge, location: "Gaur City Mall Noida" }`, resulting in `{ name: 'Arun Kumar', age: 100, location: 'Gaur City Mall Noida' }`.
   - This new object is stored in `this.userDetail`.
4. The child's template reads `details.name`, `details.age`, and `details.location` — each access triggers the **getter** (`get details()`), which returns `this.userDetail`.
5. The rendered output on screen becomes:
   ```
   Name : - Arun Kumar
   Age : - 100
   Location : - Gaur City Mall Noida
   ```
6. Notice the **age has been transformed** (25 → 100) and a **location field has been added** — neither of which existed in the original data sent by the parent. This demonstrates how the setter method intercepts and modifies incoming data before it's ever used or displayed.

## 🔑 Key Takeaways

| Concept | Purpose |
|---|---|
| `@api get property()` | Defines what value is returned whenever the property is read (by the template or externally) |
| `set property(data)` | Automatically runs whenever the parent passes a new value into this property; used to intercept/transform incoming data |
| Private backing property (e.g., `userDetail`) | Needed because the `@api` property itself is only a getter/setter pair — actual storage happens in a separate internal variable |
| Shallow copy (`{ ...data }`) | Prevents directly mutating the object reference passed by the parent; creates a new object instead |
| Data transformation in setter | Lets you validate, reformat, enrich, or default incoming data before the component uses or displays it |

---

## 🆚 Plain `@api` Property vs. `@api` Getter/Setter

| Aspect | Plain `@api` property | `@api` Getter/Setter |
|---|---|---|
| Declaration | `@api details;` | `@api get details() {...}` and `set details(data) {...}` |
| Data flow | Value is stored and used as-is | You can intercept, validate, transform, or enrich the value as it arrives |
| Storage | The property itself holds the value | A separate private property (e.g., `userDetail`) is needed to hold the actual data |
| Use case | Simple pass-through of data | Whenever the child needs to react to, modify, or compute derived values from incoming data |

## 💬 Interview Questions on This Topic

1. **What is the purpose of the setter method in LWC?**
   To modify or intercept data that's coming in from the parent component, before it's stored or used by the child.

2. **Why do you need a separate private property (like `userDetail`) alongside an `@api` getter/setter?**
   Because the `@api` property declared with `get`/`set` is not itself a storage location — it's just a pair of functions. The actual data needs to live somewhere, so a separate internal property is used to hold it.

3. **What happens if you try to mutate an object passed into a setter directly, instead of creating a shallow copy?**
   You risk directly mutating the parent's original object, since objects in JavaScript are passed by reference. This can cause unexpected side effects in the parent (or anywhere else that object is referenced), and can violate LWC's data-immutability best practices.

4. **How do you create a shallow copy of an object in JavaScript, and why is it called "shallow"?**
   Using the spread operator, e.g., `{ ...data }`. It's called "shallow" because it only copies the top-level properties — if any of those properties are themselves objects or arrays, those nested structures are still shared by reference with the original.

5. **In the example, what transformation is applied to `age`, and what new field is added?**
   `age` is multiplied by 4 (`data.age * 4`), and a new `location` field (`"Gaur City Mall Noida"`) is added — a field that didn't exist in the original data sent by the parent.

6. **When exactly does the setter function get invoked?**
   Every time the parent component passes a new value into the corresponding property — e.g., whenever the bound expression in the parent's template (`details={userDetails}`) changes, or on initial render when the value is first passed down.

7. **Can you have an `@api` setter without a corresponding getter (or vice versa)?**
   No — in JavaScript, if you define a setter for a property, you generally also need a getter if you want to read that property's value back (otherwise reading it would return `undefined`). LWC requires both to be defined together as an accessor pair for `@api` reactive properties.

8. **What is the real-world use case for using a setter instead of a plain `@api` property?**
   Common use cases include: validating or sanitizing incoming data, providing default values for missing fields, transforming data formats (e.g., converting a date string to a Date object), or computing/deriving additional fields based on the incoming data — exactly as shown by adding `location` and recalculating `age` in this example.

9. **Why is `isExposed` set to `false` for the child component but `true` for the parent?**
   The child component (`setterDemoChild`) is meant to be used only internally by its parent, not placed independently on a Lightning App Page, so it doesn't need to be exposed. The parent (`setterDemoParent`) is the entry point meant to be added directly to a page, so it's exposed with a `<target>`.

10. **What would happen if the child's template tried to read `{details.location}` without the setter adding that field?**
    It would simply render as blank/undefined, since `location` wouldn't exist on the object — this is exactly why the setter proactively adds the `location` field, ensuring the template always has the data it expects to display.

## 🚀 How to Deploy

1. Create the LWC components using the Salesforce CLI or VS Code Salesforce Extension:
   ```
   sfdx force:lightning:component:create --type lwc --componentname setterDemoParent
   sfdx force:lightning:component:create --type lwc --componentname setterDemoChild
   ```
2. Copy the respective HTML/JS/meta.xml content into the generated files.
3. Deploy to your Salesforce org:
   ```
   sfdx force:source:deploy -p force-app/main/default/lwc/setterDemoParent
   sfdx force:source:deploy -p force-app/main/default/lwc/setterDemoChild
   ```
4. Add the `setterDemoParent` component to a Lightning App Page via **Lightning App Builder**.

## 📝 Notes

- Getter/setter accessors on `@api` properties are one of the most commonly asked LWC interview topics, since they combine **JavaScript accessor syntax**, **immutability best practices**, and **LWC's reactivity model** all in one pattern.
- Always remember: **never mutate an object or array received via a setter directly** — always create a new copy (shallow with `{ ...obj }` / `[ ...arr ]`, or deep if nested structures also need to change) before modifying it.
